## Что сделано (zoom out)

База данных выросла с 4 базовых таблиц (`users`, `staff`, `conversations`, `messages`) до **9 таблиц**:
добавлены 5 новых — `services` (публичный каталог), `orders` (заказы),
`order_events` (append-only audit log), `payments` (записи о платежах),
`attachments` (ссылки на файлы в Supabase Storage). Плюс 10 услуг в seed-каталоге
(Claude, ChatGPT, Netflix, Spotify, Airbnb, YouTube, Discord, Midjourney, LinkedIn, Apple)
с правильным `requires_kyc` для Airbnb / LinkedIn Premium / Apple One.

Repository-функции (`createOrder`, `transitionOrder`, `appendOrderEvent`, `recordPayment`,
`listActiveServices`) и AI-tools (`search_catalog`, `propose_order`, `confirm_order`,
`request_human`) **в этот milestone не входили** — это следующая итерация
«State machine + AI tools».

## Решения (краткое зеркало плана)

- **5 таблиц + 5 enum'ов одной auto-migration.** `orderStatusEnum` (13 значений),
  `paymentProviderEnum`, `paymentStatusEnum`, `attachmentKindEnum`, `actorTypeEnum`.
  Drizzle сгенерировал атомарный `0003_common_richard_fisk.sql`.
- **`services` БЕЗ RLS** — публичный каталог по `docs/database.md`. На остальных 4 новых
  таблицах RLS включён через `.enableRLS()` в schema.ts (Drizzle сразу эмитит
  `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` в auto-migration — отдельный
  `0004_enable_rls_extended.sql` не понадобился; запланированный шаг стал no-op).
- **CHECK constraint `orders_service_or_custom`** — `service_id IS NOT NULL OR custom_service_description IS NOT NULL`.
  Заказ не может быть «пустым» — либо услуга из каталога, либо кастомное описание.
- **`UNIQUE(provider, provider_ref)` на `payments`** — основа идемпотентности webhook'ов
  (`CLAUDE.md` инвариант): повторный `INSERT` падает с `23505 unique_violation`.
- **FK-стратегия:**
  - `orders.user_id` → `users.id` `ON DELETE RESTRICT` (не теряем заказы);
  - `order_events.order_id` → `orders.id` `ON DELETE CASCADE` (события следуют за заказом);
  - `payments.order_id` → `orders.id` `ON DELETE RESTRICT` (нельзя удалить заказ с платежом);
  - `attachments.{order_id, message_id}` → `ON DELETE SET NULL` (файлы переживают удаление родителя).
- **`order_events.actor_id`** — полиморфный (users.id или staff.id), FK не ставим (по `docs/database.md`).
- **Деньги — `integer` копейки**, никаких `numeric`/`float`: `orders.amount_rub`,
  `orders.original_amount`, `payments.amount_rub` — все `integer`.
- **`short_id` (`ORD-XXXXX`)** — колонка `NOT NULL UNIQUE` без DB-default; генерация в
  repository-функциях следующего milestone (nanoid). В этом milestone в `orders` ничего
  не вставляли, отсутствие генератора не блокирует.
- **Append-only enforcement `order_events`** — пока **конвенцией кода**, не уровнем БД.
  Реальный `DENY UPDATE/DELETE policy + REVOKE BYPASSRLS для service_role` появится в
  milestone «State machine + AI tools», где придёт `transitionOrder()` и понадобится
  доказать инвариант на DB-уровне.
- **Seed через TS-скрипт** (`packages/db/scripts/seed-catalog.ts`) + `pnpm --filter @oplati/db db:seed`.
  Идемпотентный UPSERT по `slug` через `onConflictDoUpdate` — правка цен не требует новой
  миграции, повторный seed безопасен.
- **Zod на границе seed:** `pricingPolicy.parse(entry.pricingPolicy)` перед каждым INSERT —
  гарантия структурной валидности `jsonb`-колонки (инвариант «Zod на границах» из
  `CLAUDE.md`).
- **Airbnb — dummy tier `{priceRub: 1, originalAmount: 1}`.** Zod-схема `pricingPolicy`
  требует `tiers.min(1)` И `priceRub.positive()`; для услуг с per-booking ценой это
  значит дать минимальный валидный tier. Фактическая стоимость хранится в
  `orders.amount_rub` под каждый заказ. Альтернатива (ослабить zod до `min(0)` /
  `nonnegative()`) отвергнута — слишком много мест в коде завязаны на «tier всегда есть
  и priceRub всегда > 0».

## Что сломалось / отклонения от плана

### 1. `db:push` нерабочий — direct hostname не резолвится

План предусматривал применение DDL через `pnpm --filter @oplati/db db:push` (Task 12)
с `DATABASE_URL_DIRECT`. Фактически:

```bash
$ pnpm db:push
[⣷] Pulling schema from database...
 ELIFECYCLE  Command failed with exit code 1.
```

Корень: `db.nyxijwpuvctmvemaemqn.supabase.co:5432` — host из обоих `.env` файлов —
больше не резолвится. Supabase перевёл новые free-tier проекты на pooler-only
(`*.pooler.supabase.com:6543`). У нас `apps/web` уже работает через pooler с
`prepare: false`, но drizzle-kit `db:push` пытается direct connection и падает на
DNS-резолве, ничего полезного в stderr не печатая.

**Решение:** применил `0003_common_richard_fisk.sql` через
`mcp__claude_ai_Supabase__apply_migration` — тот же путь, что план предусматривал
для отдельной RLS-миграции. Это записывает миграцию в
`supabase_migrations.schema_migrations` (audit trail), что важнее, чем источник
запуска (drizzle vs MCP).

**Действие на будущее (не в этом milestone):**

- В `docs/database.md` / runbook стоит явно сказать «direct connection в Supabase больше
  не работает; для DDL — Supabase MCP `apply_migration`, для runtime — pooler с
  `prepare: false`».
- Возможно поменять `drizzle.config.ts` чтобы он использовал pooler с `prepare: false`,
  но drizzle-kit при `push` любит prepared statements — может не пойти. Тогда оставить
  как сейчас: DDL через MCP, audit через `.sql` в git.

### 2. Supabase project в `INACTIVE` — пришлось `restore_project`

Первый MCP-запрос отвалился по таймауту. `mcp__claude_ai_Supabase__get_project` показал
`status: "INACTIVE"` — auto-pause после 7+ дней бездействия (free tier). Базовая схема
(4 таблицы + 4 enum'а + RLS) пережила паузу, **данные пользовательских таблиц тоже
сохранились** (в `users`/`conversations`/`messages` на момент паузы были только
smoke-данные с dev-бота, потерять было нечего).

Выполнен `mcp__claude_ai_Supabase__restore_project` — статус ушёл в `COMING_UP` на
~30-60 секунд, после чего MCP начал отвечать.

**Action item:** в `docs/deployment.md` упомянуть, что Supabase free-tier авто-паузит
проект и при возврате к работе после длительного простоя первый запрос может потребовать
`restore_project`. Это не deal-breaker — просто факт жизни на free tier.

### 3. Кросс-package dependency `@oplati/db` → `@oplati/types`

В `packages/db/package.json` не было `@oplati/types` в `dependencies`. План использовал
`import type { PricingPolicy, OrderParameters } from '@oplati/types'` в `schema.ts` —
без явной workspace-dep это сломало бы `pnpm install` на чистой машине. Добавил
`"@oplati/types": "workspace:*"` в dependencies. Это явно разрешено в CLAUDE.md
(таблица границ пакетов: `@oplati/db` → `@oplati/types` ✓).

### 4. Custom RLS-миграция стала no-op

План (Task 9) предусматривал отдельный `0003_enable_rls_extended.sql` через
`drizzle-kit generate --custom`. Но Drizzle при `.enableRLS()` в schema уже эмитит
`ALTER TABLE "X" ENABLE ROW LEVEL SECURITY;` прямо в auto-migration — увидели это в
строках 18, 31, 57, 70 файла `0003_common_richard_fisk.sql`. Создавать кастомную
дубль-миграцию (как делалось в `0002_lively_supernaut.sql` в base-schema milestone)
смысла нет — мы знаем про этот path из патча `2026-04-28-11.19.md`. Task 9 + Task 13
скипнуты как корректно не нужные.

## Lessons learned

1. **Supabase free-tier auto-pause — реальность.** После 7+ дней бездействия проект
   уходит в `INACTIVE`, и MCP-запросы падают по таймауту с не-говорящей ошибкой
   `Connection terminated due to connection timeout`. Первое действие при таком
   симптоме — `get_project` → проверить `status`, потом `restore_project`. Это не
   потеря данных, это просто прогрев.
2. **`db:push` Drizzle для Supabase не работает.** DNS-резолв `db.<ref>.supabase.co`
   ломается без внятной ошибки — drizzle-kit виснет на «Pulling schema» и падает с
   exit code 1. Переход на Supabase MCP `apply_migration` — единственный надёжный путь
   для DDL. Это меняет workflow: `db:generate` локально → закоммитить `.sql` →
   `apply_migration` через MCP с тем же содержимым.
3. **`.enableRLS()` в Drizzle 0.45 эмитит ALTER TABLE прямо в auto-migration.**
   Кастомная RLS-миграция не нужна. Этот факт уже зафиксирован в патче
   `2026-04-28-11.19.md`, но план был написан до того, как мы это перепроверили на
   новых таблицах. На будущее: после `db:generate` всегда читать `.sql` и не
   планировать кастомную RLS-миграцию, если `.enableRLS()` есть в schema.
4. **Zod `pricingPolicy.tiers.min(1)` + `priceRub.positive()` несовместим с
   per-booking услугами.** Решение через dummy tier — компромисс. Долгосрочно стоит
   либо ввести `pricingKind: 'tier' | 'per_booking'` discriminated union в zod-схему,
   либо отдельную колонку `pricing_mode` в `services` с CHECK что либо `pricing_policy`
   не пустой, либо `pricing_mode = 'custom'`. Это вопрос для следующего ревью схемы
   (не блокер).
