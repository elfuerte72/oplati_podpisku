# Дублирующая миграция drizzle-kit для sync RLS-state

**Date:** 2026-04-28 11:19
**Files:** packages/db/migrations/0002_lively_supernaut.sql
**Severity:** low

## Problem

После добавления `.enableRLS()` в `packages/db/src/schema.ts` команда
`pnpm --filter @oplati/db db:generate` создала миграцию `0002_lively_supernaut.sql`
с теми же четырьмя `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`, что уже были в
`0001_enable_rls.sql`. На code review зафиксирован риск: через несколько
месяцев читатель audit trail увидит «дубликат» и захочет «исправить» — может
случайно откатить или удалить миграцию, нарушив `supabase_migrations`.

Сама команда `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` идемпотентна, поэтому
двойное применение безопасно для БД. Но история миграций без объяснения выглядит
ошибкой.

## Root Cause

Drizzle-kit `db:push` диффит **только то, что описано в `schema.ts`**, и
игнорирует кастомные SQL-миграции (созданные через `generate --custom`). Когда
RLS был включён через `0001_enable_rls.sql` (кастомная миграция), но в
`schema.ts` отсутствовал `.enableRLS()`:

1. snapshot drizzle-kit (`meta/0001_snapshot.json`) не содержал информации про RLS.
2. реальная БД содержала RLS-on на 4 таблицах.
3. `db:push` сравнивал snapshot ↔ БД и видел расхождение в обратную сторону:
   «в коде RLS нет → в БД есть → надо отключить».
4. Drizzle предлагал `ALTER TABLE ... DISABLE ROW LEVEL SECURITY` —
   потенциально снёс бы RLS, если бы кто-то нажал Yes (от non-TTY drizzle-kit
   защищается, но в TTY-окружении автоматизации не было бы).

Корневая причина: смешение «декларативной» (`schema.ts` через `db:generate/push`)
и «императивной» (`generate --custom` + ручное применение) стратегий миграций
без явной синхронизации snapshot.

## Solution

1. Добавил `.enableRLS()` к 4 таблицам в `schema.ts` — теперь schema-as-code
   декларирует RLS, и drizzle-kit видит его в snapshot.
2. `db:generate` создал миграцию `0002_lively_supernaut.sql` с ENABLE-командами,
   повторяющими `0001_enable_rls.sql`.
3. Применил `0002` через Supabase MCP — в БД ничего не изменилось (idempotent),
   но запись в `supabase_migrations.schema_migrations` появилась, и snapshot
   `meta/0002_snapshot.json` зафиксировал RLS-on в состоянии-источнике.
4. Добавил заголовочный комментарий в `0002_*.sql`, объясняющий зачем нужна
   эта «дубликатная» миграция и почему её удалять/переименовывать нельзя.
5. Проверил: `pnpm --filter @oplati/db db:push` теперь говорит
   `[i] No changes detected` — пуш-режим больше не предлагает DISABLE.

## Prevention

- **Конвенция: любая кастомная SQL-миграция, меняющая state, недоступный для
  drizzle-kit (RLS, политики, триггеры, generated-columns, расширения), должна
  сразу же сопровождаться декларативным эквивалентом в `schema.ts`** —
  даже если drizzle-orm пока не умеет генерировать эту часть (тогда добавлять
  `.enableRLS()`, `pgPolicy(...)`, или комментарий-маркер).
- **Pre-merge проверка:** в CI/локально прогонять `db:push` (или `drizzle-kit check`),
  убеждаться, что вывод — `No changes detected`. Если drizzle что-то предлагает
  — это сигнал, что snapshot и реальная БД разошлись.
- **На `db:push` никогда не отвечать `Yes` на destructive prompts автоматически** —
  всегда читать diff. Если drizzle хочет что-то выключить/удалить, это почти
  всегда означает «забыли описать в schema.ts».
- **Header-комментарий в любой sync-миграции** объясняет «зачем здесь повтор» —
  спасает от попытки «починить дублирование» через год.
- **При работе с Supabase RLS в drizzle:** держать схему до конца
  декларативной — `pgPolicy()` через `extraConfig` массив (drizzle-orm v0.45+)
  будет генерировать политики в .sql автоматически, что снимает класс проблемы.
