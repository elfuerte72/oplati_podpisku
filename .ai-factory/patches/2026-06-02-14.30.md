# Бот «потерял память»: пустая БД + молчаливая деградация в амнезию

**Date:** 2026-06-02 14:30
**Files:** packages/db/package.json (+ db:migrate), apps/web/lib/telegram/handle-update.ts (root cause, не менялся)
**Severity:** critical (бот в проде нефункционален — не помнит диалог, не создаёт заказы)

## Problem

Пользователь прислал скрин диалога с `@dev_test_podpiska_bot` (preview, ветка
`mvp`): бот переспрашивает уже сказанное и не доводит до заказа.

```
user: привет, хочу оплатить airbnb
bot:  Какое бронирование оплатить — есть ссылка или сумма?
user: на сумму 26000руб
bot:  Какой сервис нужно оплатить?         ← забыл airbnb
user: airbnb
bot:  Уточни: ссылка/сумма в долларах? даты?
user: сумма 26000руб дата заезда 25 июня до 25 июля
bot:  Это бронирование на месяц — какой сервис? Airbnb, Booking?  ← снова забыл
```

Симптом — «нулевая память»: каждый ответ учитывает только последнее сообщение,
и ни один заказ не создаётся (бот ни разу не вызвал `search_catalog` /
`propose_order`). В логах Vercel при этом — только зелёные `200 OK`.

## Root Cause

**Боевая БД Supabase (`nyxijwpuvctmvemaemqn`) имела пустую `public`-схему — 0 таблиц.**
На этот проект смотрят И preview, И prod (Supabase env общий). Цепочка отказа:

```
нет таблицы users
  → getOrCreateUserByTelegramId() бросает
  → persistInbound() ловит в catch → возвращает null      (handle-update.ts:134-143)
  → ctx === null
  → ветка fallback: runAgentNoTools([{ только текущее сообщение }])  (handle-update.ts:346)
  → агент без истории И без tools → амнезия + ноль заказов
```

Почему `public` оказалась пустой — реконструкция:
1. Изначально (2026-05-17) миграции применялись через **Supabase MCP `apply_migration`**,
   а не через drizzle (db:push падал на DNS pooler-only free-tier — см. patch
   2026-04-28). Трекинг попал в `supabase_migrations.schema_migrations` (7 строк),
   `drizzle.__drizzle_migrations` остался пустым.
2. Между 05-17 и 06-02 данные `public` были потеряны (free-tier
   pause/wipe), при этом `supabase_migrations.schema_migrations` уцелел.
3. **Не было команды `db:migrate`** (только `db:generate`/`db:push`/`db:seed`),
   поэтому после потери таблиц никто их не накатил заново. Бот тихо работал в
   амнезия-режиме.

Усугубляющие факторы:
- **«Graceful degradation» маскирует отказ БД.** `handle-update.ts` глотает ошибки
  БД и всегда отвечает `200 OK` — в логах Vercel всё зелёное, инцидент невидим.
  На деле деградация = молчаливое превращение бота в амнезика без tools.
- **Free-tier автопауза.** На момент диагностики проект был `INACTIVE`.
- **Два конкурирующих трекинга миграций** (`drizzle.__drizzle_migrations` vs
  `supabase_migrations.schema_migrations`) — нет единого источника правды.

## Solution

1. `restore_project` — поднял Supabase из `INACTIVE`.
2. Применил все 7 миграций через `drizzle-kit migrate` (DATABASE_URL_DIRECT,
   pooler :5432) → 10 таблиц + 27 services (seed `0006`).
3. **Проверил конвейер памяти на живой БД** реальными репозиторий-функциями
   (`getOrCreateUserByTelegramId → getOrCreateActiveConversation → appendMessage
   ×3 → loadRecentMessages`): история возвращается в хронологии, агент видит и
   `airbnb`, и `26000`. Тестовые строки удалены.
4. **Добавил `db:migrate`** в `packages/db/package.json`
   (`node --env-file=../../.env node_modules/drizzle-kit/bin.cjs migrate` —
   drizzle-kit сам .env не читает, а `.bin/drizzle-kit` — shell-shim, не
   запускается через node напрямую).
5. **Сверил трекинг:** засеял `drizzle.__drizzle_migrations` 7 строками
   (`hash = sha256(.sql)`, `created_at = journal.when`), чтобы `db:migrate`
   стал идемпотентным no-op и применял только новые миграции (drizzle решает по
   таймстампу `created_at < folderMillis`, не по хешу).
6. **LoveAndPay протестирован** (read-only `GET /api/v2/rates`): связность +
   HMAC-подпись + API-ключ валидны (404 `RATE_NOT_FOUND`, не 401). Фикс. курс
   USDT/RUB на аккаунте не задан → код штатно падает на `RATE_FALLBACK_USDT_RUB`.

## Prevention

- **`db:migrate` теперь часть workflow.** После любого передеплоя/восстановления
  БД — `pnpm --filter @oplati/db db:migrate` накатит недостающее. Forward-only,
  идемпотентно.
- **Health-check должен проверять БД, а не только liveness.** `/api/health`
  обязан делать `select 1` к Postgres и быть красным при недоступности — иначе
  отказ БД невидим за `200 OK`.
- **Убрать «амнезию» из graceful degradation.** При недоступной БД бот не должен
  молча терять контекст и tools. Минимум — честная ошибка пользователю + алерт
  (Sentry/телеграм), а не fallback в `runAgentNoTools`. [follow-up]
- **Keep-alive против free-tier автопаузы** — лёгкий cron раз в сутки + алерт при
  недоступности. [follow-up, согласовано с владельцем]
- **Один источник правды для миграций.** Выбрать drizzle (`db:migrate`) ИЛИ
  Supabase MCP `apply_migration`, не оба. Сейчас стандартизируемся на
  `db:migrate`; `supabase_migrations.schema_migrations` оставлен как исторический
  audit trail.
