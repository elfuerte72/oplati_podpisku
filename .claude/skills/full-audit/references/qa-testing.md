# Ось L — QA: полнота тестового ландшафта и процесс

Фокус оси — ДЫРЫ в покрытии и процессе QA, не качество написанных тестов
(качество — ось E, E5/E6; не дублируй её). Ниже — снимок ландшафта на
2026-08-10: сначала ПЕРЕПРОВЕРЬ каждый факт по коду (что-то могло измениться),
затем оценивай дыры по денежной критичности.

## Снимок ландшафта (перепроверить, не принимать на веру)

- Vitest в 3 workspace: `apps/web` (~460), `packages/types` (~110),
  `packages/db` (интеграционные на PGlite — реальный Postgres + реальные
  миграции, ~25 describe-блоков по денежным инвариантам).
- **`packages/agent` — ноль тестов и нет `test`-скрипта** → CI
  (`pnpm -r --if-present test` в `tests.yml`) пропускает его МОЛЧА.
- Роут-тесты есть у 8 из 29 роутов. Без них: `/api/bot`,
  `/api/payments/loveandpay`, `/api/orders/confirm`, `/api/orders/status`,
  `/api/cabinet`, `/api/cabinet/referral`, `/api/auth/telegram/link` (+status),
  все 8 `/api/cron/*`, `/api/admin/telegram-webhook`, `/api/chat/history`,
  `/api/chat/clear`, `/api/profile`, `/api/catalog`.
- Крупные модули без прямых тестов: `lib/telegram/catalog-callbacks.ts` (436
  строк), `handle-update.ts` (416; покрыт только analytics-аспект),
  `lib/cabinet/actions.ts` (387), `lib/telegram/vpn-flow.ts` (380),
  `lib/cabinet/read.ts` (279), **`lib/tool-handlers/confirm-order.ts` (244 —
  денежный путь)**, `agent-dialog.ts`, `link-flow.ts`, `persist.ts`,
  `send.ts`, `billing-address.ts`.
- **E2E нет вообще** (Playwright-сьюта в репо нет), UI/component-тестов нет
  (`@testing-library` не установлен; тесты компонентов — только чистая
  `.ts`-логика). Смоук после деплоя — `/api/health` `startedAt` + `/api/ready`
  (миграции); остальной смоук — ручной по рунбуку.
- **Coverage-метрики нет** (в vitest-конфигах нет coverage; c8/istanbul не
  подключены) — «460 тестов» ничего не говорит о покрытии строк/веток.
- Property-based тестов нет (fast-check отсутствует).

## L1 · Ранжирование дыр по денежной критичности

Для каждого непокрытого пути ответь: «какой регресс здесь дойдёт до прода
незамеченным и что он сделает с деньгами/данными?» Приоритет:

1. `confirm-order.ts` — фиксация цены, гейт привязки, выставление счёта.
2. `/api/bot` route — проверка secret-token (единственный non-200), разбор
   апдейтов: регресс = бот принимает поддельные апдейты или падает на живых.
3. `/api/payments/loveandpay` route — подпись + маршрутизация событий (handlers
   покрыты юнитами, сам route — нет).
4. `/api/cron/*` — Bearer-авторизация каждого роута (fail-closed) нигде не
   тестируется на уровне роута.
5. `/api/cabinet` — auth `initData` + ownership на каждом action.
6. `/api/orders/confirm` и `/api/auth/telegram/link` — гонки/одноразовость.

## L2 · Обязательные регресс-тесты денежных инвариантов

Сверь: на каждый инвариант осей A/B/K существует хотя бы один тест (юнит или
PGlite). Чего по снимку НЕ видно в `integration.test.ts` — проверь и, если
правда нет, находка: частичный `UNIQUE(order_id) WHERE status='pending'`
(двойной живой инвойс), гонка конкурентного потребления одного `link_token`,
`amount_mismatch`-путь на уровне БД, поведение `wouldCreateCycle` на глубине
кап-16, RLS-политики (PGlite их не прогоняет — чем компенсировано?).

## L3 · Негативные кейсы внешних границ

Для КАЖДОГО вебхука/подписанного входа должен существовать тест на:
невалидную подпись, отсутствующие заголовки, битое тело (не-JSON), replay
(повтор того же события), неожиданное событие/статус. Проверить по факту для:
L&P webhook, Freekassa webhook, `/api/bot` secret-token, `initData` подпись,
`X-Internal-Token`, `CRON_SECRET`. Отсутствие негативного кейса на подпись —
HIGH.

## L4 · CI-гейты и молчаливые пропуски

- `tests.yml`: `pnpm -r --if-present test` — workspace без `test`-скрипта
  зелёный молча (сейчас так с `packages/agent`). Находка + проверить, нет ли
  ещё таких.
- Required-чеки ruleset'а (`Tests`/`Type Check`/`Lint`/`Build`/`Secret Scan`/
  `Dependency Review`) соответствуют фактическим именам jobs (переименованный
  job = мёртвый гейт: PR мержится без него).
- `pnpm typecheck` проверяет и тесты (L-14) — убедиться, что это всё ещё так
  (tsconfig не исключает `*.test.ts`).
- Деплой-гейт: `deploy.yml` гоняет тот же набор перед вебхуком; `paths-ignore`
  не пропускает кодовые файлы под видом доков.

## L5 · Инфраструктура тестов

- Coverage: предложить включить `vitest --coverage` (provider v8)
  информационно (не гейтом сразу — см. правило «новый чек обязателен только
  после зелёных прогонов»). В отчёте — top-5 непокрытых денежных файлов.
- Моки внешних API: проверить, что юнит-тесты клиентов (pay-space, loveandpay,
  freekassa, rapira, remnawave) мокают fetch, а не ходят в сеть; тест, который
  при отвале мока молча ходит в интернет, — находка.
- PGlite: миграции в тестах = реальные файлы `migrations/` (не схема напрямую),
  иначе тест не ловит расхождение схема↔миграции.
- Флаки: таймауты/`Date.now()` в тестах без фейковых таймеров; тесты, зависящие
  от порядка выполнения.

## L6 · Чего нет как класса (оценить риск, предложить минимум)

- **E2E**: нет ни одного автоматического прогона «заказ → счёт → вебхук →
  карта» даже на моках уровня HTTP. Оценить: какой минимальный e2e (1–3
  сценария против dev-стенда или локального next + мок-провайдеров) закрыл бы
  самые дорогие регрессы. Не предлагать тяжёлую матрицу браузеров — прод-риск
  в бэкенд-флоу, не в вёрстке.
- **Property-based**: кандидаты — парсеры денег (`AMOUNT` в копейки, «1,000»
  vs «1,00»), подписи (сортировка значений), `paySpaceMoney` (строка|число).
- **Смоук прод-деплоя**: сейчас health+ready; чего не хватает (например,
  синтетический `GET /api/orders/status` без сессии = 200-контракт), что можно
  добавить в `deploy.yml` без секретов и без записи в БД.

## L7 · Формат находок оси

Каждая дыра — с конкретикой: «инвариант X (файл Y) не покрыт ни одним тестом;
регресс Z пройдёт CI и приведёт к W». Пустое «мало тестов» не принимается.
В `fix_sketch` — какой именно тест написать (уровень: юнит / route / PGlite /
e2e) и что он ассертит.
