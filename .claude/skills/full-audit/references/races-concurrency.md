# Ось K — Сквозные гонки и конкурентность

Метод: для каждой пары конкурентов ниже НАЙТИ в коде защитный механизм
(назвать file:line) или объявить дыру. «Кажется маловероятным» — не защита:
вебхук + поллинг + cron + повторный клик пользователя гарантированно
пересекаются на ~50 заказах/день.

## K1 · Оплата одного заказа: вебхук L&P ↔ вебхук Freekassa ↔ poll-payment ↔ expire-payments

- Успех: `claimPaymentSucceeded` — атомарный `pending→succeeded` условным
  UPDATE; побочные эффекты (переход заказа, Telegram-DM, реф-начисление,
  issue-card) — ТОЛЬКО у победителя. Claim + `transitionOrder(paid)` — в одной
  транзакции (`processInvoicePaid`), сбой перехода откатывает claim.
- Неуспех: `claimPaymentTerminal` — симметричный атомарный `pending→failed`;
  НЕ безусловный UPDATE (не перезаписывает `succeeded` при гонке с paid-путём).
- `amount_mismatch`: терминальный путь в одной транзакции + РОВНО один DM
  (дедуп атомарным claim'ом); повторы вебхука/поллинга молчат.
- Expire против оплаты: state machine запрещает `paid → expired`; expire не
  трогает заказ с живым инвойсом.

## K2 · Повторный confirm заказа (живая веб-вкладка после привязки ↔ handoff в боте)

- Заказ в `pending_payment` → `payments/create` идемпотентно возвращает
  существующий pending-инвойс (`repeat_confirm`), не второй счёт.
- Частичный `UNIQUE(order_id) WHERE status='pending'` — не более одного живого
  инвойса; гонка 23505 ловится снаружи, транзакция откатывается целиком.

## K3 · issue-card ↔ recovery в poll-payment

- Атомарный claim `paid → in_fulfillment` ДО любых операций с провайдером
  (`transitionOrderDetailed`, at-most-once). Проигравший не выпускает вторую
  карту и не делает второй topup.
- `createCard` без ретраев; async-topup поллит `topup/check` — что при
  падении процесса между topup и записью результата?

## K4 · Просмотр кабинета ↔ параллельный topup

- `syncCardBalance` — compare-and-set по прочитанному балансу: проигрыш гонки
  параллельному topup → кэш не трогается. `last_used_at` осознанно не
  обновляется (иначе просмотр кабинета мешает recycle-cron).

## K5 · Конкурентные запросы к Freekassa

- Nonce — последовательность Postgres `freekassa_nonce`: два `confirm_order`
  в одну миллисекунду получают разные nonce. Любой путь с `Date.now()`-nonce —
  BLOCKER.

## K6 · Привязка Telegram (`consumeLinkToken`)

- Merge двух строк `users` — одна транзакция; конкурентное потребление одного
  токена (двойной клик / два устройства) — токен одноразовый атомарно.
- Параллельные записи в обе строки во время merge (сообщение в веб-чате во
  время привязки) — куда попадут children?
- Handoff заказа после привязки ↔ живая веб-вкладка, повторившая confirm —
  оба получают ОДНУ платёжную ссылку (`repeat_confirm`).

## K7 · Кап заказов на пользователя

- ≤10 заказов/сутки: как считается — атомарно или read-then-insert? Два
  конкурентных `propose_order` на 10-м заказе → 11 заказов?
  (Оценить severity честно: кап — защита расходов, не деньги клиента.)

## K8 · Cron ↔ cron

- Каждый джоб против самого себя (двойной запуск) — см. ось G; здесь сверить
  ПЕРЕСЕЧЕНИЯ разных джобов: `poll-payment` (recovery paid) ↔
  `expire-payments` (хоронит протухшие) на одном заказе; `recycle-cards` ↔
  `issue-card` (topup карты, которую recycle закрывает этой ночью).

## K9 · Работа после ответа HTTP

- Любая доводка после ответа — только `after()` или cron. `setImmediate`/
  `process.nextTick`/floating promise после ответа — терялись на Vercel и
  остаются антипаттерном (процесс может быть перезапущен деплоем).
- Floating promises на денежных путях (без `await`/`.catch`) — HIGH+.

## K10 · Транзакционные границы

- Для каждой многошаговой денежной операции: все шаги, обязанные быть
  атомарными, — в одной `db.transaction`; побочные эффекты вне БД (Telegram,
  провайдеры) — ПОСЛЕ коммита, не внутри транзакции (иначе откат оставит
  отправленный DM / выпущенную карту без записи).
