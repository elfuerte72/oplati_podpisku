# Ось I — Реферальная программа и выплаты

Одноуровневая (с 2026-07-02): партнёр получает процент ТОЛЬКО с оплат своих
прямых рефералов. Деньги начислений — append-only ledger. Выплаты — каркас E1,
реального движения денег НЕТ. Исторические спека/план в `docs/history/`
описывают ТРЁХуровневую схему — код им противоречить обязан.

## I1 · Ledger начислений (`referral_accruals`)

- Append-only; идемпотентность — `UNIQUE(payment_id, beneficiary, level)`.
- Начисление — `accrueReferralForPayment` в `processInvoicePaid` СРАЗУ после
  `claimPaymentSucceeded` (в том же потоке обработки оплаты): проигравший
  гонку claim не начисляет.
- Инвариант: **сумма начислений заказа ≤ его комиссия**. Проверить расчёт
  ставок (`REFERRAL_RATE_TABLE` в `@oplati/types`: 4%/4%/6%/7% по статусам).
- Новых строк уровней 2–3 не появляется (`REFERRAL_MAX_LEVEL=1`); исторические
  строки валидны — код не должен их «чинить».

## I2 · Захват реферера

- `users.referred_by` — immutable; `setReferrerOnce` отклоняет установки,
  создающие цикл (`wouldCreateCycle`: обход вверх, кап 16, fail-closed) —
  иначе пара A↔B вечно фармит комиссию.
- Две точки захвата: (1) бот `/start ref_<code>` при СОЗДАНИИ строки — без
  анти-абьюз-гейта; (2) Mini App `initData.start_param` + поздний захват — оба
  с гейтом `hasPurchasedOrders` (покупателя не переприсваиваем).
- ⚠️ Инвариант инцидента: `referred_by_set_at` в raw-`INSERT` = SQL `now()`,
  НЕ JS `new Date()` — Date-объект в bind-параметре ронял слой кэша запросов,
  захват молча падал только при заданном реферере. Проверить все raw-INSERT'ы
  на Date-объекты в bind-параметрах.
- `start_param` берётся только из ПОДПИСАННОГО `initData` (проверка подписи до
  использования).

## I3 · Месячная прогрессия (`referral-rollup`)

- Идемпотентность: `PK(user_id, month)` в `referral_monthly_stats`.
- Храповик статусов (статус не понижается), бонусы
  достижения/спринт/серия — по `planMonthlyProgression` в `@oplati/types`
  (там же тесты).
- UI-термин «статус», в коде/БД — `circle`/`current_circle`: переименования в
  одном слое без другого — находка (сломает JOIN'ы/контракты).

## I4 · Выплаты (Этап E1 — каркас, денег нет)

- `settlePayout` **нигде не вызывается** (семафор до D-REF-6). Если появился
  вызов — BLOCKER (реальный executor не выбран, исполнитель — mock).
- Машина статусов заявки — только через `transitionReferralPayout`.
- Реквизиты: полный PAN не хранится и не логируется (схемы input→stored),
  маскирование + отсев Луна; **CVV не собирается нигде** (PCI-запрет).
- Комиссия вывода `computePayoutFee` (3.5% карта / 1% крипта) — удержание из
  брутто; integer-арифметика.

## I5 · Merge пользователей (`consumeLinkToken`)

- Merge telegram-строки и веб-строки — в ОДНОЙ транзакции; выживает
  telegram-строка, children (заказы, сообщения, рефералы) переезжают.
- Цикл-чек при merge (тот же `wouldCreateCycle`-класс проверки).
- `link_tokens` одноразовые, TTL 10 мин; потребление токена атомарно
  (повторное потребление того же токена не должно пройти).

## I6 · Партнёрский API (`/api/cabinet/referral`)

- Веб-ветка — под rate-limit по IP ДО резолва сессии (инвариант 9).
- Ответы — через Zod-схемы (`referral-api-schemas`); снапшот не отдаёт чужих
  данных (ownership по сессии/initData).
