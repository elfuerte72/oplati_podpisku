# Full Review — полное код-ревью oplati_podpicky

Ты — оркестратор ревью. Твоя задача — **не ревьюить самому**, а разложить diff по
осям, запустить параллельные саб-агенты (каждый со своим чеклистом инвариантов) и
собрать их находки в единый отчёт **без смешивания осей**.

Корневая добродетель — **предсказуемость процесса**: один и тот же маршрут каждый
прогон. Оси независимы, чтобы одна (напр. стиль) не заслоняла другую (напр. дыру в
идемпотентности платежа).

## Шаг 1 — Установить fixed point и охват

Разбери аргумент скила (`$ARGUMENTS`), выбери РОВНО один режим:

1. **Аргумент пустой** (дефолт) → ревью ветки:
   - `git merge-base main HEAD` — база;
   - `git diff main...HEAD` — закоммиченные изменения ветки;
   - `git diff HEAD` + `git status --porcelain` — незакоммиченные (тоже ревьюим);
   - `git log main..HEAD --oneline` — контекст коммитов.
2. **SHA / ветка / тег** → `git diff <arg>...HEAD` + `git log <arg>..HEAD --oneline`.
3. **Пути** (существующие файлы/директории) → `git diff main...HEAD -- <paths>`; если diff пуст — ревьюим файлы целиком.
4. **PR** (`#123`, `123`, `PR 123`, ссылка на github PR) → `gh pr diff <n> --patch` + `gh pr view <n>` (спецификация из тела PR / связанного issue).

Убедись, что diff **непустой**. Если пуст — сообщи и остановись (нечего ревьюить).

## Шаг 2 — Собрать преамбулу и загейтить оси

Получи список изменённых файлов (`git diff --name-only <base>...HEAD` + незакоммиченные).
Определи, какие оси релевантны, по таблице гейтов:

- **A** запускать, если тронуты: `packages/db/**`, `packages/types/src/order-state-machine.ts`, `**/migrations/**`, любые `*repositor*`, код с денежными полями (`amount_rub`, `*_cents`, `*_kopecks`).
- **B** запускать, если тронуты: `**/payments/**`, `**/loveandpay/**`, `**/pay-space/**`, `**/webhook*`, `**/api/bot/**`, `**/jobs/**`, `**/referral/**`, `**/cron/**`.
- **C** запускать **всегда** (безопасность/PII проверяется на любом diff).
- **D** запускать **всегда** (границы/конвенции проверяются на любом diff).
- **E** запускать **всегда** (корректность/тесты).

Если ось не загейчена — **пропусти её** и явно отметь `— пропущено (файлы не затронуты)`
в финальном отчёте (не молчаливое усечение).

## Шаг 3 — Запустить саб-агенты параллельно

Запусти релевантные оси **одним сообщением, несколькими вызовами `Agent`**
(параллельно, чтобы не загрязнять контексты друг друга). Каждому агенту передай
дословно:

```
Ты ревьюишь ОДНУ ось изменений в репозитории oplati_podpicky.
Ось: <буква + название>.
Прочитай чеклист .claude/skills/full-review/references/<файл-оси>.md — это
ЖЁСТКИЕ инварианты проекта, а не эвристики. Прочитай CLAUDE.md для контекста.

Diff под ревью:
  <точные git/gh-команды из Шага 1>
Изменённые файлы: <список>

Для каждого пункта чеклиста проверь diff. Открывай затронутые файлы целиком,
если нужно понять контекст (импорты, транзакции, вызывающий код) — не суди по
одному хунку. Ищи и то, что ДОБАВЛЕНО с нарушением, и то, что нарушение УБИРАЕТ
существующую защиту (напр. снят ON CONFLICT, ослаблена RLS, убран timeout).

Верни находки списком, отсортированным по severity, в формате:
  [SEVERITY] file:line — <инвариант> — <в чём нарушение, 1–2 строки> — <как
  проявится: конкретный вход/состояние → неверный результат>
Severity: BLOCKER (нарушен инвариант / дыра безопасности / потеря или двойное
списание денег / поломка идемпотентности) | HIGH | MEDIUM | LOW.
Если по этой оси нарушений нет — верни ровно «нарушений не найдено».
Будь конкретным и коротким (<400 слов). Не выходи за свою ось — чужие оси
покрывают другие агенты.
```

Ось C — через `agent-skills:security-auditor`, ось E — через
`agent-skills:code-reviewer`, оси A/B/D — через `general-purpose`.

## Шаг 4 — Собрать отчёт

Выведи находки под **раздельными заголовками осей**, НЕ сливая и НЕ переранжируя
между осями (BLOCKER оси B не «важнее» BLOCKER оси C — это разные измерения):

```
## A. БД и состояния
[BLOCKER] ...
[HIGH] ...

## B. Платежи и идемпотентность
...

## C. Безопасность и PII
...

## D. Границы и архитектура
...

## E. Корректность и тесты
...

## Сводка
A: 1 BLOCKER, 0 HIGH · B: пропущено · C: 2 HIGH · D: 0 · E: 1 MEDIUM
Худшее по каждой оси: A — прямой UPDATE orders SET status (orders.ts:88).
```

Правила отчёта:
- Ничего не выдумывай: каждая находка — конкретный `file:line`. Если агент вернул
  расплывчатое — отбрось или пометь как «требует проверки», не поднимай severity.
- **Не переранжируй между осями** и не выбирай «главную проблему» глобально — это
  сознательно, чтобы платёжный баг не спрятал дыру безопасности.
- Не предлагай правки в этом прогоне — сначала отчёт. Правки — отдельным шагом по
  запросу пользователя.
- Оси-BLOCKER'ы — это стоп-краны для merge; проговори это в сводке.

## Границы скила

- Скил **читает и анализирует**, ничего не меняет и не коммитит.
- Не запускает тесты/линт сам (это стоп-краны CI); при желании пользователь
  запускает `pnpm typecheck` / `pnpm --filter web test` отдельно.
- Не заменяет внешние ревью (Greptile / CodeRabbit / `/code-review ultra`) — а
  дополняет их проектными инвариантами, которых у них нет.
