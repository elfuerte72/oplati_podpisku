## О проекте

Telegram-бот + веб-чат для оплаты иностранных подписок русскоязычным пользователям. Клиент пишет, что хочет оплатить, — AI-агент «Оплатишка» находит цену, создаёт заказ, принимает оплату в RUB; исполнение пока ручное (операторы). Масштаб старта — ~50 заказов/день.

**Стек:** TypeScript 5.6 · Node.js 24 · pnpm + Turborepo · Next.js 16 (App Router) · grammY · `@anthropic-ai/sdk` (свой tool-loop, default-модель `claude-sonnet-4-6`, override через `ANTHROPIC_MODEL`) · self-hosted Postgres 17 (переезд с Supabase 2026-07-24; Storage/Auth/Realtime не используются) · Drizzle · Zod · Tailwind v4 · Sentry + pino · Vitest · **Dokploy на VPS** `187.124.172.104` (Docker + Traefik) + системный crontab.

**Осознанно НЕ используем** (не предлагать без явного запроса): Vercel AI SDK и токен-стриминг (чат целевой, короткие ответы; свой tool-loop работает в проде), Trigger.dev (хватает системного crontab; env зарезервирован), shadcn/ui (свой комикс-UI).

## Что работает сейчас

- **Telegram-бот → `/api/bot`** — grammY webhook (проверка `X-Telegram-Bot-Api-Secret-Token`, единственный non-200 кейс → `401`). **Дедуп по `update_id`** (`lib/dedup.ts`, аудит 2026-08-10): Telegram переДОСТАВЛЯЕТ апдейт, если не получил 200 вовремя, а обработчик синхронный и живёт до 90 с — повтор проходил весь путь заново (второе сообщение, второй счёт по `confirm`, второй вызов панели VPN). Ключ в Redis несёт id бота (иначе прод и dev гасят апдейты друг друга) и живёт В ДВЕ ФАЗЫ: 100 с на время работы, 10 мин после неё — умерший процесс ключ не освобождает, и длинный TTL с самого начала превращал бы ретрай Telegram в тихую потерю. Fail-open и быстро (ретраи клиента выключены, предел ожидания 1,5 с): claim идёт ПЕРЕД обработчиком, и зависший Redis иначе остановил бы весь бот. ⚠️ **`ANTHROPIC_API_KEY` в жёсткий гейт роута НЕ входит** — его пропажа глушила `/start`, меню, оплату и VPN, к Anthropic отношения не имеющие; гейт живёт на AI-пути (`runAgentDialog`), где отвечает текстом со ссылкой на `/support` и шлёт Sentry-алёрт. **Взаимодействие с Оплатишкой в ЧАТЕ бота — за флагом `BOT_AI_ENABLED` (дефолт ВЫКЛЮЧЕНО, 2026-07-03):** при выключенном флаге бот не обслуживает текст/медиа/каталожные inline-кнопки/`/menu` — работают только команды `/start`, `/support` и inline-меню, а покупки идут в Mini App. **Молчания больше нет** (тикет 09 админ-панели, 2026-08-17): на свободный текст и на медиа уходит одна фраза с кнопкой «Поддержка» — раньше написавший «помогите» не получал НИЧЕГО и уходил. Обращение по-прежнему создаётся ТОЛЬКО нажатием кнопки (правило владельца), подсказка его не создаёт. Дедуп в ДВА эшелона (`lib/telegram/silent-hint.ts`): Redis на разные процессы и память процесса на альбом — Telegram шлёт апдейт на каждое фото, а `claimOnce` fail-open, и без локального эшелона десять фото давали бы десять подсказок там, где Redis не настроен; при `BOT_AI_ENABLED=1` — обычный путь `runAgent()` из `@oplati/agent` → Anthropic → tools → Supabase (AI-диалог + кнопочный `/menu`-каталог). Код обоих путей сохранён — флаг это временный выключатель, не удаление. Диалог синхронно пишется в БД с graceful degradation при её недоступности (бот отвечает, но «забывает» историю).
- **Веб-чат → `/api/chat`** — тот же `runAgent()` (инвариант: оба канала используют одного агента), ответ JSON-ом без стриминга. **AI-диалог на сайте — за флагом `WEB_AI_ENABLED` (дефолт ВЫКЛЮЧЕНО, решение владельца 2026-07-19):** при выключенном флаге любое сообщение в поле ввода получает мгновенную заготовку «выбери сервис в каталоге / поддержка в боте» — без вызова Anthropic, без сессии и записей в БД (rate-limit тоже не зовётся — ответ статический); UI сайта не меняется, покупка кнопочная (`/api/orders/propose`+`confirm`) не затронута. Код агента цел — временный выключатель по образцу `BOT_AI_ENABLED`. История — `/api/chat/history`, сброс — `/api/chat/clear`, сессия по cookie (`lib/chat/session.ts`). Конвертация истории в Anthropic-формат — ОБЩИЙ `toAgentHistory` (`lib/chat/history.ts`, дубль из handle-update.ts удалён 2026-07-18): отрезает ведущие `assistant` — окно `loadRecentMessages(…, 20)` режет по числу строк и при непарной записи начиналось с assistant → Messages API отвечал 400 на каждый ход НАВСЕГДА (чётность окна сохраняется; H-1 аудита). Комикс-UI «Оплатишка» (`components/chat/`, `components/comic/`, skill `oplatishka-design`). Интро при первом визите — `components/intro/IntroOverlay.tsx` (2 кадра, localStorage-флаг).
- **Привязка Telegram к веб-сессии** — `POST /api/auth/telegram/link` выпускает одноразовый токен (TTL 10 мин, таблица `link_tokens`) → deep-link `telegram.me/<bot>?start=link_<token>` → бот в `/start link_*` зовёт `consumeLinkToken` (если у клиента есть и telegram-, и веб-строка в `users` — merge в одной транзакции, выживает telegram-строка, children переезжают) → клиент поллит `GET /api/auth/telegram/link/status`. Точки входа UI: интро, панель профиля, карточка-гейт в чате (`components/chat/TelegramLink.tsx`). **После привязки** панель профиля (`ProfilePanel.tsx`) вместо кнопки Telegram показывает **«Личный кабинет»** — ссылку на Mini App (`cabinetUrl` из `/api/profile` ← `cabinetDeepLink()`: задан `TELEGRAM_MINIAPP_SHORTNAME` → прямой `telegram.me/<bot>/<shortname>`, иначе fallback `telegram.me/<bot>?start=cabinet` через /start-меню с web_app-кнопкой; веб-браузер сам открыть web_app-кнопку не может). Аватар в профиле осознанно НЕ показываем (у веб-сессии нет `initData`; тянуть фото через Bot API `getUserProfilePhotos` + прокси ради кружка не стали) — только имя из Telegram. **Механика перехода (фикс мобильной привязки 2026-07-03):** токен выпускается ЗАРАНЕЕ при рендере кнопки (prefetch с гейтом видимости; перевыпуск по TTL; rate-limit `web-link` поднят 5→10/мин), кнопка — настоящая `<a href="telegram.me/...">`: universal link открывает приложение Telegram только при прямом тапе; прежняя схема `window.open('about:blank')` + `location.replace` после `await` на iOS/in-app-браузерах не доводила пользователя до бота (токены выпускались, но не потреблялись — видно в `link_tokens.used_at IS NULL`). При `waiting` показывается fallback «скопировать ссылку». **Handoff заказа в бота:** после успешного `consumeLinkToken` бот ищет свежий (≤24 ч) заказ `ready_for_payment` и, если нашёл, сразу выставляет счёт (`confirmOrder`) и шлёт ссылку оплаты в чат — возвращаться в мобильный браузер не нужно; сбой handoff не роняет привязку (обычный успех-текст). `payments/create` при повторном confirm заказа в `pending_payment` идемпотентно возвращает существующий pending-инвойс (`repeat_confirm`), поэтому живая веб-вкладка, повторившая подтверждение после привязки, получает ту же ссылку. **Гейт оплаты:** веб-пользователь без `telegram_id` не получает платёжную ссылку — `confirm_order` бросает `TelegramLinkRequiredError` (`telegram_link_required`), т.к. чек и реквизиты карт доставляются только в Telegram. **Мобильный сайт — воронка в Telegram:** баннер «Продолжить в Telegram» (`components/chat/MobileTelegramBanner.tsx`, только <lg, прямая `<a>` на `supportUrl` из `/api/profile`); анти-петля — кнопка «Сайт» в /start-меню бота ведёт на `/?src=tg`, такой визит помечается в sessionStorage и баннер не показывается.
- **Tools агента** (`packages/agent/src/tools.ts`): `web_search` (серверный tool Anthropic — актуальные цены, в каталоге цен НЕТ), `search_catalog`, `propose_order`, `confirm_order`, `request_human`. Заказ принимается на **любой** сервис: из каталога (`serviceId`) или вне его (`customDescription` — свободный текст, оператор перепроверит). Каталог `services` публичен только на чтение активных записей (`RLS + SELECT policy`), запись — только server-side/service role. **Кнопочный веб-выбор (`StartScreen`)** сейчас без пункта «Свой вариант…» — флаг `ALLOW_OWN_VARIANT=false` (2026-07-02): временно ограничиваем список доступными к оплате сервисами (часть карт/подписок не принимаем); код сохранён, AI-путь `customDescription` не затронут. Цена = `курс × USD-цена + COMMISSION_PERCENT` (на проде 30%, дефолт 10%) + разовая **надбавка за выпуск карты** `CARD_ISSUE_FEE_USD_CENTS` (на проде $4=400, дефолт 0) — берётся только когда у клиента нет активной карты (`findActiveByUserId`; при повторной оплате топап без fee); снимок в `orders.card_issue_fee_kopecks` (миграция 0019), экран заказа показывает разбивку «Подписка / Выпуск карты / Итого». **Копеек в цене нет: подписка и надбавка округляются ВВЕРХ до целого рубля** (`roundUpToWholeRubles` в `apps/web/lib/pricing.ts`, решение владельца 2026-08-05). Округляются именно эти две строки, а не итог: витрина каталога показывает `subtotal + commission` (без fee) — округли только итог, и «≈ 868 ₽» в списке тарифов разошлось бы с суммой заказа, а разбивка чека перестала бы сходиться. Разница уходит в комиссию (`amountRubKopecks` в результате tool'а остаётся сырым subtotal). Обе точки расчёта — `lib/catalog/build.ts` (оценка) и `lib/tool-handlers/propose-order.ts` (фиксация) — обязаны звать одну функцию. Курс USD→RUB (внутренне `usdt_rub`) берётся из публичного Rapira `GET /open/market/rates`, пара `USDT/RUB`, поле `askPrice` (цена покупки USDT за RUB); при ошибке сети/HTTP/контракта — `RATE_FALLBACK_USDT_RUB` (дефолт 81; поднят с 77 2026-07-19, M-14). Курс фиксируется при `propose_order` **на 2 часа** (`TTL_HOURS`; было 24ч — решение владельца 2026-07-18: суточная фиксация = односторонний опцион на курс за счёт маржи). Фиксация форсится сервером (H-2 аудита): переход `ready_for_payment → expired` разрешён в state machine, протухший черновик хоронит cron `expire-payments` ИЛИ гейт `isPriceLockExpired` в `payments/create` (`409 order_expired` → UI говорит «оформи заново»). **Принимаем ТОЛЬКО рубли** (СБП/карта) — USDT/крипту от клиента НЕ принимаем (убрано из GREETING/SYSTEM_PROMPT 2026-07-03).
- **Приём рублей — два шлюза, Freekassa основной с 2026-07-28** (`PAYMENT_PRIMARY_PROVIDER=freekassa`, касса `74953`; Love&Pay — резерв). **Инварианты, которые нельзя нарушать:** флаг выбирает шлюз ТОЛЬКО для нового счёта (`lib/payments/gateway.ts`), **вебхуки ОБОИХ провайдеров работают всегда** — иначе в момент переключения оплаты по уже выставленным счетам прежнего шлюза не были бы приняты; ответ вебхука — HTTP 200 всегда (инвариант 6), у Freekassa принятым уведомление считается по ТЕЛУ `YES`; идемпотентность — атомарный `claimPaymentSucceeded` (`pending→succeeded` одним условным UPDATE), побочные эффекты только у победителя гонки webhook↔poll; **недоплата терминальна** (`amount_mismatch` → платёж и заказ в `failed` + РОВНО один DM владельцу через `claimPaymentTerminal`); счёт живёт 1 час (`INVOICE_TTL_HOURS`), `orders.expires_at` выравнивается по сроку инвойса в ТОЙ ЖЕ транзакции. Потолок держится в два эшелона: витринный кап **$1200** и рублёвый гейт `FREEKASSA_MAX_AMOUNT_RUB` (дефолт 140 000). Тех. сбой транспорта → `503 provider_unavailable` и текст «заказ сохранён, попробуй позже» во всех каналах. Всё остальное — базовые URL, формулы подписей, контракт вебхуков, конверсионная метрика, автофоллбэк, комиссия покупателя — в [`docs/reference/payment-gateways.md`](docs/reference/payment-gateways.md); контракт Freekassa, снятый живым платежом, — в [`docs/reference/freekassa-api.md`](docs/reference/freekassa-api.md).
- **Антифрод-трек Freekassa (2026-08-15, тикеты 01-11, спека в `.scratch/freekassa-antifraud/`).** Причина холдов была в нас: провайдер получал IP нашего VPS и несуществующий email `<telegram_id>@telegram.org` — портрет дроп-схемы. Теперь: **(1) правда о плательщике** — счёт уходит с `users.last_seen_ip` (пишется с троттлингом из живых запросов клиента: кабинет/propose/confirm/чат, `rememberClientIp`; fallback на IP VPS алертится) и настоящим `users.email` (обязателен: «плашка контактов» на экране заказа сайта и Mini App — общий `components/contacts/ContactCard.tsx`; гейт `422 email_required` в `payments/create`; суррогат — алертящаяся аномалия); merge при привязке Telegram переносит контакты веб-строки. **(2) Телефон от порога** `PHONE_REQUIRED_FROM_RUB` (env, не задан → выключено; прод 10000): гейт `422 phone_required` с порогом в теле (в UI не зашит — `isPhoneRequiredForAmount` единственное место конверсии; порог отдают `/api/profile` и cabinet-snapshot), сбор — плашка/`request_contact` в боте (чужой контакт отвергается по `contact.user_id`; Mini App «Взять из Telegram»: `requestContact` номер приложению НЕ отдаёт — приходит боту contact-сообщением) + экран «Профиль» (action `update-contacts`; ручная правка → `phone_source='manual'`); `tel` провайдеру — за флагом `FREEKASSA_SEND_TEL` (дефолт ВЫКЛ до живого подтверждения контракта); сверка `phone_match` в meta `payment_succeeded` — только пометка (Р4). Контакты и IP — режим PAN: redact в pino/Sentry (канарейка `lib/contacts/redact-canary.test.ts`). **(3) Видимость холда**: статус `7` = `ANTIFRAUD_HOLD` (эмпирический, подтверждён поддержкой 2026-08-14), каждый опрос пишет `payments.last_provider_status`; холд → заказ в **`payment_review`** («Платёж на проверке банка»: НЕ протухает, `pending_payment → payment_review → paid|failed|cancelled`; poll опрашивает его платёж без 25ч-потолка; дольше 7 дней → DM-сторож `payment-review-watch` без автозакрытия) + клиенту РОВНО одно автосообщение (дедуп по смене `last_provider_status`); исход-отказ → честное сообщение + DM. **(4) Кнопка «Проблема с оплатой»** (до выпуска карты; Mini App + сайт `/api/orders/problem`; «я оплатил» → `payment_review`, дедуп DM час, доставка ПЕРВОЙ) и **учёт возвратов** (`countRefundishHistoryByUser` 180 дней → информ-DM; возврат по succeeded-платежу → денежная аномалия). Миграции 0031-0034 применены на прод 2026-08-15 вместе с выкатом (PR #161, env `PHONE_REQUIRED_FROM_RUB=10000` задан); живой заказ подтвердил: счёт уходит с настоящими email и IP, fallback-алертов ноль.

текст оператора маскируется от номеров карт ДО отправки и записывается ПОСЛЕ неё (строка в переписке — запись произошедшего); захват диалога атомарный и чужой не перебивает. **Партнёры** (тикет 12): `/admin/partners` (привёл / начислено / баланс / ставка — ТОЛЬКО из `locked_rate_l1_bps`), раскрытие приглашённых и `/admin/partners/payouts` с двумя решениями по заявке. **Список партнёров растёт от НАЧИСЛЕНИЙ** (`referral_accruals ∪ referral_partners`), а не от таблицы профилей: строку профиля создаёт только месячный роллап 1-го числа, и заработавший 5 августа партнёр до 1 сентября отсутствовал бы на экране, который честно писал бы «Партнёров пока нет» при живых деньгах в ledger; без профиля ставка показывается дефолтная — ровно та, по которой начисление и посчитано. «Выплачено» — ДВА перехода `requested → processing → paid` через существующий атомарный `transitionReferralPayout` (прямой прыжок машина не разрешает, и `processing` страхует от повторного нажатия), «отклонить» — один переход, и компенсирующая строка в ledger НЕ пишется: формула баланса просто не считает отклонённые заявки. Операция читает ФАКТИЧЕСКИЙ статус заявки (`findReferralPayoutForPanel`) и от него пляшет: два перехода вне одной транзакции означают, что упавший между ними процесс оставляет заявку в `processing` — её сумма продолжает вычитаться из баланса, и зашей роут `from: 'requested'` намертво, вынуть такую заявку можно было бы только SQL'ем на проде (`isPayoutDecidable` поэтому пускает и `processing`; несостоявшийся переход возвращает статус ИЗ БАЗЫ, а не запрошенный — соврать о состоянии денег нельзя). **Заблокированному антифродом партнёру выплата не проводится** (`409 partner_suspended`; кабинет не даёт ему подать заявку, но поданная ДО блокировки живёт в `requested` — без гейта блокировка снималась бы одним кликом), отклонить его заявку можно: это способ её закрыть. По умолчанию экран показывает только открытые заявки (`?all=1` — все): закрытые копятся навсегда и вытеснили бы живые за потолок выборки. Панель фиксирует ФАКТ, деньги уходят вручную (`settlePayout` — mock). Реквизиты выплаты наружу не отдаются. Раздел только у владельца. ⚠️ Кто именно провёл выплату, видно ТОЛЬКО в логе — колонки актора у `referral_payouts` нет (разбор в `docs/BACKLOG.md`). Уведомления персоналу — `lib/alerts/notify-staff.ts` через бота ВХОДА, получатели из `staff` узкой выборкой без `totp_secret` и ТОЛЬКО с правом на соответствующий раздел (`capability`), дедуп по ключу с окном на вызов, 403 у одного не глушит остальных, а незаданный токен бота БРОСАЕТ (иначе «не отправлено» неотличимо от «отправлено» и обращение теряется при зелёном ответе клиенту); события: новое обращение, застрявший заказ (только если автоповтор `issue-card` НЕ помог), холд банка сразу, низкий баланс карт. ⚠️ Алёрт баланса вернулся с ДВУМЯ порогами: «не хватает на типовой заказ» (авария, раз в час) и «не хватает на самый дорогой заказ каталога» (предупреждение, раз в СУТКИ — окно задаётся на вызов, ключ с датой сам по себе суток не держит) — один порог от максимума был бы вечно красным, а такие алёрты перестают читать; выключение теперь ЯВНЫМ флагом `VCC_BALANCE_ALERT_DISABLED`, ноль в пороге означает «считать относительно», а явно заданный порог ОТМЕНЯЕТ второй уровень. Порог экрана панели считается ТОЙ ЖЕ функцией, что и крон-алёрт. Дедуп фиксируется только по факту доставки, Sentry живёт под тем же окном, а если получателей нет вовсе — уведомление уходит владельцу (`notifyOps`): на проде `staff` пуст до ручного заведения, и молчание было бы неотличимо от тишины. **Редизайн 2026-08-27 (PR #173, спека `.scratch/admin-panel-redesign/`):** все тексты панели — в ОДНОМ словаре `lib/panel/labels.ts` (термины «Ждут оплаты», «Проверка платежей», «Истёк срок», «Ошибка»; тон безличный; канарейка в `labels.test.ts` роняет тест на «ты»-формах и слове Sentry — в словаре, в `roles.ts` и в исходниках страниц; ключи адресов `?s=unpaid`/`?sort=` не менялись — пересланные ссылки живы; клиентские словари кабинета/бота словарь панели НЕ импортируют, аудитория разная). ## Фаза 2 — виртуальные карты (PaySpace)

Карты выпускает **app.pay.space** (это НЕ Love&Pay: L&P и Freekassa принимают рубли, PaySpace
выпускает карту, которой клиент платит на сайте сервиса). Контракт подтверждён живыми вызовами.

**Инварианты, которые нельзя нарушать:**

- **`createCard` НЕ ретраится** (`idempotent:false`) — единственная мутирующая операция без
  идемпотентного ключа у провайдера: повтор на таймаут/5xx выпустил бы вторую профинансированную
  карту-призрак. Остальные операции идемпотентны через `request_id` и ретраятся ×2.
- **Атомарный claim `paid → in_fulfillment` ДО операций** (`transitionOrderDetailed`) — at-most-once
  выпуск; recovery потерянных — cron `poll-payment`.
- **Полные `pan`/`cvc` не пишутся в логи, БД и Sentry** — только `pan_masked`. Санкционированных
  каналов выдачи ровно два: сообщение в Telegram при выпуске и разовый показ в кабинете. Других
  добавлять нельзя без threat-model.
- **Дока провайдера врёт** — суммы приходят то строкой, то числом, `exp_date` в формате `MM/YY`,
  опциональные поля бывают `null`. Всё через Zod, дрейф → `PaySpaceContractError`.
- **Операционный гейт — баланс VCC-субаккаунта:** на каждую карту нужно `цена + буфер (+$4 fee)`.
  Сколько именно снимется с фонда ради заказа, знает ОДНА функция
  `orderFundingRequirementUsdCents` (`lib/pay-space/funding.ts`) — её же зовут порог алёрта
  низкого баланса и preflight; правило «пригодна ли живая карта для долива» тоже одно
  (`isCardReusable`, оно же в `issue-card`).
- **Preflight фонда перед выставлением счёта** (на проде с 2026-08-25, PR #171): `POST /api/payments/create`
  последним шагом перед созданием счёта проверяет, есть ли чем выпустить карту, и при нехватке
  отдаёт `422 fulfillment_capacity` — деньги не принимаются вовсе. Гейт стоит на ВЫСТАВЛЕНИИ
  счёта, а не на приёме денег (`repeat_confirm` проходит мимо); отказ НЕ трогает заказ
  (`ready_for_payment` с зафиксированной ценой — перевод в `expired`/`failed` был бы наказанием
  клиента за нашу проблему); **fail-open** — непрочитанный баланс оплату пропускает, выключатель
  явным флагом `PAYSPACE_PREFLIGHT_DISABLED`. Баланс берётся из СВОЕГО снимка
  `vcc_balance_snapshots` (его пишет крон опроса баланса, свежесть 30 мин; протух — один живой
  запрос с поводком 2 с), поэтому в горячем пути провайдер не нужен и его недоступность продажи
  не останавливает. Свободным считается **остаток минус уже обещанные карты**
  (`findOrdersCommittingCardFund`: `pending_payment` с живым счётом, `paid`, `in_fulfillment`)
  минус `PAYSPACE_SAFETY_RESERVE_USD_CENTS`; ⚠️ `ready_for_payment` в обязательства НЕ входит —
  иначе заказ вычитал бы сам себя. ⚠️ `VCC_BALANCE_ALERT_DISABLED` гасит СООБЩЕНИЯ, а не опрос — иначе флаг
  «не шуметь» ломал бы питание снимка. **Проверка и занятие фонда — одна неделимая операция** под
  `pg_advisory_xact_lock('vcc-funding')` (тикет 05): заказ становится `pending_payment` только
  ПОСЛЕ ответа шлюза, и в этом окне двое видели одни и те же деньги. Замок держится на время
  РАСЧЁТА, а не вызова шлюза; резерв (`vcc_fund_reservations`, одна строка на заказ) живёт до
  срока счёта и учитывается, только пока заказ в `ready_for_payment`. ⚠️ Не удалось занять (таймаут замка) — ОТКАЗ, а не пропуск:
  fail-open выключал бы защиту ровно под нагрузкой. Остаточный риск просадки между гейтом и
  выпуском сохраняется. Тексты, дедупы, событие журнала и разбор —
  [`docs/reference/virtual-cards.md`](docs/reference/virtual-cards.md).
- Срок жизни карты — одно число `CARD_LIFETIME_DAYS`, зеркало с витриной кабинета (инвариант 10).

Клиент, буфер под VAT/FX, модель префандинга, классификация отказов топапа и рециклинг —
[`docs/reference/virtual-cards.md`](docs/reference/virtual-cards.md).

## Архитектурные инварианты (не нарушать)

1. **`order_events` — append-only.** Никогда не `UPDATE`/`DELETE`. Любое изменение статуса = новая строка в той же транзакции, что меняет `orders.status`. Форсится триггером БД `order_events_append_only` (миграция 0018) — `UPDATE`/`DELETE` бросают exception даже для `service_role` (RLS его не покрывает).
2. **Идемпотентность webhook'ов** — `UNIQUE(provider, provider_ref)` на `payments` + `INSERT ... ON CONFLICT DO NOTHING`. Повторный вызов не создаёт дубль или двойной переход. Anti-replay webhook'а L&P держится на атомарном `claimPaymentSucceeded` (подпись без timestamp/nonce), а claim платежа + `transitionOrder(paid)` идут в ОДНОЙ транзакции (`processInvoicePaid`) — сбой перехода откатывает claim, иначе оплаченный заказ застревал бы без recovery. Плюс частичный `UNIQUE(order_id) WHERE status='pending'` — не более одного живого инвойса на заказ. Терминальные события L&P (`expired`/`cancelled`) переводят платёж через симметричный атомарный `claimPaymentTerminal` (`pending→failed` условным UPDATE, null-возврат = idempotent_skip) — НЕ безусловный UPDATE: при гонке с paid-путём не перезаписывает уже `succeeded` платёж в `failed`.
3. **Деньги — integer в минимальных единицах.** `amount_rub` — копейки, `original_amount` и `balance_usd_cents` — USD-центы. Никогда `numeric`/`float`.
4. **State-переходы заказа — только через `transitionOrder()`** (`packages/db/src/repositories/orders.ts`). Прямой `UPDATE orders SET status` запрещён. Разрешённые переходы — `allowedTransitions` в `packages/types/src/order-state-machine.ts`.
5. **Zod на всех границах.** Webhook body, Telegram updates, AI tool inputs, URL params — парсятся схемой из `@oplati/types`. Не `any`, не `as T` без обоснования.
6. **Webhook endpoints всегда `200 OK`** (даже при невалидном input — ошибка в теле), иначе Telegram/L&P ретраят и забивают очередь. Исключение — неверный `X-Telegram-Bot-Api-Secret-Token`: `401` отдают `/api/bot` (клиентский бот) и `/api/staff-bot` (бот персонала, свой секрет).
7. **Каталог `services` — public read, не public write.** RLS включён; `anon/authenticated` имеют только `SELECT` по policy `services_public_read_active` (`is_active=true`). Seed/изменения каталога — через server-side/service role и Drizzle.
8. **Весь доступ к user-таблицам — только через `service_role`/прямое подключение.** RLS на них — deny-by-default без позитивных политик (браузерный anon-клиент не читает ничего, кроме активного каталога). Модель безопасна, пока не появится клиентский Supabase-запрос к user-данным: тогда deny-by-default его заблокирует — понадобится per-user policy, а не ослабление RLS.
9. **Неаутентифицированные write-эндпоинты — под rate-limit.** `/api/chat`, `/api/orders/propose`, `/api/orders/confirm`, `/api/auth/telegram/link`, `/api/chat/clear`, `/api/cabinet/referral` (веб-ветка) зовут `checkRateLimit` по IP ДО резолва сессии и записей в БД: без cookie каждый запрос иначе получает свежую сессию и свежий суточный кап (cost-DoS на строки users/orders/link_tokens). `POST /api/cabinet` авторизован подписью `initData`, поэтому сплошного IP-лимита у него НЕТ намеренно (за CGNAT и за собственным VPN Оплатишки один адрес на всех клиентов — общий бакет резал бы живых плательщиков за чужой флуд): по IP считаются ТОЛЬКО похожие на подделку отказы подписи и битые тела (`cabinet-auth`, приём как у `alert-webhook-auth`; `expired` и `misconfigured` в счёт НЕ идут — это штатное протухание сессии и наша же авария конфига), а опознанный запрос лимитируется по `telegram_id` в СВОЁМ бакете `cabinet` (не общем с ботом) и обязательно ДО upsert'а `users` — для этого `resolveCabinetUser` разделён на `verifyCabinetInitData` (чистая проверка подписи) и `upsertCabinetUser` (запись). ⚠️ Соседний `/api/cabinet/referral` на эту схему ещё НЕ переведён (см. `docs/BACKLOG.md`). В боте три бакета по той же причине «свой кошелёк на каждый вход»: `/start` — `telegram-start` (это шаг оплаты, `link_<token>`; ронять его чужим трафиком нельзя), медиа — `telegram-media` (Telegram шлёт по апдейту на каждое фото альбома), текст и callback-кнопки — `telegram`. `GET /api/orders/status` — read-only (`readWebSessionId` + `findUserIdByWebSessionId`, пользователя НЕ создаёт) + ОТДЕЛЬНЫЙ бакет `web-order-status` (60/мин, аудит 2026-07-28): после оплаты клиент опрашивает статус каждые 4 с (≈15/мин), и общий с `propose`/`confirm` бакет на 8/мин он выедал сам — часть поллов ловила 429, а создание следующего заказа с того же IP блокировалось на 5 минут (за CGNAT мобильных операторов это несколько живых клиентов в одном IP). **Источник identity зависит от `CLIENT_IP_MODE` (дефолт `traefik` с 2026-07-28).** На проде он же: доверенный источник — **ПРАВЫЙ элемент `x-forwarded-for`** (его пишет сам Traefik из адреса соединения), а клиентский `x-real-ip` игнорируется — за Traefik он проходит насквозь и подделывается. Значение нормализуется и валидируется как IP (`node:net`.isIP): без этого прокси с `host:port` давал бы новую identity на каждом соединении (эфемерный порт) и лимит обходился бы полностью; мусор ключом не становится, невалидный правый элемент → `unknown` (fail-closed, БЕЗ добора левее). В режиме `vercel` (исторический; ДЕФОЛТОМ быть перестал — прежний дефолт при потере переменной молча включал доверие к подделываемому за Traefik `x-real-ip`, то есть полный обход лимита, CWE-348) берётся `x-real-ip`, а НЕ левый `x-forwarded-for` (подделываем клиентом → ротация обнуляла лимит, CWE-348); `xff` — только fallback (правый элемент). Третья ветка — `X-Client-IP` при timing-safe совпадении `PROXY_SHARED_SECRET` — осталась от реверс-прокси РФ-доступа эпохи Vercel ([`docs/history/vercel-era.md`](docs/history/vercel-era.md)); на проде секрет НЕ задан, поэтому ветка мертва. Оживлять её можно только вместе с прокси: без него заголовок подделает любой клиент (тот же CWE-348). Fail-open при незаданном Upstash.

10. **Зеркало — два значения, обязанные совпадать, без автосверки.** Правишь одну сторону — той же правкой правишь вторую; ничто не упадёт, разъедется только поведение. Известные зеркала помечены словом «зеркало» на месте. Сейчас их четыре: потолок **$1200** (`HIGH_VALUE_SERVICE_SLUGS` ↔ `lib/telegram/amount.ts` ↔ `StartScreen.tsx` ↔ `CatalogView.tsx` ↔ `MAX_ORDER_USD_CENTS` в `lib/jobs/vcc-balance.ts`), `FREEKASSA_BUYER_FEE_PERCENT` ↔ ползунок комиссии в кабинете Freekassa (API комиссий у них нет — разъезд означает обещание клиенту неверной цены), `CARD_LIFETIME_DAYS` ↔ срок в витрине кабинета и **свежесть снимка фонда** `SNAPSHOT_FRESH_MS` (30 мин, `lib/pay-space/preflight.ts`) ↔ шаг крона `poll-payment` в `infra/crontab.example` (5 мин): переведёшь крон на час — каждая оплата снова пойдёт к провайдеру живьём. Зеркало — плата за отсутствие общего источника, поэтому предпочтительный ход — не «сверить внимательнее», а **убрать зеркало**: так сделано с ценой (обе точки расчёта зовут одну функцию) и с журналом миграций (расхождение ловит `GET /api/ready` и красит деплой).

## Команды

Обычные скрипты (`dev`, `build`, `typecheck`, `lint`, `test`) — в `package.json` корня и
пакетов, запуск через `pnpm` / `pnpm --filter <pkg>`. Здесь только то, чего в скриптах не
прочитать:

```bash
pnpm --filter @oplati/db db:generate    # сгенерировать миграцию из schema.ts
pnpm --filter @oplati/db db:push        # применить схему напрямую (ТОЛЬКО dev; на проде — db:migrate)
pnpm --filter @oplati/db db:migrate     # применить через migrate (.env из корня)
pnpm --filter @oplati/db db:seed        # seed каталога сервисов (⚠️ прод-каталог живёт в БД, мерж его не обновляет)
pnpm --filter @oplati/db db:staff list|add|disable|enable|reset-totp   # персонал панели (секрет TOTP не выдаёт — его создаёт панель при первом входе)
pnpm --filter @oplati/db db:init-roles  # роли БД (read-only `metabase_ro`, см. runbooks/metabase.md)
```

⚠️ Все `db:*`-скрипты грузят `.env` из корня, а он указывает на старые Supabase-базы: на проде
персонал заводится тем же `INSERT … ON CONFLICT`, что в `upsertStaffByTelegramId`, через `psql`
в контейнере `oplatishka-db-ry3smb` (порядок ssh-команд — скилл `deploy-and-migrations`).

### Миграции БД

**Forward-only через Drizzle.** Схема — `packages/db/src/schema.ts`. Правка схемы → `db:generate` → `.sql` в `packages/db/migrations/` → `db:push` (или `db:migrate`, если push не видит `DATABASE_URL`). Никогда не редактировать применённую миграцию и не править БД через Supabase Dashboard в обход Drizzle. Destructive-изменения — только backwards-compatible (nullable-колонки, два деплоя на удаление).

⚠️ **Миграция, УДАЛЯЮЩАЯ колонку, применяется ПОСЛЕ выката кода, а не до.** Drizzle на `db.select().from(t)` генерирует ЯВНЫЙ список колонок из `schema.ts` РАБОТАЮЩЕГО образа — значит образ, выпущенный до удаления, продолжает спрашивать колонку и получает `column ... does not exist` на каждом запросе. Grep «поле нигде не читается» это не ловит: он гоняется по новому коду, а ломается старый. В окне между выкатом и миграцией `/api/ready` законно красный (`migrations_pending`), но приложение ЖИВО — лишняя колонка безвредна. Обратная сторона: откат на образ старше такой миграции кладёт то, что читает эту таблицу (порядок и способ вернуть колонку — [`docs/runbooks/rollback.md`](docs/runbooks/rollback.md)).

**Enum-расширения — отдельной миграцией.** `ALTER TYPE ... ADD VALUE` в Postgres нельзя использовать в той же транзакции, где добавленное значение применяется (migrator оборачивает миграцию в транзакцию). Поэтому добавление значения в enum держим отдельной миграцией, не смешивая с DDL/DML, которые это значение используют (иначе `db:migrate` упадёт).

⚠️ **ДЕПЛОЙ НЕ ПРИМЕНЯЕТ МИГРАЦИИ. После каждого мержа с новой миграцией применить её на прод-БД отдельно — сразу, а не «когда включим фичу».** Пайплайн собирает образ и перезапускает сервис, не более. 2026-07-28 этот шаг потерялся: код Freekassa уехал в `main` 26.07, миграции 0025/0026 на прод не попали, и при включении шлюза первый же счёт упал с `relation "freekassa_nonce" does not exist` — **при зелёном деплое, здоровом `/api/health` и без единого алёрта** (см. [`docs/incidents.md`](docs/incidents.md)).

С 2026-07-29 такая схема больше не молчит: **`GET /api/ready`** сравнивает журнал миграций,
запечённый в образ, с журналом в живой БД (и свежесть, и ЧИСЛО применённых), и шаг «Проверить
готовность релиза» в `deploy.yml` красит деплой. Liveness `/api/health` БД по-прежнему не
трогает. Обнаружение автоматизировано, применение — руками: прод-БД снаружи недоступна,
порядок ssh-команд и дописывания журнала — скилл `deploy-and-migrations`, пошагово —
[`docs/runbooks/deploy.md`](docs/runbooks/deploy.md).

## Конвенции кода

- **`strict: true`** + `noUncheckedIndexedAccess` + `verbatimModuleSyntax`. `any` запрещён; `unknown` + Zod narrow.
- **Never swallow errors** — `catch {}` и `catch { console.log }` запрещены: либо re-throw, либо `Sentry.captureException` + structured error.
- **Result pattern** для ожидаемых неудач (`{ ok: false, reason }`); `throw` — для неожиданного.
- **`console.log` запрещён** в production-коде — только `logger.*` (pino). PAN/CVC/токены не логируются никогда.
- **`fetch` без timeout запрещён** — всегда `AbortController`, и таймаут обязан покрывать ЧТЕНИЕ ТЕЛА, а не только заголовки (аудит 2026-08-10): сервер, отдавший `200` и замолчавший на теле, вешал запрос навсегда. Клиенты PaySpace/L&P перевзводят таймер на чтение тела своим бюджетом (у `createCard`, `POST /invoices`, `revoke` ретрая нет — оборванное тело значит осиротевшую операцию у провайдера). Серверный код читает JSON через `fetchJsonWithTimeout` из `lib/http.ts`; `fetchWithTimeout` снимает таймер до чтения тела и годится только браузеру. Транспорт undici — это `TypeError('fetch failed')` И `TypeError('terminated')` (обрыв сокета уже ПОСЛЕ заголовков), оба ловит `isNetworkTypeError`.
- **`Date` в raw-`sql`-фрагменты Drizzle передавать нельзя — только ISO-строку** (`cutoff.toISOString()`, паттерн `analytics.ts`): postgres-js на проде падает `TypeError … Received an instance of Date` при сериализации параметра, а PGlite в тестах `Date` переваривает — регресс невидим в зелёном прогоне (инцидент 2026-08-15, PR #162). Параметры обычных builder-условий (`eq`, `lt`, `gte`, …) не затронуты — там drizzle маппит `Date` сам.
- **Commits — Conventional Commits** (`feat(agent):`, `fix(payments):`); squash merge; заголовок ≤ 72 символа.
- Graceful degradation на внешних зависимостях (Anthropic, БД): понятный ответ пользователю, не 500.
