# Бэклог — отложенные задачи и идеи

**Единственный список «на потом».** Всё, что решено не делать сейчас: отложенные
задачи, открытые находки аудитов, идеи по продукту. Прод работает без них.

Правила ведения:
- новая запись — с **датой** и ответом на «почему отложено» (без этого через месяц
  непонятно, отложено осознанно или забыто);
- закрытая — убирается отсюда и попадает в [`CHANGELOG.md`](CHANGELOG.md);
- если запись описывает контур, которого больше нет, — её надо удалить, а не
  оставлять «на всякий случай»: устаревшая запись хуже отсутствующей, потому что
  агент (и человек) читает её как актуальную.

Закрытые аудиты и исполненные планы — в [`history/`](history/).

## Безопасность

### Панель Dokploy печатает ключи R2 в свои логи (найдено 2026-07-25)

При каждом бэкапе панель логирует полную команду `rclone rcat` вместе с
`--s3-access-key-id` и `--s3-secret-access-key` **открытым текстом** — видно в
`docker service logs dokploy`. В бакете `dokploy-backups` лежат дампы боевой БД,
то есть эти ключи дают доступ ко всем клиентским данным мимо RLS и прав на сервере.

- **Экспозиция ограничена:** в Loki они НЕ уезжают — агент Alloy собирает только
  `oplatishka-web*` и `dokploy-traefik`, а логи панели с 2026-07-25 ещё
  и явно исключены `drop`-правилом. Доступ к ключам = доступ к `docker.sock` на VPS
  или к самой панели.
- **Что делать:** ротировать токен R2 в Cloudflare и выдать ему права **только** на
  бакет `dokploy-backups` (текущая область прав не проверялась). Само логирование —
  поведение Dokploy, править нечем.
- **Заодно:** админский API Dokploy отдаёт весь env приложений (ключ Anthropic, токен
  бота, `DATABASE_URL` с паролем, `CRON_SECRET`, `INTERNAL_API_TOKEN`, пароль Basic
  Auth dev-стенда) в открытом виде любому с `DOKPLOY_API_KEY`. Это устройство панели,
  а не баг, но означает: ключ панели равен всем секретам сразу.

### `CRON_SECRET` лежит открыто на VPS (S-3 проверки 2026-07-25)

`/etc/cron.d/oplatishka` содержит секрет открытым текстом, и cron пишет **всю
командную строку вместе с `Authorization: Bearer <секрет>` в `/var/log/syslog`**
при каждом запуске. Секрет также виден в `ps` / `/proc/<pid>/cmdline`. Владелец
секрета может дёрнуть `retention` (удаление сообщений) и `recycle-cards`
(необратимый release карт = деньги).

- **Смягчает:** `/opt/alloy/config.alloy` файлы `/var/log` не собирает — в Loki
  секрет не уезжает. Экспозиция ограничена локальными процессами VPS.
- **Что делать:** вынести секрет в отдельный `600`-файл и звать
  `curl --config /etc/oplatishka/cron.conf`; `/etc/cron.d/oplatishka` → `chmod 600`.
  Заготовка и обоснование — в шапке [`../infra/crontab.example`](../infra/crontab.example).
- **Почему не сделано сразу:** правка на живом VPS, а не в репозитории; чтобы
  файл и репозиторный пример не разъехались, менять надо оба одновременно.

### Приложение подключается к Postgres суперюзером (S-5 / C-3, 2026-07-25)

Роль `oplatishka` — `rolsuper=t`, `rolbypassrls=t` (так создаёт образ
`postgres:17`). Утечка `DATABASE_URL` (панель Dokploy, дамп в R2, лог) даёт не
scoped-роль, а полный суперюзер: можно `ALTER TABLE order_events DISABLE TRIGGER`,
то есть снять DB-уровневую защиту инварианта №1, и `COPY … FROM PROGRAM`. На
Supabase таких прав у приложения не было.

- **Что делать:** отдельная роль `NOSUPERUSER BYPASSRLS` с GRANT только на
  `public`; суперюзер оставить для миграций и `db:init-roles`.
- ⚠️ **Не забыть про последовательность `freekassa_nonce`** (миграция 0026):
  новой роли нужен `GRANT USAGE ON SEQUENCE freekassa_nonce`. Без него `nextval`
  упадёт с permission denied, и создание счетов Freekassa встанет целиком —
  сейчас это не видно только потому, что приложение ходит суперюзером.
- **Риск правки:** смена `DATABASE_URL` на проде + прогон миграций под другой
  ролью. Делать на dev-стенде, потом на проде.

### Репозиторий публичный, а в доках инфра-хосты (S-6 / C-4, 2026-07-25)

`elfuerte72/oplati_podpisku` — `visibility: PUBLIC`. В доках светятся URL панели
Dokploy, внутренние хосты сервисов, логин Basic Auth dev-стенда, имя R2-бакета.
Токенов не закоммичено (проверено), но адрес панели, компрометация которой = деплой
произвольного кода и все прод-секреты, отдаётся бесплатно.

- **Что делать:** панель за IP-allowlist или VPN; инфра-хосты вынести из
  публичного репозитория.

### CSP → боевой режим (L-21 аудита; отложено 2026-07-19)

CSP с 2026-07-11 работает в `Report-Only`. Жалоб за период наблюдения не было.
С 2026-07-25 `report-uri` снова доставляет отчёты в Sentry (до пересборки DSN не
попадал в билд, отчёты уходили в никуда) — то есть наблюдение опять живое.

- **Что делать:** в `apps/web/next.config.ts` заменить
  `Content-Security-Policy-Report-Only` на `Content-Security-Policy`.
- **Перед включением:** просмотреть CSP-репорты в Sentry за неделю; после —
  смоук сайта (чат, каталог, оплата, партнёрка). Откат — вернуть `-Report-Only`.
- ⚠️ **Проверить баннер Freekassa в футере.** Он тянется с `cdn.freekassa.net`;
  домен уже внесён в `img-src`, но при любой правке политики это надо сохранить —
  пропавшая картинка для Freekassa равна снятому баннеру, то есть нарушению
  условий подтверждения ресурса.

### `CLIENT_IP_MODE` — безопасный режим opt-in (C-2, 2026-07-25)

Дефолт `'vercel'`, то есть на self-host правильный режим надо задать вручную, и
рантайм не проверяет, что его задали. Пересоздали приложение или потеряли env →
`curl -H 'x-real-ip: <random>'` обнуляет per-IP лимит на каждом запросе (CWE-348),
без единого алёрта.

- **Что делать:** дефолт по признаку платформы (`VERCEL === '1' ? 'vercel' :
  'traefik'`) либо fail-fast / Sentry-warn при
  `NODE_ENV=production && !VERCEL && CLIENT_IP_MODE==='vercel'`.

### Hermes-агент работает от root — изоляция «уровня 2» (заведено 2026-07-26)

Гилфойлу выдали read-токены Loki и Sentry и правило «в Оплатишке только читать»,
записанное в его `SOUL.md`. Это дисциплина промпта, а не ограничение прав: процесс
агента запущен от **root**, значит технически может остановить контейнеры, прочитать
env приложения (боевые ключи L&P/PaySpace, пароль БД) и подключиться к Postgres.
Модель угроз здесь не «злой агент», а обычная ошибка исполнения или prompt injection
из содержимого, которое он читает (логи, сообщения канала).

- **Что делать:** отдельный unix-пользователь (`hermes`), **без группы `docker`** —
  членство в ней равносильно root; узкие правила `sudoers` строго на чтение
  (`docker ps`, `docker logs`, конкретные скрипты сводки), без `docker exec` и
  `docker run`; файлы профиля и `.env` агента — `chown hermes:hermes`, режим `600`.
- **Проверка после:** от имени `hermes` не выполняются `docker exec`, `docker stop`,
  чтение `/etc/dokploy`, `psql` в боевую БД; сводка `oplatishka-status.sh` при этом
  по-прежнему отрабатывает целиком.
- **Цена вопроса:** час работы + риск сломать уже работающего агента, поэтому
  делать не в спешке и с бэкапом профиля.

### GitHub-runner периодически не дозванивается до VPS (симптом закрыт, причина внешняя, 2026-07-25)

Деплои PR #110 и #113 упали одинаково: `curl exit 28` — **TCP-соединение к 443 не
устанавливается вовсе** («Couldn't connect to server»), до HTTP дело не доходит. Оба раза прод
пересобирали вручную.

**Диагноз: короткие эпизоды сетевой недоступности VPS со стороны раннеров GitHub** (маршрут
Azure → Hostinger). Наш код и конфиг ни при чём, воспроизвести по требованию нельзя.

**⚠️ Прежнее объяснение «панель не отвечает под нагрузкой собственной сборки» ОПРОВЕРГНУТО —
не возвращать его:**
- лог сборки #109 закрыт в 08:31:52, а падение #110 — в 08:40–08:42, через 8 минут после;
- лог сборки #112 закрыт в 13:03:01, падение #113 — в 13:08–13:16;
- `sar` в 13:10:31 (разгар падения): load average 1 мин = **0.25**, `blocked` = 0 — простой;
- проба из GitHub Actions в 15:00 того же дня: 5/5 на панель, 3/3 на прод-сайт, голый `nc` на
  443/80/22 — всё проходит.

**Что ещё исключено:** `ufw` пропускает 443 отовсюду; `fail2ban` — только jail `sshd`; внешнего
firewall у Hostinger нет (список пуст); Traefik не перезапускался 2 недели; панель не за
Cloudflare; фантомных сборок нет.

**Сделано:** `--connect-timeout 10` (без него неотвечающий SYN висел ~133 с системного таймаута
ядра, и три попытки съедали бюджет сплошным ожиданием — окно ретраев было фиктивным), 10 попыток
с паузой 45 с, проверка факта обновления прода по `startedAt` из `/api/health` и алёрт о провале
в Telegram.

**Осталось открытым:**
- **Проверить, был ли в те окна (08:40 и 13:08 UTC) даун самого сайта** по Better Stack. Если
  недоступность не специфична для GitHub, в эти минуты клиенты тоже не открывали сайт — и это
  проблема куда крупнее CI.
- **Self-hosted runner на VPS** — раннер сам опрашивает GitHub исходящим соединением,
  входящее из Azure не нужно, класс проблемы исчезает. Цена — секреты репозитория и агент
  с доступом к прод-контуру живут на боевом VPS, плюс нагрузка на те же 2 ядра.
  **Решение владельца 2026-07-25: пока не делаем**, хотя эпизодов уже три за день
  (08:40–08:42, 13:08–13:16, 17:15–17:24, по 8–10 минут). Провал деплоя больше не молчит —
  приходит алёрт, перезапуск в один клик. Наблюдаем неделю: участятся или удлинятся —
  возвращаемся к этому пункту с накопленной статистикой, а не по одному случаю.
- ~~Секреты `DEPLOY_ALERT_BOT_TOKEN` / `DEPLOY_ALERT_CHAT_ID`~~ — заданы 2026-07-25

`poll-payment` в течение 5 минут.

- **Что делать:** `--init` у контейнера + обработчик SIGTERM с дренажом, либо
  `stopGracePeriodSwarm` и вынос фулфилмента из синхронного пути вебхука.

лежащий прокси. Случай «провайдер отвечает 200, выдаёт ссылку, но оплаты не
проходят» для кода выглядит полным успехом.

- **Что делать:** алёрт на аномалию отношения `payment_invoice_created` →
  `payment_succeeded` за окно (условно: выставлено ≥5 счетов, оплачен 0 за час).
  События уже пишутся в `order_events`, логи приложения с 2026-07-25 в Loki — то
  есть считать можно и по БД, и по логам, без нового хранилища.
- **Почему важно именно сейчас:** переключатель провайдера (см. план Freekassa)
  включает владелец вручную. Без этого сигнала его нечем дёргать вовремя — а значит
  вся ценность второго канала теряется на задержке «пока клиент не пожалуется».
- **Осторожно с порогом:** при малом потоке заказов ноль оплат за час — норма.
  Считать только когда счетов выставлено достаточно, иначе алёрт станет шумом.

</details>

### Freekassa — ОСНОВНОЙ шлюз, Love&Pay — резерв (решение владельца 2026-07-26)

> **Обновление 2026-07-26: этапы 1–3 ТЗ реализованы** в ветке `feature/freekassa`
> (клиент+подписи, вебхук, переключатель `PAYMENT_PRIMARY_PROVIDER`, тесты).
> Всё ниже оставлено как контекст решения; **актуальный статус** — в шапке
> [`plan-freekassa-integration.md`](plan-freekassa-integration.md), фактический
> контракт и открытые вопросы — в [`reference/freekassa-api.md`](reference/freekassa-api.md).
>
> **Обновление 2026-07-26 (вторая волна): этап 4 тоже сделан** — `poll-payment`
> провайдер-агностичен, метрика конверсии считается, автофоллбэк за флагом
> `PAYMENT_AUTO_FALLBACK`, в плашке ошибки есть выход в поддержку.
>
> **Что осталось в бэклоге по этой теме:**
> 1. Живая проверка контракта (ждёт `FREEKASSA_SHOP_ID`) и смоук копеечной суммой.
> 2. Проброс реального IP клиента для веб-заказов (сейчас всегда
>    `FREEKASSA_FALLBACK_IP`) — `payments/create` зовётся внутренним self-call'ом,
>    заголовков клиента там нет.
> 3. Дыра, которую ничем не закрыли: если шлюз падает ПОСЛЕ выставления счёта,
>    клиент кликает по ссылке и видит страницу ошибки провайдера — мы об этом не
>    узнаём. Лечится промежуточной страницей-редиректом на нашей стороне; это
>    заметная переделка платёжного пути, отложено осознанно.
> 4. **Возврат ПОСЛЕ успешной оплаты не отслеживается** (найдено при ревью
>    2026-07-26). Добор смотрит только платежи в статусе `pending`; если клиенту
>    вернули деньги через шлюз уже после выпуска карты, мы этого не увидим —
>    карта останется активной. Та же дыра есть и у Love&Pay, то есть это не
>    регресс, а общий пробел: обработки возвратов у нас нет вовсе
>    (`refund_requested`/`refunded` в машине статусов есть, ставит их только
>    человек). Отдельная тема, требует решения «что делаем с уже выпущенной
>    картой».

**Роли поменялись местами.** Запись заводилась 2026-07-25 как «Freekassa = fallback»;
2026-07-26 владелец решил обратное: **Freekassa становится основным приёмом рублей, L&P
уходит в резерв** и включается, если Freekassa недоступна. Переключение — переменной
окружения (см. ниже), автоматического переключения нет.

**Интегрировать ОБЯЗАТЕЛЬНО через API, не через SCI-форму** (указание владельца).
Разница: SCI — это форма, которую отправляет браузер клиента (`pay.fk.money`, подпись
MD5 по секретному слову 1); API — сервер сам создаёт заказ и получает ссылку. Нам нужен
серверный контроль суммы и статуса, как у L&P.

#### Обязательные детали запроса (от провайдера, 2026-07-26)

- **`email`** — реальный адрес клиента либо `<telegram_id>@telegram.org`. У нас
  `telegram_id` есть всегда: оплата без привязки Telegram запрещена гейтом
  `TelegramLinkRequiredError`.
- **`ip`** — реальный IP клиента либо IP нашего сервера. **`127.0.0.1` блокируется.**
  Для заказов из Mini App и бота IP клиента отсутствует → нужен
  `FREEKASSA_FALLBACK_IP` = `177.7.34.106`; для веб-заказов брать `getClientIp` и
  подставлять серверный только когда он `unknown`.
- **`i`** — способ оплаты: **`44` — СБП по QR**, **`36` — банковские карты РФ**.
  Решить: показывать клиенту выбор или слать один по умолчанию (при выборе — это новый
  элемент UI в трёх местах: веб, Mini App, бот).

#### Переключатель провайдера (согласовано 2026-07-26)

Владелец предложил булев `FREEKASSA_ACTIVE=true|false`. **Работать будет**, но при
реализации учесть три вещи:

1. **Смена env на Dokploy = перезапуск контейнера**, то есть переключение не мгновенное
   (полторы-две минуты) и делается руками. Для «шлюз лёг — переключились» это приемлемо,
   но надо понимать, что это не рубильник в UI.
2. **Рекомендованная форма — `PAYMENT_PRIMARY_PROVIDER=freekassa|loveandpay`** вместо
   булева: булев не выражает состояние «оба выключены» и потребует переписывания при
   третьем провайдере. Итоговое решение за владельцем.
3. **Ключи обоих провайдеров обязаны быть заданы одновременно** — иначе переключение
   упрётся в отсутствующий секрет ровно в тот момент, когда некогда разбираться.

#### Что уже сделано

- Регистрация магазина начата (`Оплатишка`, URL `oplatishka.com/`); **кабинет в
  ожидании активации**.
- В env прода заданы `FREEKASSA_API_KEY`, `FREEKASSA_SECRET_WORD_2` (подпись вебхука) и
  `FREEKASSA_SECRET_WORD_1` (нужен только SCI-форме, кодом не читается; лежит про
  запас). **Пуст только `FREEKASSA_SHOP_ID`** — он выдаётся при активации.
  Значения в репозиторий не попадают (он публичный) — только в env и локальный `.env`.
- ⚠️ Секретное слово 2 содержит `$`, `{`, `[`. Проверено пробником на dev-стенде:
  **Dokploy не интерполирует `$` и снимает одинарные кавычки** — значение доходит байт
  в байт, экранировать не нужно. Молчаливое искажение здесь стоило бы неработающей
  проверки подписи, так что при смене способа доставки env проверять заново.
- Полное ТЗ на реализацию — **`docs/plan-freekassa-integration.md`** (в репозитории с

- Баннер провайдера — в футере сайта (`components/info/FreekassaBadge.tsx`),

#### Что можно делать ДО активации кабинета, а что нельзя

**Можно (это ~80% работы):** клиент API + подпись HMAC-SHA256, Zod-схемы в
`@oplati/types`, роут вебхука `/api/payments/freekassa` с проверкой подписи и
идемпотентностью, миграция enum, переключатель провайдера, все юнит- и route-тесты на
фикстурах. Всё это пишется и проверяется без живого кабинета.

**Нельзя без активации:** подтвердить контракт живым вызовом (правило проекта — доки
провайдеров врут), получить `shopId` и секретное слово 2, зарегистрировать URL
уведомления в кабинете, прогнать копеечный сквозной платёж. Поэтому код выкатывается
**с выключенным флагом**, а включается только после живого смоука.

#### Технические предусловия (проверено по коду 2026-07-26)

- **`payment_provider` — это pgEnum** (`yookassa/cryptobot/sbp/manual/loveandpay/paypace`),
  значения `freekassa` в нём НЕТ. Нужна миграция, причём **отдельная**: `ALTER TYPE …
  ADD VALUE` нельзя использовать в той же транзакции, где значение применяется (см.
  раздел «Миграции БД» в CLAUDE.md).
- Инварианты 2, 3, 6 переносятся с L&P без изменений; детектор недоступности
  (`lib/loveandpay/availability.ts` + `PaymentProviderUnavailableError`) станет общим.
- Комиссия Freekassa отличается от L&P, а `COMMISSION_PERCENT` (30% на проде) заложен
  под L&P — **пересчитать маржу до перевода основного потока**.

Подробное ТЗ (этапы работ, грабли, тесты) — `docs/plan-freekassa-integration.md`; по
решению владельца оно пока живёт только в ветке `docs/freekassa-plan`, не в `main`.

**Про баннер (не удалять со страницы):**
- Он в футере слева внизу и присутствует в HTML главной на apex и www. Это их способ
  подтвердить владение ресурсом — **проверяют главную страницу**, поэтому баннер обязан
  оставаться, пока провайдер используется.
- ⚠️ Их ассет `cdn.freekassa.net/banners/medium_1.png` отдаёт **404** (проверено с двух IP,
  с `Referer` и браузерным UA — не hotlink-защита; корень CDN 403, соседние пути тоже 404).
  Похоже, ребрендинг в DUCKGO переместил файлы, а форма отдаёт старый URL. Сейчас браузер
  показывает `alt`-текст. Нужен верный URL от провайдера; если домен окажется другим —
  обязательно добавить его в `img-src`, иначе картинка не загрузится уже по нашей вине.

**Что уже готово в коде:**
- `payments.provider` + `UNIQUE(provider, provider_ref)` — второй провайдер встаёт рядом
  без переделки модели данных (инвариант 2). ⚠️ Уточнение 2026-07-26: **само значение
  `freekassa` всё же требует миграции** — колонка объявлена pgEnum, а не текстом.
- Детектор недоступности провайдера уже есть: `lib/loveandpay/availability.ts` +
  typed `PaymentProviderUnavailableError` → `503 provider_unavailable`. Сегодня все каналы
  показывают «технический сбой, попробуй позже» — **это и есть точка врезки fallback'а**.

**Что решить ДО начала работы:**
1. **Один живой инвойс на заказ.** Частичный индекс `UNIQUE(order_id) WHERE status='pending'`
   не даст держать pending-инвойсы двух провайдеров одновременно. При переключении шлюза
   сначала перевести существующий pending-платёж прежнего провайдера в `failed`
   (`claimPaymentTerminal`), и только затем создавать новый инвойс. Либо пересматривать
   индекс — но тогда «какой инвойс считать актуальным» становится новым инвариантом.
   ⚠️ На практике это значит: клиенты, у которых счёт уже выставлен, в момент переключения
   должны оформить заказ заново. Счёт живёт 1 час, так что окно небольшое.
2. **Цена клиенту.** Комиссия Freekassa отличается от L&P, а цена фиксируется на
   `propose_order` ДО выбора провайдера. Либо цена одна и маржа плавает по провайдеру, либо
   цена зависит от провайдера — тогда усложняется UX (клиент видел одну сумму, платит другую).
   Первое проще и честнее к клиенту.
3. ~~Автоматический fallback или ручной?~~ **Решено 2026-07-26: ручной, переменной
   окружения.** Авто (при `503` сразу пробуем второго) давало бы бесшовность, но клиент не
   понимает, куда платит, и растёт риск двойных инвойсов.
4. **Требования провайдера к egress/IP.** У L&P понадобился задекларированный IP (из-за чего
   когда-то жил squid-прокси). В доке Freekassa требования allowlist на исходящие запросы
   не видно — **уточнить у провайдера**; если нужен, декларируем IP VPS `177.7.34.106`.
5. **Способ оплаты `i`.** `44` — СБП по QR, `36` — карты РФ. Решить: дефолт один на всех
   или выбор клиенту (выбор = новый элемент UI в вебе, Mini App и боте).

**Что предстоит реализовать (по образцу L&P, инварианты те же):**
- Клиент провайдера + подпись, схемы в `@oplati/types`; **контракт подтверждать живым
  вызовом**, не по докам (правило проекта: доки провайдеров врут — так было и с L&P, и с PaySpace).
- Webhook `/api/payments/freekassa`: проверка подписи, **всегда 200 OK** (инвариант 6),
  идемпотентность через `claimPaymentSucceeded` + `UNIQUE(provider, provider_ref)` (инвариант 2),
  терминальная недоплата `amount_mismatch` + ровно один DM владельцу.
- Выравнивание `orders.expires_at` по TTL инвойса (`setOrderExpiresAt`) — TTL у провайдеров
  может различаться.
- Подстраховка потерянных вебхуков: `poll-payment` сейчас опрашивает только L&P. Либо второй
  опрос, либо сделать цикл провайдер-агностичным.
- Тесты: клиент/подпись/handlers по образцу `lib/loveandpay/*.test.ts`, плюс route-тест на
  транзакционную связку и на гейт `order_expired`.


- **Рефералка, Этап E2** — реальный исполнитель выплат (сейчас mock, денег не
  двигает): решить, чем платим (payout-API L&P? сеть USDT?), подключить
  `settlePayout`, формы реквизитов в UI. **E3** — антифрод выводов.
- **VCC-preflight крупных заказов** — перед заказом до $5000 (Airbnb/Booking)
  баланс VCC не проверяется: `createCard`/`topup` падает уже ПОСЛЕ приёма рублей
  → заказ в `failed` и ручной возврат. Добавить проверку баланса в `propose_order`
  для high-value сумм. Актуально: баланс VCC на 2026-07-25 — $104.60 при пороге
  алёрта $50, то есть запас в пару заказов.
- **Поддержка → Telegram forum-topics** — целевая схема вместо interim-DM (один
  topic = один заказ, `/ai_back` возвращает AI).
- **`TELEGRAM_MINIAPP_SHORTNAME`** — не задан, поэтому кнопка «Личный кабинет» на
  сайте открывает кабинет через `?start=cabinet`-меню, а не прямой ссылкой (лишний
  тап). Значение живёт в @BotFather → Bot Settings; через Bot API не читается.
- **Повторный $4 за выпуск карты** — закрыто 2026-07-25 (срок жизни карты стал
  одним числом, долив без надбавки весь срок). Оставлено как ориентир: если
  экономика изменится, точка настройки — `CARD_LIFETIME_DAYS` в
  `@oplati/types/card-lifecycle`.
