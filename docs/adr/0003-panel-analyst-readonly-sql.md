# Аналитик панели пишет SQL сам и выполняет его под отдельной read-only ролью без PII

**Статус:** принято владельцем 2026-09-02 (grill-сессия трека admin-panel-v2,
вопросы Q5, Q10, Q11, Q13), реализовано в тот же день (тикеты 04–08). Рабочее
ТЗ — `.scratch/admin-panel-v2/spec.md` (локальный трекер, вне репозитория).

Сегодня любой вопрос к данным вне готового дашборда Metabase («сколько заказов
застряло в оплате на этой неделе и по каким сервисам?») — это SQL руками через
Metabase за отдельным входом. Самые ценные вопросы задаются реже всего, потому
что дорого. Решено: в панели появляется раздел «Аналитик» — чат с AI, который
по вопросу обычным языком сам пишет SQL, выполняет его инструментом `run_sql` и
отвечает цифрами и таблицами; под ответом видны выполненные запросы и что
вернула база.

Четыре решения, которые стоит записать отдельно от ТЗ:

1. **Свободный SQL, а не набор предопределённых вопросов (Q5).** Ценность
   раздела — в вопросах, которых никто не предусмотрел; список готовых карточек
   уже есть в Metabase и в разделе «Аналитика». Цена принятия — модель может
   написать что угодно, и защита обязана не зависеть от промпта.

2. **Защита — гранты роли и read-only транзакция, а не инструкции модели.**
   Отдельная роль БД `panel_ai_ro` (`packages/db/scripts/panel-ai-role.sql`):
   `LOGIN`, `CONNECTION LIMIT 2`, `default_transaction_read_only = on`,
   `statement_timeout = 30s`, `BYPASSRLS` (RLS без политик иначе даёт 0 строк —
   как у `metabase_ro`). Гранты — набор `metabase_ro` плюс `client_feedback`,
   `funnel_sends`, вьюхи аналитики; **не выдано:** `messages`, `attachments`,
   `link_tokens`, сырая `analytics_events`, контакты в `users`,
   `payments.raw_payload`, `referral_payouts.destination`. Роль УЖЕ `metabase_ro`
   там, где читатель — внешний провайдер модели, а не человек: `staff` без
   `totp_secret`/`totp_last_step`/email/telegram_id, `vpn_subscriptions` без
   `subscription_url`. Поверх роли — независимые эшелоны в коде:
   транзакция `READ ONLY` + `SET LOCAL statement_timeout` в исполнителе
   (`packages/db/src/readonly-query.ts`, своё подключение по
   `PANEL_AI_DATABASE_URL`, `getDb()` не перенацеливается); **одно выражение
   форсит сам Postgres** — запрос уходит extended protocol (`tx.unsafe(sql, [],
   { simple: false })`), а строку из нескольких команд сервер отвергает
   (`42601`); запрос завёрнут в подзапрос с `LIMIT rowLimit + 1`; валидация
   инструмента (`SELECT`/`WITH`, без `INTO`, `FOR UPDATE`, `pg_sleep*`, `COPY`)
   — понятный отказ модели, а не барьер. ⚠️ Барьером она БЫЛА по замыслу и не
   была на деле: `unsafe()` без параметров идёт simple protocol и исполняет
   `;`-цепочку, а ручной лексер расходился с лексером Postgres на `$` внутри
   идентификатора и на escape-строках `E'\''` — цепочка с `COMMIT; BEGIN READ
   WRITE` снимала и read-only транзакцию, оставляя единственным барьером гранты
   (code-review 2026-09-02, исправлено там же). Каждый эшелон
   проверяется тестом отдельно, в том числе на PGlite без роли вовсе.
   `ALTER DEFAULT PRIVILEGES` не ставится: новая таблица = явный грант обеим
   ролям, и словарь схемы в промпте обязан описывать ровно то, что выдано —
   зеркало ловится тестом `schema-dictionary.test.ts`, а не глазами.

3. **Модель — DeepSeek v4 flash через клиент помощника поддержки (Q10).** Тот же
   Anthropic-совместимый endpoint, тот же ключ `SUPPORT_AI_API_KEY`, тот же
   `runProfile`; модель переопределяется `PANEL_AI_MODEL`. Владелец принял, что
   результаты запросов уходят на серверы DeepSeek; цена принятия — провайдер
   видит только то, что отдаёт роль (без email, телефонов, переписки), а
   строковые ячейки дополнительно проходят `maskForModel` — и ячейки результата,
   и ТЕКСТ ОШИБКИ Postgres (он несёт значение, о которое споткнулся запрос:
   `invalid input syntax for type integer: "…"`). Идентификаторы
   (`telegram_id`, `user_id`, uuid) НЕ маскируются намеренно (Q13): аналитик
   обязан уметь указать на конкретного клиента, иначе ответ «у одного клиента
   три протухших заказа» бесполезен. Расходы DeepSeek в клиентский дневной
   бюджет не входят; кап — бакет `panel-ai` 30 запросов / 10 мин по `staff.id`
   (fail-open, как клиентские бакеты — за сотрудником уже стоит вход с TOTP);
   учёт — строка лога `panel.ai.usage`. Отдельную таблицу не заводим:
   `ai_usage_daily` — одна глобальная строка на день без ключа канала, и
   расширять её PK ради панели значит трогать клиентский бюджет.

4. **Чат эфемерный (Q11).** История живёт в клиентском компоненте и уходит с
   каждым запросом (Zod: ≤ 20 ходов, ≤ 8 КБ); сервер stateless, в БД ничего не
   пишется — ни разговоров, ни сообщений. Запись в БД со стороны аналитика —
   никогда. Графиков в ответах нет — «начинаем с чата».

**Что это значит для следующих изменений схемы.** Новая таблица с данными,
полезными аналитику, требует трёх правок в одном PR: грант в
`panel-ai-role.sql`, описание в `schema-dictionary.ts`, ручной `GRANT` на
проде и dev (роль на проде создаётся и обновляется руками — тикет 15). Таблица
с PII в грант не попадает по умолчанию: словарь называет её недоступной, и
модель честно отвечает «данные недоступны аналитику» вместо попытки обхода
(ловушка с email в eval обязана проходить всегда).

Отклонённые варианты: предопределённые вопросы без свободного SQL (не решает
проблему «вопроса, которого не предусмотрели»); подключение аналитика ролью
приложения с защитой только промптом (одна инъекция в вопросе — и модель
читает `messages`); Sonnet вместо DeepSeek (решение владельца — цена);
сохранение истории чатов в БД (расход на схему ради функции, ценность которой
не доказана).
