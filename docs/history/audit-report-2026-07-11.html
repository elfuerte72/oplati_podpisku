1. Управленческое резюме

Проект технически работоспособен, а критический денежный путь спроектирован заметно выше среднего: успешная оплата имеет атомарный claim, переходы заказов централизованы, аудит событий защищён на уровне БД, миграции production полностью совпадают с репозиторием, RLS включён, сборка и 370 тестов проходят. Критических уязвимостей или подтверждённой утечки данных не обнаружено.

До масштабирования и приёма крупных заказов необходимо закрыть четыре риска высокой важности: изоляцию Preview от production-секретов и данных, защиту main/secret scanning, финансовый preflight для заказов до $5000 и противоречие по выдаче PAN/CVC в веб-кабинете. Общий статус: условно готов к эксплуатации при текущем малом объёме, не готов к безопасному масштабированию без remediation High.

4. База данных и транзакционная логика

Итог по БД: хороший. Все 20 Drizzle migration hashes байт-в-байт совпали с live drizzle.__drizzle_migrations. В production 16 public-таблиц, у всех включён RLS. Единственная public policy разрешает только SELECT активных services. Остальные таблицы deny-by-default для anon/authenticated; server-side доступ идёт через доверенный DB/service role.

Успешный платёж: корректный атомарный путь

Подписанный invoice.paid
Conditional payment claim
SELECT … FOR UPDATE заказа
Order status + event в одной tx
Асинхронный issue-card
  • UNIQUE(provider, provider_ref) и partial unique «один pending payment на order» подтверждены live.
  • claimPaymentSucceeded выполняет pending → succeeded conditional UPDATE; webhook и poll не дублируют side effects.
  • transitionOrderDetailed блокирует заказ, валидирует state machine и записывает status/event в одной транзакции.
  • Создание draft-заказа и события created также атомарно.
  • Issue-card сначала делает claim paid → in_fulfillment, поэтому внешний выпуск at-most-once на уровне приложения.

5. Безопасность

Что реализовано хорошо

  • Telegram secret-token, L&P HMAC/signature и internal/cron secrets проверяются до бизнес-логики; сравнение timing-safe.
  • Black-box: неверный Telegram secret → 401; L&P без подписи → безопасный 200 skipped; cron без auth → 401.
  • Zod на webhook, AI tools, route bodies и provider responses.
  • Rate limit до дорогого AI/записи для web/chat/bot/link; production Upstash env присутствуют.
  • AI budget, Haiku router, tool-loop cap и per-user order cap ограничивают расходы.
  • PAN/CVC не найден в БД; PaySpace raw body защищён non-enumerable полем и redact path.
  • Сессия web использует HttpOnly/Secure/SameSite cookie.

Главные security-действия

  1. Изолировать Preview и production credentials.
  2. Защитить main, включить secret scanning/push protection и CodeQL.
  3. Принять решение по browser card reveal; затем CSP.
  4. Убрать PII из логов и усилить Sentry scrubber.
  5. Сузить Supabase grants и Vercel env targets/types.

Deployment Protection выключен согласно архитектурному решению, чтобы Telegram webhook не перехватывался Vercel. Это допустимо только при сохранении endpoint-level подписей и rate limits. Настройки Vercel Firewall/WAF не удалось прочитать подключённым MCP, поэтому заявленный WAF-слой не считается независимо подтверждённым данным аудитом.

Результат dead-code анализа

Knip считает неиспользуемыми четыре Supabase client-файла; поиск по всему репозиторию подтвердил, что их импортируют только собственные barrel-файлы и документация. Вместе с ними можно удалить @supabase/ssr и @supabase/supabase-js, поскольку приложение работает через Drizzle/postgres-js. Отдельные scripts Knip может считать false positive, потому их следует проверять по operational runbooks перед удалением. Неиспользуемые exports/types — в основном API surface, который можно сузить после rg-проверки.

Циклы

Madge показал 15 циклов, главным образом db/index → repositories/index → repository → type DB from index и types/index ↔ loveandpay. Большинство импортов type-only и исчезает в runtime, поэтому это не подтверждённый production cycle. Тем не менее перенос DB/DBLike в отдельный db-types.ts и запрет импорта barrel из leaf-модулей улучшат анализируемость и исключат будущий runtime-cycle.
