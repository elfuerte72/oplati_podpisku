> Архив. Раздел «Что с этим может агент» рунбука `monitoring.md` в том виде, в каком
> он был до трека ops-group. С 2026-09-04 агент из мониторинга выведен: уведомления
> идут в ops-группу ботом входа, дневная сводка выключена, ключ агента с прода
> снимается. Владелец переделывает агента под SMM вне репозитория. Скилл и SOUL

### Что с этим может агент

Hermes-агент владельца (зовут **Гилфойл**, профиль `oplatishka`, живёт на прежнем
бостонском VPS) знает про скрипт и имеет два **read-токена** — Loki и Sentry
(`hermes-readonly-2`, scopes `event:read/org:read/project:read`). То есть на вопрос
«как дела с инфраструктурой» отвечает по фактам, а не по памяти.

⚠️ **Скилл агента не должен дублировать факты об инфраструктуре.** Первая версия
(`skills/oplatishka-project/SKILL.md`, июль) переписывала в себя стек и адреса из
CLAUDE.md — и после двух переездов агент уверенно рассказывал про Vercel, Supabase
и squid-прокси, которых уже не было. Копия фактов устаревает молча: никто не
замечает, пока агент не ответит вслух.

Действующая версия — [`docs/history/hermes/SKILL.md`](hermes/SKILL.md) (в
репозитории, чтобы пережить следующий переезд): роль, границы, инструменты и
**ссылки на первоисточник** вместо самих фактов. Репозиторий публичный, поэтому
агент читает актуальное напрямую:

```
https://raw.githubusercontent.com/elfuerte72/oplati_podpisku/main/CLAUDE.md
https://raw.githubusercontent.com/elfuerte72/oplati_podpisku/main/docs/runbooks/monitoring.md
```

Обновляя скилл, ту же копию класть на сервер агента:
`/root/.hermes/profiles/oplatishka/skills/oplatishka-project/SKILL.md`.

**Устройство агента (2026-07-28).** Гилфойл переведён на один проект. Telegram-бот
`@hermesbymxpk_bot` обслуживается профилем `oplatishka`; прежний профиль
`default` (криптотрейдинг) остановлен, его ключи и история стёрты.

⚠️ **`default` нельзя удалить каталогом:** он физически совпадает с корнем
установки `/root/.hermes`, внутри которого лежит `profiles/oplatishka`. Удаление
корня снесло бы и рабочего агента. Чистится содержимое, а не папка.

Профиль выбирается переменной в systemd-юните шлюза
(`~/.config/systemd/user/hermes-gateway.service`, `Environment="HERMES_PROFILE=oplatishka"`);
одного бота может обслуживать только один профиль — Telegram отдаёт апдейты
одному получателю.

**Доступ агента к проду ограничен командой.** Агент живёт на бостонском сервере,
контур — во Франкфурте. У него отдельный ключ (`~/.ssh/hermes_oplatishka`), для
которого в `authorized_keys` прода прописан `command="…/oplatishka-status.sh"`:
любая присланная команда игнорируется, выполняется только сводка. Это ограничение
на стороне сервера, а не дисциплина агента — root по ssh ему не выдан намеренно.

```bash
ssh -i ~/.ssh/hermes_oplatishka root@187.124.172.104   # вернёт сводку, шелла не даст
```

⚠️ **Грабля 2026-07-28: агент и прод — на разных машинах.** Скрипт сводки лежал у
агента локально и опрашивал его собственный сервер. После переезда там осталась
только **остановленная резервная БД**, и агент доложил владельцу «база выключена
трое суток, платежи не работают» — при полностью исправном контуре (все сервисы
`1/1`, 133 заказа на месте, cron отработал 239 раз за сутки).

Ошибка правдоподобная и потому опасная: факт агент видел верно, неверным был
вывод, к какому серверу этот факт относится. Лечится не уговорами, а тем, что
смотреть больше некуда: локальный скрипт заменён обёрткой, которая ходит на прод
по ограниченному ключу, а в скилле записано прямо — локальные `docker`-команды
прод не показывают.

Полного доступа к Grafana (алёрты, uptime, дашборды) у него нет: для этого нужен
отдельный Viewer-токен, а наш `GRAFANA_SA_TOKEN` административный — им сегодня
меняли правило алёрта и contact point, отдавать его агенту нельзя.

Граница «только чтение» прописана в его `SOUL.md` и памяти. ⚠️ **Это дисциплина,
а не изоляция:** агент работает от root, поэтому технически может всё. Настоящее
ограничение — запустить его от отдельного пользователя без группы `docker`
(она равносильна root) и с узкими правилами sudo только на чтение. Запланировано
отдельной задачей, не сделано.

Права на изменение инфраструктуры через Dokploy ему **намеренно не выданы**
(решение владельца 2026-07-26):

- админский ключ Dokploy возвращает весь env приложений открытым текстом —
  боевые ключи Love&Pay и PaySpace, токен бота, пароль БД; всё это ушло бы в
  тело запроса к внешней модели при первом же вопросе про приложение;
- рядом с «перезапустить» в том же API лежат удаление приложения и перезапись
  env целиком;
- агент живёт на том же VPS, которым управлял бы: в сценарии «сервер лёг» он
  ляжет вместе с ним.

Остановить и перезапустить — руками через панель, она открывается с телефона.
Если позже понадобится дать агенту действия, делать это **не** админским ключом,
а узкими скриптами-обёртками с фиксированным набором операций, либо отдельным
пользователем Dokploy с ролью без прав `envVars` (RBAC там есть).
