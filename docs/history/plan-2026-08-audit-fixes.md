## Как пользоваться этим файлом

Одна сессия = **одна пачка** = один PR. Пачки отсортированы по риску: 1–3 —
тихая потеря денег, 4–5 — безопасность и абьюз, 6–8 — устойчивость, 9–10 —
рефералка и данные, 11–13 — тесты. Порядок можно менять, но пачку 1 стоит взять
первой: обе её находки означают, что клиент платит и остаётся без результата, а
мы об этом не узнаём.

Внутри пачки находки подобраны так, чтобы правки лежали рядом и закрывались
общим набором тестов, — это осознанно, чтобы PR оставался обозримым.

## Правила работы (действуют для КАЖДОЙ пачки)

1. **Сначала перепроверь находку по коду, потом чини.** Верификация аудита не
   опровергла ни одной находки из 45 — сигнал слабый, поэтому презумпции
   правоты у них нет. Открой указанный `file:line`, прочитай функцию целиком и
   вызывающий код. Если находка не подтверждается — **не чини**, запиши в PR,
   почему она неверна. Две находки (пачка 1) уже перепроверены вручную при сдаче
   аудита и подтверждены.
2. **Регрессионный тест обязателен на каждый фикс.** Тест должен падать на старом
   коде и проходить на новом. Без теста фикс не считается сделанным: половина
   находок — это ровно те места, где «зелёный CI при сломанном инварианте».
3. **Границы прогона.** Не ходить на прод и в боевую БД, не дёргать внешние API.
   Всё проверяется локально: `pnpm typecheck`, `pnpm --filter web test`,
   `pnpm --filter @oplati/types test`, `pnpm --filter @oplati/db test` (PGlite,
   БД не нужна).
4. **Инварианты проекта из `CLAUDE.md` не нарушать** — особенно: переходы статусов
   только через `transitionOrder()`, `order_events` append-only, деньги — целые
   в минимальных единицах, Zod на всех границах, вебхуки всегда 200 (кроме
   `/api/bot` 401), никаких `console.log` и `catch {}`, `fetch` только с таймаутом.
5. **Пайплайн.** Ветка от `main` → PR → зелёные `Tests`/`Type Check`/`Lint`/
   `Build`/`Secret Scan`/`Dependency Review` → squash. Прямой push в `main`
   закрыт ruleset'ом. Коммиты — Conventional Commits, заголовок ≤ 72 символов.
6. **Миграции.** Ни одна пачка ниже миграции не требует. Если она всё же
   понадобится — forward-only через Drizzle, и помнить: **деплой миграции не
   применяет**, это отдельный ручной шаг после мержа.
7. **`docs/CHANGELOG.md` — вести обязательно.** Запись на каждую пачку.
8. **Если фикс упирается в продуктовое решение — остановись и спроси.** Такие
   места помечены ниже как «нужно решение владельца». Не выбирать за владельца.
9. **Перед merge — `/full-review`** на ветке (скилл в репозитории). Аудит нашёл
   проблемы; ревью проверяет, что фикс их действительно закрыл и не привёз новых.
