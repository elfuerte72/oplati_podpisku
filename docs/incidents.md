# Журнал инцидентов и отложенных рисков

Операционные инциденты прода и осознанно отложенные проблемы. Правила ведения:
новый инцидент — сверху секции «Открытые», с датой, влиянием и следующим шагом;
закрытый — переносится в «Закрытые» с описанием развязки. Технические детали
кода — в CLAUDE.md/коде, здесь только операционная суть и кто что должен сделать.

Статусы: **ОТКРЫТ** (требует действия) · **ПРИНЯТ** (осознанный риск, действий не будет) · **ЗАКРЫТ**.

## Открытые

### 2026-07-25 — Автодеплой падал: VPS периодически недоступен с раннеров GitHub — ОТКРЫТ (симптом закрыт)

- **Что случилось:** деплои PR #110 (08:40 UTC) и #113 (13:07 UTC) упали с `curl exit 28` —
  TCP-соединение к `dokploy.mxpkn8ns.ru:443` не устанавливалось вовсе, все попытки подряд.
  Оба раза прод пересобирали вручную из панели.
- **Причина:** короткие эпизоды сетевой недоступности VPS со стороны раннеров GitHub
  (маршрут Azure → Hostinger). Воспроизвести по требованию нельзя: проба из Actions через
  два часа дала 5/5 на панель, 3/3 на прод-сайт и успешный `nc` на 443/80/22.
- **Опровергнуто:** первоначальное объяснение «панель не отвечает под нагрузкой собственной
  сборки» неверно — в обоих окнах сборок не шло (логи закрыты за 8 и за 5 минут до), а `sar`
  в разгар падения показал load average 0.25 при `blocked` 0. Не подтвердились также ufw,
  fail2ban, firewall Hostinger, Cloudflare и перезапуск Traefik.
- **Влияние:** прод оставался на старом коде до ручного вмешательства; при этом workflow
  завершался ошибкой, но никого не уведомлял.
- **Сделано:** `--connect-timeout 10` вместо 133-секундного системного таймаута, 10 попыток
  вместо 3, проверка факта обновления прода по `startedAt` из `/api/health` (раньше пайплайн
  заканчивался на «триггер принят» и провал сборки оставался незамеченным), алёрт о провале
  в Telegram.
- **Отдельно выяснено в тот же день:** встроенный автодеплой Dokploy (GitHub App) **не
  работает вообще** — не «иногда теряет события», как считалось. Все доставки в журнале
  App красные; Repository access = `All repositories`; эндпоинт `/api/deploy/github`
  доступен извне; секрет и ключ у Dokploy на месте. Расхождение — на проверке подписи.
  Проверено экспериментом: docs-коммит в `dev` (наш workflow его пропускает) деплоя не
  вызвал. То есть workflow — не причина проблем с деплоем, а единственное, что деплой
  вообще доставляет. **Решение владельца: App не чинить** — он деплоит без CI-гейта.
  Детали и чего нельзя делать при отключении App — в
  [`runbooks/deploy.md`](runbooks/deploy.md).
- **Сделано 2026-07-25:** подписка на события `push`/`pull_request` у App снята (журнал
  больше не красный, App не начнёт деплоить мимо гейта); доступ к коду при этом цел —
  `testConnection` по-прежнему видит 14 репозиториев, ветки читаются, сборка клонирует
  как раньше. Секреты алёрта заданы: `DEPLOY_ALERT_BOT_TOKEN` — бот
  `@oplatishkaAlert_bot` (тот же, что для алёртов Sentry), `DEPLOY_ALERT_CHAT_ID` —
  Telegram владельца, значение совпадает с `SUPPORT_OPERATOR_CHAT_ID`. Доставка
  проверена живым `sendMessage` (HTTP 200).
- **Клиенты НЕ пострадали (проверено по Better Stack 2026-07-25):** монитор
  `oplatishka.com` на 16:44 UTC показывал непрерывный uptime 22 ч 42 мин, то есть сайт
  доступен с ~18:02 UTC 24 июля — включая оба окна падения деплоя. Проверка идёт каждые
  5 минут, окно 13:08–13:16 монитор бы застал. Значит недоступен был только маршрут
  «раннеры GitHub → VPS», а не VPS вообще.
- **Третий эпизод в тот же день, 17:15–17:24 UTC** (на мерже PR #117). Новая обвязка
  отработала полностью: 10 попыток, честный красный статус, алёрт в Telegram доставлен
  (`HTTP 200`). Ручной перезапуск в 17:29 прошёл с первой попытки, прод обновился.
  **Ключевое наблюдение:** шаг снятия состояния записал `startedAt=<нет ответа>` — раннер
  не достучался и до самого сайта, не только до панели. То есть с сети GitHub недоступен
  ВЕСЬ VPS, а Better Stack (проверяет из Европы) в это время видел сайт живым. Значит
  эпизоды привязаны к маршруту из сети раннеров, а не к состоянию VPS.
- **Хронология эпизодов 2026-07-25** (для сравнения, если повторится): 08:40–08:42,
  13:08–13:16, 17:15–17:24 — то есть 8–10 минут каждый. Текущее окно ретраев ~9 минут,
  в третьем эпизоде его чуть не хватило.
- **Решение владельца 2026-07-25: пока не трогать.** Автозапуск деплоя на мерж остаётся
  (обсуждались варианты «ручной запуск в Actions» и «только кнопка в панели Dokploy» —
  отклонены: кнопка в панели теряет гарантию «выкачено то, что протестировано», проверку
  результата и алёрт). Наблюдаем неделю; если эпизоды участятся или удлинятся — возвращаемся
  к self-hosted runner на VPS (см. [`BACKLOG.md`](BACKLOG.md)) с данными на руках.

### 2026-07-22 — Сайт недоступен из РФ без VPN (блокировка Vercel + дроссель Cloudflare) — ОТКРЫТ (beta-решение готово)

- **Что случилось:** РКН/ТСПУ блокирует IP-диапазоны Vercel, а Cloudflare у мобильных
  операторов РФ (проверено на Мегафоне) дросселирует — соединение обрывается после
  ~16 КБ: HTML сайта доходит, CSS/JS режется, сайт «голый» и не работает. Затронут и
  Mini App `/cabinet` (тот же домен).
- **Что пробовали и НЕ помогло:** Cloudflare оранжевое облако + выключение ECH (через
  API, на Free-плане переключателя в UI нет) + выключение HTTP/3 — Мегафон всё равно не
  открывает. Вывод: сам Cloudflare под дросселем, CF-проксирование задачу не решает.
- **Что помогло (beta):** reverse-proxy через российский VPS Timeweb
  (`104.171.133.70`, Москва) — `beta.oplatishka.com` открывается с телефона без VPN со
  стилями. Цепочка `Traefik(443,TLS) → Caddy-sidecar → Vercel`; реальный IP клиента
  доходит в `X-Client-IP` (для rate-limit). Прод (`www`/apex) НЕ переключён — идёт
  напрямую на Vercel, ничего не сломано.
- **Влияние:** пользователи РФ без VPN не открывают сайт/кабинет. ЦА в основном с VPN
  (покупают зарубежные сервисы), весь фулфилмент в Telegram, поэтому прод не аварийно —
  но владелец считает доступность сайта из РФ принципиальной.
- **Следующий шаг (владелец + разработка):** перевести прод на Timeweb-прокси по ранбуку
  в [`BACKLOG.md`](BACKLOG.md) (webhook L&P увести на `*.vercel.app`, задать
  `PROXY_SHARED_SECRET`, смёржить PR #92, добавить маршруты www/apex, переключить DNS,
  смоук e2e). Открытые хвосты: снять `alt-svc h3` на нашем маршруте; внешний
  uptime-мониторинг Timeweb-VPS (новая точка отказа сайта из РФ).
- **Юридически (не консультация):** reverse-proxy собственного незаблокированного сайта
  на VPS — не «обход блокировок» по ст. 15.8 149-ФЗ; оферта Timeweb Cloud VPS прокси
  своего сайта не запрещает (в отличие от их виртуального хостинга); владелец «только
  свои сайты» — не провайдер хостинга (реестр РКН не требуется). Отдельный, более
  чувствительный риск — VPN-кнопка бота (реклама средств обхода, штрафы с 09.2025) —
  сайта/домена не касается, обсудить с юристом.

### 2026-07-14 — `t.me` исключён из глобального DNS, Telegram deep-links недоступны — ОТКРЫТ (смягчено)

- **Что случилось:** реестр `.me` выставил домену `t.me` статус `serverHold`; публичные
  DNS-резолверы отвечают `NXDOMAIN`. В браузерах перестали открываться все ссылки на бота,
  Mini App, канал и реферальные приглашения. Сам Telegram и Bot API продолжают работать.
- **Влияние:** новые пользователи не доходят до `/start ref_<code>`, поэтому реферер не
  фиксируется; также нарушены привязка Telegram с сайта и входы в Mini App через браузер.
- **Смягчение:** все генерируемые приложением HTTPS deep-links переведены на официальный
  alias `telegram.me`; payload-форматы `ref_`, `link_` и `startapp` не менялись.
- **Следующий шаг:** после восстановления `t.me` не откатывать alias автоматически;
  отдельно решить, нужны ли постоянные ссылки через домен `oplatishka.com`.

### 2026-07-03 — ORD-93RQE: оплата принята, карта не пополнена (Insufficient VCC balance) — ОТКРЫТ

- **Что случилось:** клиент thomas оплатил App Store $20 (2 002 ₽, 15:41 UTC), вебхук L&P
  принял платёж, но топап карты упал: `PaySpaceApiError: Insufficient balance on VCC
  subaccount` → заказ в `failed`. Деньги приняты, услуга не оказана. Рядом — постоянный
  алёрт `vcc_balance.low` (148 событий за ~2 недели, порог $50).
- **Смягчение:** у клиента уже есть активная карта с реквизитами (получасом раньше
  успешно купил YouTube Premium, ORD-DJV61) — его App Store-заказ это топап той же карты.
- **Действия (владелец):**
  1. Пополнить VCC-субаккаунт PaySpace — СРОЧНО (пополнение с крипто-баланса T+1 + ~3% fee).
  2. После пополнения вручную топапнуть карту клиента на $20 + буфер (PaySpace-кабинет)
     или решить возврат 2 002 ₽.
  3. Учесть: авто-recovery заказ в `failed` не подхватывает (poll-payment поднимает только
     зависшие `paid`).
- **Связь с клиентом:** новый бот не может написать ему первым (см. инцидент про переезд
  бота ниже) — либо дождаться его Start/обращения в поддержку, либо исполнить молча
  (реквизиты карты у него уже есть).

  может повториться.
- **Действие (владелец):** проверить Vercel → Settings → Billing / Spend Management,
  найти причину паузы и убрать её (лимит расходов / способ оплаты).

## Принятые риски

### 2026-07-18 — GitHub→Vercel вебхук потерял merge в main: прод не задеплоился — ПРИНЯТ (смягчено)

- **Что случилось:** после squash-мержа PR #83 (`2d7e533`) Vercel не создал Production-деплой —
  событие push не дошло до GitHub App Vercel. Все предыдущие мержи в main (включая docs-only
  PR #82 тем же утром) деплоились автоматически — сбой разовый. Даунтайма не было: прод
  продолжал обслуживать предыдущий билд.
- **Развязка:** прод задеплоен вручную `vercel deploy --prod` с актуального `main`;
  `www.oplatishka.com` отдаёт новый билд, смоук (`/api/health`, `/api/catalog`) зелёный.
- **Смягчение (операционная привычка):** после каждого мержа в `main` проверять появление
  Production-деплоя (`vercel ls` или дашборд). При повторении — переподключить Git-интеграцию
  (Vercel → Settings → Git → Disconnect/Connect) и/или завести Deploy Hook как запасной триггер.

### 2026-07-03 — Клиенты старого бота недостижимы для сообщений — ПРИНЯТ

- Прод-бот переехал `@test_prodipsa_bot` → `@oplatishkaa_bot` (смена токена), старый бот
  удалён из BotFather. Новый бот не может написать первым клиентам, которые не нажали
  у него Start: чеки, реквизиты карт и уведомления об оплате им не доставятся.
- Рассылка «мы переехали» со старого бота невозможна (бот удалён). Клиенты
  восстанавливаются сами: все ссылки сайта/mini app ведут на нового бота.
- Держать в голове при ручном фулфилменте старых клиентов (см. ORD-93RQE).

### 2026-07-03 — Токен нового бота засвечен в чате сессии — ПРИНЯТ

- Токен `@oplatishkaa_bot` был отправлен владельцем в чат Claude Code. Ротация предложена,

### 2026-07-03 — Месячный тариф Telegram Premium скрыт с витрины — ПРИНЯТ (до решения)

## Закрытые

### 2026-07-19 — Ложные алёрты «прокси L&P не отвечает» всю ночь — ЗАКРЫТ

- **Что случилось:** с 23:55 до 01:20 UTC (и разово в 03:05) healthcheck прокси
  считал squid лежащим — 19 событий `lnp_proxy.down`, владельцу пришло 3 DM
  «КРИТИЧНО». VPS при этом работал: 18 из 19 ошибок — `redirect count exceeded`
  (origin `loveandpay.io` стал отвечать на корень 307-цепочкой, fetch ходил по
  редиректам до лимита), 1 — таймаут той же цепочки. Каждый redirect-ответ
  приходил ЧЕРЕЗ прокси, т.е. транспорт был жив — алёрты ложные.
- **Влияние:** только шум в личке владельца; платежи не страдали (ночью
  трафика не было, сам прокси работал).
- **Развязка:** healthcheck переведён на `redirect: 'manual'` — любой
  HTTP-ответ (включая 3xx) = прокси жив; регресс-тест в proxy-health.test.ts.
  Дедуп DM остаётся best-effort (in-memory на warm-инстансе) — 3 DM за ночь
  вместо одного это его известное ограничение, принято.

### 2026-07-03 — Мобильная привязка Telegram не доводила до бота — ЗАКРЫТ (PR #57)

- Токены привязки выпускались, но не потреблялись (`link_tokens.used_at IS NULL`):
  `window.open` + JS-редирект не открывал приложение Telegram на iOS/in-app-браузерах.
- Фикс: предвыпуск токена + прямая `<a href="t.me/...">` + handoff заказа в бота после
  привязки + идемпотентный repeat_confirm. Подтверждено живым тестом с телефона.
