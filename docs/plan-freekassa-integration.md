## Отклонения от этого ТЗ, принятые при реализации

1. **Гейт ключей в `lib/env.ts` — односторонний.** ТЗ (этап 3) требовало
   проверять ключи ОБОИХ провайдеров. Симметричная проверка сломала бы dev-стенд:
   там платёжных ключей нет намеренно, а `PAYMENT_PRIMARY_PROVIDER` не задан и
   берёт дефолт `loveandpay` — приложение просто перестало бы стартовать.
   Проверяются только ключи Freekassa: это значение задаётся руками и только на
   проде.
2. **Гасить чужой pending-инвойс через `claimPaymentTerminal` не потребовалось.**
   Заказ с живым платежом уже имеет статус `pending_payment`, поэтому
   `payments/create` уходит в ветку идемпотентного ответа и отдаёт рабочую ссылку
   прежнего шлюза (его вебхук намеренно продолжает принимать деньги). Кода без
   достижимого сценария не добавлено.
3. **Пол витрины остался привязан к `LOVEANDPAY_MIN_AMOUNT_RUB`.** Иначе смена
   провайдера меняла бы состав каталога как побочный эффект (например, вернулся
   бы скрытый месячный тариф Telegram Premium) — это продуктовое решение, а не
   техническое следствие.
4. **Реальный IP клиента для веб-заказов не пробрасывается** — шлём
   `FREEKASSA_FALLBACK_IP` всегда. `payments/create` вызывается внутренним
   self-call'ом, заголовков клиента там нет, а протаскивание IP через
   `confirmOrder` затрагивало бы три точки входа.
5. **Поиск платежа по уведомлению имеет запасной путь** по `MERCHANT_ORDER_ID`:
   равенство `intid` возвращённому `orderId` докой не гарантировано. Срабатывание
   запасного пути алертится — это и есть способ закрыть вопрос по факту.

## 1. Зачем и в какой роли

L&P периодически не принимает оплаты, и клиенты уходят.

**⚠️ Роли поменялись местами 2026-07-26 (решение владельца).** Заводилось как
«Freekassa = запасной канал»; теперь наоборот:

| | Провайдер | Роль |
|---|---|---|
| Основной | **Freekassa** | принимает рубли в обычном режиме |
| Резерв | **Love&Pay** | включается, если Freekassa недоступна |

**Решения владельца:**

| Вопрос | Решение |
|---|---|
| Способ подключения | **Строго API, не SCI-форма** (2026-07-26) |
| Роль | **Переключатель провайдера в env.** `PAYMENT_PRIMARY_PROVIDER` задаёт, кто принимает деньги; смена значения + перезапуск контейнера, без правок кода и релиза |
| Цена клиенту | **Одна, маржа плавает.** Комиссии провайдеров разные, но клиент платит ровно ту сумму, что зафиксирована при заказе; разница съедается маржой (30%) |
| Что на проде сейчас | Только L&P. Freekassa включается отдельным решением после смоука |

**Почему Freekassa делается вперёд смоука L&P на новой инфраструктуре.** У L&P с
2026-07-25 сломана касса на их стороне (обещают починить 27-го), поэтому сквозной
платёж на Dokploy-контуре ещё ни разу не проходил. Ждать нечего — Freekassa пишется
параллельно, а смоук L&P проводится, когда их касса оживёт.

**Почему переключатель, а не авто-fallback по `503`.** Детектор
`isPaymentProviderUnavailable` реагирует только на транспорт: таймаут, 5xx, лежащий
прокси. Ситуация «L&P исправно выдаёт ссылку, а платежи у клиентов не проходят» для
нашего кода выглядит полным успехом — авто-fallback не сработает, клиент всё равно
уйдёт. Ровно этот случай и наблюдался. Автоматика поверх переключателя может быть
добавлена позже, но она не заменяет ручной рычаг.

## 3. Предусловия: что настроить в кабинете Freekassa

**Это делает владелец до начала разработки.** Без этих значений писать нечего.

### 3.1 Получить и передать (в env, не в репозиторий)

| Что | Куда потом | Зачем | Статус |
|---|---|---|---|
| API-ключ (страница настроек ЛК) | `FREEKASSA_API_KEY` | ключ HMAC-подписи запросов к API | ✅ задан в env прода Dokploy + локальный `.env` (2026-07-26) |
| Секретное слово 2 | `FREEKASSA_SECRET_WORD_2` | проверка подписи входящего уведомления | ✅ задан там же (2026-07-26), значение сверено побайтово по хешу |
| Секретное слово 1 | `FREEKASSA_SECRET_WORD_1` | только для SCI-формы, кодом **не читается** | ✅ задан про запас |
| `shopId` (ID магазина) | `FREEKASSA_SHOP_ID` | обязательный параметр каждого запроса | ⏳ **пусто — ждёт активации кабинета** |

**На dev-стенде этих ключей быть НЕ должно** — та же причина, по которой там нет
ключей L&P и PaySpace: тестовый заказ выставил бы реальный счёт. Проверено 2026-07-26:
на `oplatishka-web-dev` записей `FREEKASSA_*` нет.

#### Все переменные окружения интеграции — одним списком

Значений здесь нет и быть не может: репозиторий публичный. Секреты живут в env
приложения `oplatishka-web` (Dokploy) и в корневом `.env` для локальной разработки —
оба места gitignored/вне репозитория.

| Переменная | Кто задаёт | Есть сейчас | Читается кодом |
|---|---|---|---|
| `FREEKASSA_API_KEY` | владелец | да | подпись запросов к API |
| `FREEKASSA_SECRET_WORD_2` | владелец | да | проверка подписи вебхука |
| `FREEKASSA_SECRET_WORD_1` | владелец | да | **нет** — только для SCI, лежит про запас |
| `FREEKASSA_SHOP_ID` | владелец | **нет, ждёт активации** | обязательный параметр запроса |
| `FREEKASSA_FALLBACK_IP` | разработка | нет | `177.7.34.106`, когда IP клиента неизвестен |
| `PAYMENT_PRIMARY_PROVIDER` | разработка | нет | `freekassa` \| `loveandpay`, дефолт `loveandpay` |

Локально (`.env`) заданы `FREEKASSA_API_KEY`, `FREEKASSA_SECRET_WORD_1`,
`FREEKASSA_SECRET_WORD_2` — то есть подпись можно писать и проверять сразу; упирается
всё только в `shopId`. Имена новых переменных добавить в `.env.example` (без значений).

⚠️ **Смена env в Dokploy применяется только при следующем деплое или reload'е.**
Секретные слова записаны в конфигурацию прода, но работающий контейнер их пока не
видит — и не должен, кодом они ещё не читаются. Отдельный перезапуск прода ради
неиспользуемых значений не делался.

⚠️ **Грабля, снятая экспериментом (2026-07-26).** Секретное слово 2 содержит `$`, `{`,
`[`. Классический риск: панель или docker подставят `$` + буквы как имя переменной либо
оставят кавычки внутри значения — и подпись вебхука перестанет сходиться, причём молча.
Проверено на dev-стенде пробником той же формы: **Dokploy не интерполирует `$` и
снимает одинарные кавычки**, значение доходит байт в байт. Писать можно как есть, без
экранирования. Если появится третий способ доставки env (compose-файл, CI) — проверять
заново, там правила другие.

Активация магазина на 2026-07-26 — **в процессе**. URL'ы в форме активации заданы:
оповещение `https://www.oplatishka.com/api/payments/freekassa` (POST), успех
`/payment-success`, отказ — главная. ⚠️ Эндпоинта оповещения в коде ещё нет: если
Freekassa проверяет его доступность, проверка не пройдёт, пока не сделан этап 2.

Секретное слово 1 нужно только для SCI-формы — **мы её не используем**, интеграция
строго через API.

### 3.2 Настроить в интерфейсе

1. **URL оповещения (webhook)** → `https://www.oplatishka.com/api/payments/freekassa`.
   Метод — **POST** (в ЛК выбирается GET или POST; фиксируем POST, чтобы не разбирать
   два формата).
2. **Включить проверку подтверждения**, если такая опция есть: тогда обработчик обязан
   ответить телом `YES`.
3. **Способы оплаты (`i`)** — включить как минимум `44` (СБП по QR) и `36` (карты РФ).
   Терминология Freekassa путает: в доке `i` называется «валютой платежа», хотя это
   именно способ оплаты.
4. **Allowlist IP для API**, если провайдер его требует, — задекларировать
   `177.7.34.106`. После переезда на Dokploy egress фиксирован, поэтому отдельный
   прокси (как squid для L&P) **не нужен**.
5. **URL успеха/неудачи** — если провайдер требует их в настройках магазина, а не в
   запросе: успех `https://www.oplatishka.com/payment-success`.

### 3.3 Проверить

- Магазин прошёл проверку владения ресурсом (баннер на главной).
- Договор/тарифы: **какая комиссия по СБП и по картам** — от этого зависит, насколько
  просядет маржа при переключении (решение «цена одна» означает, что просадку несём мы).

## 4. Контракт провайдера

> **Правило проекта: доки провайдеров врут.** Так было с L&P (тестовая панель кабинета
> шлёт фейковый формат событий) и с PaySpace (суммы то строкой, то числом, `exp_date`
> в `MM/YY`). Ниже — то, что написано в документации; **каждый пункт подтверждается
> живым вызовом на копеечной сумме и записывается в `docs/reference/freekassa-api.md`
> с фактическими ответами.**

### 4.0 Где документация (проверено 2026-07-26)

Живой домен ровно один — **<https://docs.freekassa.net/>**. `docs.freekassa.com`,
`docs.fk.life` и `freekassa.com/docs` не отвечают вообще (не редирект — соединение не
устанавливается), так что ссылку в сторонних статьях не использовать.

Нужные разделы (нумерация как в самой доке):

| Раздел | О чём |
|---|---|
| **1.3. Настройка формы оплаты** | параметры SCI-формы: `m`, `oa`, `currency`, `o`, `s` + опциональные `i`, `em`, `phone`, `lang`, `us_key` |
| **1.5. Формирование подписи в платёжной форме** | `MD5("ID магазина:Сумма:секретное слово 1:Валюта:Номер заказа")` |
| **1.4. Оповещение о платеже** | параметры webhook'а и список IP отправителя |
| **1.7. Формирование подписи в скрипте оповещения** | `MD5("ID магазина:Сумма:секретное слово 2:Номер заказа")` |
| **2.2. Подпись запросов** | `HMAC-SHA256` по отсортированным значениям — это уже про API, не про SCI |
| **Создать заказ и получить ссылку на оплату** | `POST /orders/create`, там же рекуррентные платежи |

**Два разных способа подключения — не путать.** Провайдер даёт их параллельно, и
секретных слова поэтому два:

1. **SCI-форма** — браузер клиента отправляется на `https://pay.fk.money/` с полями
   формы; подпись MD5 по **секретному слову 1**. Просто, но платёж инициирует
   фронтенд, а нам нужен серверный контроль суммы и статуса.
2. **API** (`https://api.fk.life/v1/`) — сервер сам создаёт заказ и получает ссылку;
   подпись HMAC-SHA256 по **API-ключу**. **Мы идём этим путём** — он совпадает с
   моделью L&P, где инвойс создаёт наш сервер.

**Секретное слово 2 нужно в обоих случаях** — им подписывается входящее уведомление,
а уведомление приходит независимо от способа создания заказа. Секретное слово 1 при
API-интеграции не используется вовсе, но пусть лежит в env: переход на SCI-форму как
запасной вариант не потребует беготни по кабинету.

### 4.1 Запросы к API — подтверждено докой

- Базовый URL `https://api.fk.life/v1/`, формат JSON.
- Подпись: значения параметров сортируются **по ключам** в алфавитном порядке,
  склеиваются через `|`, затем `HMAC-SHA256(строка, api_key)`; результат кладётся в
  поле `signature`.
- `createOrder` — обязательные `shopId`, `nonce`, `signature`, `paymentId`; далее
  `i` (способ оплаты), `email`, `ip`, `amount`, `currency`.
- Ссылка на оплату приходит в ответе (в поле `location`) — её отдаём клиенту.

**⚠️ `nonce` обязан монотонно возрастать** («всегда больше предыдущего»). Это состояние,
которого у нас пока нет ни у одного провайдера. Простейшее решение — миллисекундный
timestamp; при двух параллельных запросах в одну миллисекунду значения совпадут,
поэтому нужен либо счётчик в БД, либо монотонный источник с гарантией уникальности.
Решить до реализации — это единственное место, где интеграция не копирует L&P.

### 4.2 Наши данные в запросе

- `email` — реальный адрес либо `<telegram_id>@telegram.org`. У нас `telegram_id` есть
  **всегда**: оплата без привязки Telegram запрещена гейтом `TelegramLinkRequiredError`.
- `ip` — **`127.0.0.1` блокируется провайдером.** Для заказов из Mini App и бота IP
  клиента отсутствует, поэтому отправляем публичный IP сервера — завести
  `FREEKASSA_FALLBACK_IP` (значение `177.7.34.106`), а для веб-заказов брать
  `getClientIp` и слать серверный только когда он `unknown`.

### 4.3 Уведомление (webhook) — подтверждено докой

- Приходит GET или POST form-data (задаётся в ЛК; фиксируем POST).
- Параметры: `MERCHANT_ID`, `AMOUNT`, `intid`, `MERCHANT_ORDER_ID`, `P_EMAIL`,
  `P_PHONE`, `CUR_ID`, `SIGN`, `payer_account`, `commission`, `us_*`.
- Подпись: `MD5("MERCHANT_ID:AMOUNT:секретное слово 2:MERCHANT_ORDER_ID")`.
- Обработчик отвечает телом `YES`.
- Документация рекомендует сверять IP отправителя: `168.119.157.136`,
  `168.119.60.227`, `178.154.197.79`, `51.250.54.238`. **Проверить список у провайдера
  перед выкаткой** — молчаливая смена их адресов положит приём платежей.

**Следствия для нашей архитектуры (важное):**

1. В подписи нет ни времени, ни nonce → уведомление **воспроизводимо**, ровно как у
   L&P. Защита та же: атомарный `claimPaymentSucceeded` (инвариант 2), а не проверка
   подписи.
2. `intid` — идентификатор платежа на стороне провайдера → это `provider_ref` в
   `payments`, он же ключ `UNIQUE(provider, provider_ref)`.
3. `AMOUNT` придёт строкой с дробной частью, а у нас деньги — целые копейки
   (инвариант 3). Конвертация через parseFloat запрещена: разбирать строку и сверять
   точно, иначе рубль-в-копейку разъедется и `amount_mismatch` начнёт врать.
4. Ответ `YES` не противоречит инварианту 6 — это `200 OK` с телом `YES`.

## 5. Работы

### Этап 1 — контракт и клиент

- Миграция **отдельным файлом**: `ALTER TYPE payment_provider ADD VALUE 'freekassa'`.
  В Postgres добавленное значение нельзя использовать в той же транзакции, где оно
  объявлено, а мигратор оборачивает миграцию в транзакцию — смешаешь с DML, и
  `db:migrate` упадёт на проде.
- Zod-схемы запроса/ответа в `@oplati/types` (`freekassa.ts`).
- `apps/web/lib/freekassa/`: `client.ts` (создание заказа, `fetch` строго с
  `AbortController`), `sign.ts` (HMAC-SHA256 для API + MD5 для проверки уведомления),
  `errors.ts`, `availability.ts` — по образцу `lib/loveandpay/`.
- **Живой вызов на минимальной сумме**, фактические ответы — в
  `docs/reference/freekassa-api.md`.

### Этап 2 — webhook

`app/api/payments/freekassa/route.ts`:

- Zod на теле (инвариант 5), проверка подписи, сверка IP отправителя с allowlist.
- Всегда `200` (инвариант 6), тело `YES` при успехе.
- Успех: `claimPaymentSucceeded` + `transitionOrder(paid)` **в одной транзакции**
  (сбой перехода обязан откатывать claim — иначе оплаченный заказ застрянет без
  recovery), затем реферальное начисление и выпуск карты, как у L&P.
- Недоплата: терминальный путь `amount_mismatch` + ровно один DM владельцу через
  `claimPaymentTerminal`.
- Выравнивание `orders.expires_at` по TTL инвойса Freekassa (`setOrderExpiresAt`);
  TTL у провайдеров разный — не копировать `INVOICE_TTL_HOURS` вслепую.

### Этап 3 — переключатель провайдера (разобрано 2026-07-26)

#### Имя и форма переменной

```
PAYMENT_PRIMARY_PROVIDER = freekassa | loveandpay        # дефолт в коде: loveandpay
```

Владелец предлагал булев `FREEKASSA_ACTIVE=true|false`. **Рекомендация — строковый
enum**, и вот почему конкретно:

1. **Булев легко задать так, что он молча не сработает.** В обсуждении переменная была
   записана как `FREEKASSA_ACTIVE = True` — по-питоновски, с заглавной. Наивная проверка
   `value === 'true'` прочитает это как «выключено», и деньги пойдут через другой шлюз
   без единой ошибки в логах. Строковый enum через `z.enum(['freekassa','loveandpay'])`
   на опечатке **падает при старте**, а не тихо меняет поведение.
2. **Читаемость дежурного.** В аварийной ситуации нужно за секунду понять, кто сейчас
   принимает деньги. `PAYMENT_PRIMARY_PROVIDER=freekassa` отвечает на этот вопрос
   прямо; `FREEKASSA_ACTIVE=false` требует помнить, кто «второй».
3. **Третий провайдер.** Булев превращается в набор флагов с бессмысленными
   состояниями («оба активны», «оба выключены»). Enum расширяется значением.

Дефолт `loveandpay` — намеренно: он проверен живыми деньгами. Потеряется env — контур
вернётся к известному рабочему состоянию, а не к неопробованному.

#### Гейт «выбран провайдер — обязаны быть его ключи»

В `lib/env.ts` добавить `superRefine`: при `PAYMENT_PRIMARY_PROVIDER=freekassa`
обязательны `FREEKASSA_API_KEY`, `FREEKASSA_SHOP_ID`, `FREEKASSA_SECRET_WORD_2`; при
`loveandpay` — ключи L&P. Иначе неизбежен сценарий «переключили флаг, забыли ключ» —
и узнаем об этом от первого клиента, а не от валидации.

#### Что переключатель меняет, а что НЕ меняет — критично

| | Зависит от флага? |
|---|---|
| Создание **нового** инвойса (`payments/create`) | **да** — единственное место |
| Вебхук `/api/payments/freekassa` | **нет, работает всегда** |
| Вебхук `/api/payments/loveandpay` | **нет, работает всегда** |
| `poll-payment` (добор потерянных уведомлений) | **нет** — опрашивает по `payments.provider` каждой строки |

**Почему вебхуки нельзя гейтить флагом.** В момент переключения у части клиентов уже
выставлены счета прежнего провайдера. Если закрыть его вебхук, их оплаты не будут
приняты: деньги у клиента списаны, заказ висит неоплаченным. Правило простое:
**флаг решает, кому отдавать новые платежи, и никогда — чьи деньги принимать.**

#### Ограничение «один живой счёт на заказ»

Частичный индекс `UNIQUE(order_id) WHERE status='pending'` не даёт держать два живых
инвойса. Следствие: если у заказа уже есть pending-платёж прежнего провайдера, перед
созданием нового надо перевести старый в `failed` через `claimPaymentTerminal`.

На практике окно небольшое — счёт живёт 1 час (`INVOICE_TTL_HOURS`), — но клиент,
попавший в него, увидит «оформи заказ заново». Вписать в рунбук переключения.

#### Как выглядит переключение вживую

1. В Dokploy поменять значение переменной у приложения `oplatishka-web`.
2. Нажать Redeploy (или `application.reload`) — **контейнер перезапускается, это
   полторы-две минуты**, мгновенного рубильника нет.
3. Убедиться по `/api/health` (`startedAt` обновился) и создать пробный заказ.

Автоматического переключения по `503` нет и не планируется на первом этапе: детектор
`isPaymentProviderUnavailable` ловит только транспорт (таймаут, 5xx), а самый частый
реальный случай — «шлюз отвечает 200, но платежи у клиентов не проходят» — для кода
выглядит успехом.

#### Прочее

- Тексты клиенту не называют провайдера — «Оплатить 2 490 ₽» одинаково для обоих.
- Имя провайдера пишется в `payments.provider` при создании строки, а не выводится из
  флага задним числом: иначе после переключения история платежей начнёт врать.

### Этап 4 — подстраховка и наблюдаемость

- `poll-payment` сегодня опрашивает только L&P: потерянное уведомление Freekassa никто
  не дожмёт, а это единственная страховка от зависшего платежа. Сделать цикл
  провайдер-агностичным (по `payments.provider`), а не копировать джоб.
- Метрика конверсии «инвойс выставлен → оплачен» по провайдерам. Сейчас её нет, и
  именно поэтому о неработающих оплатах L&P узнали от клиентов. Без неё переключатель
  нечем дёргать вовремя.

### Этап 5 — тесты

По образцу `lib/loveandpay/*.test.ts`:

- подпись API (сортировка ключей, склейка через `|`) и подпись уведомления (MD5);
- разбор `AMOUNT` в копейки, включая дробные и «ровные» суммы;
- идемпотентность повторного уведомления (PGlite);
- терминальная недоплата + дедуп DM;
- route-тест `payments/create` на выбор провайдера по флагу и на смену провайдера при
  живом pending-инвойсе;
- `nonce` монотонен при параллельных вызовах.

## 6. Выкатка

1. Ключи в env dev-приложения **не задаём** — на dev намеренно нет платёжных ключей,
   иначе тестовый заказ выставит реальный счёт.
2. Код выкатывается на прод **с флагом `loveandpay`** — до живой проверки Freekassa
   ничего не меняется для клиентов.
3. Как активируют кабинет: внести `FREEKASSA_SHOP_ID`, переключить флаг на `freekassa`,
   redeploy.
4. Смоук на проде минимальной суммой: заказ → ссылка → оплата → уведомление → `paid`
   → выпуск карты → реквизиты в Telegram. Проверить `payments.provider='freekassa'`
   и что сумма в копейках сошлась точно.
5. Смоук прошёл — оставляем `freekassa` основным (целевое состояние). Сорвался —
   возвращаем `loveandpay` и разбираемся без спешки.

⚠️ **Осознанный риск смены ролей.** L&P проверен живыми деньгами, Freekassa — ни одним
платежом. Разумный порядок: сначала прогнать через Freekassa несколько реальных
заказов, и только потом делать её основной. Если владелец решит иначе (например,
из-за поломки кассы L&P) — решение его, но зафиксировать, что первый же дефект
непроверенного контракта встретит весь поток, а не один тестовый заказ.

## 7. Открытые вопросы

- ~~Как гарантировать монотонность `nonce`~~ — **предложение: последовательность
  Postgres.** `CREATE SEQUENCE freekassa_nonce`, значение берётся `nextval`. Она
  монотонна при любой параллельности и переживает перезапуск; пропуски (гэпы) при
  откате транзакции допустимы — провайдер требует «больше предыдущего», а не «без
  дырок». Timestamp в миллисекундах не годится: два одновременных запроса дадут одно
  значение. Утвердить при реализации.
- ~~**Комиссии Freekassa по СБП и картам**~~ — **решение владельца 2026-07-26:
  наша наценка остаётся 30% независимо от шлюза** (`COMMISSION_PERCENT=30`), цена
  клиенту не меняется. Разницу в комиссии провайдеров съедает маржа — это принято
  осознанно. Узнать их тариф всё равно стоит (для планирования, не для кода).
- **Актуален ли список IP уведомлений** — сверить с провайдером перед выкаткой.
- **Нужен ли allowlist IP на их стороне** для запросов к API (в доке не упомянут).
- ~~**Способ оплаты `i`**~~ — **решено:** шлём один, по умолчанию `44` (СБП),
  значение меняется переменной `FREEKASSA_METHOD_ID`; `sbp`→44, `card`→36, если
  канал передал способ явно. Выбора в интерфейсе нет.
- ~~Кнопка «оплатить другим способом»~~ — **решение владельца 2026-07-26: её не
  будет.** Не планировать и не возвращаться к этому.

## 8. С чего начать (для новой сессии)

**Что прочитать до первой строки кода:**

1. `CLAUDE.md` — раздел «Архитектурные инварианты», особенно 2 (идемпотентность
   вебхуков), 3 (деньги целыми копейками), 5 (Zod на границах), 6 (вебхук всегда 200).
2. `apps/web/lib/loveandpay/` целиком — это эталон, который копируется по структуре:
   `client.ts`, `sign.ts`, `handlers.ts`, `availability.ts` + их тесты.
3. `apps/web/app/api/payments/loveandpay/route.ts` и `create/route.ts` — как устроены
   транзакционная связка claim + переход и гейт `order_expired`.
4. Разделы 4 и «Этап 3» этого файла.

**Порядок работ** (этапы 1–5 выше): миграция enum → типы и клиент → вебхук →
переключатель → подстраховка/наблюдаемость → тесты. Этапы 1–3 можно делать до
активации кабинета целиком; блокируется только живая проверка контракта.

**Что считается сделанным:**

- `pnpm typecheck`, `pnpm lint`, `pnpm --filter web test` зелёные;
- вебхук идемпотентен под повтором (тест на PGlite), недоплата терминальна, DM ровно
  один;
- переключатель проверен route-тестом в обе стороны, вебхук прежнего провайдера при
  этом продолжает принимать деньги;
- в `docs/reference/freekassa-api.md` лежат **фактические** ответы провайдера, а не
  пересказ доки;
- имена новых переменных добавлены в `.env.example` (без значений);
- запись в `CHANGELOG.md`, этот файл переехал в `docs/history/`.

**Где вести работу.** Ветка `feature/freekassa` (создана 2026-07-26 от накопительной
docs-ветки) — в ней уже лежат это ТЗ и обновлённый бэклог. Работать в ней, а `main`
получит и спеку, и код **одним PR по готовности**. Отдельного PR ради документации
не делаем: `main` защищён ruleset'ом (прямой push запрещён), и гонять через него файл,
который всё равно поедет вместе с кодом, — лишний шаг.

**Чего не делать:**

- не включать Freekassa основной до живого смоука;
- не гейтить вебхуки флагом (см. «Этап 3»);
- не парсить `AMOUNT` через `parseFloat` — только точный разбор строки в копейки;
- не переиспользовать `INVOICE_TTL_HOURS` от L&P вслепую — у провайдеров разный срок
  жизни счёта;
- не верить доке без живого вызова: на этом проекте она врала дважды (L&P, PaySpace).
