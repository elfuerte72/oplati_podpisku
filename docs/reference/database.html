1 Что такое БД на самом деле

Не «магия в облаке», а очень дисциплинированный Excel.

База данных — это набор таблиц. Каждая таблица хранит один тип сущностей: одна таблица — про клиентов, другая — про заказы, третья — про платежи. Внутри таблицы данные лежат строками, как в Excel-листе. Разница с Excel в трёх вещах, и именно они делают БД базой:

1. Строгие правила

Колонка «сумма» обязана быть целым числом. Нельзя случайно вписать туда текст. БД отказывает в записи, которая нарушает правила. В Excel — пиши что хочешь.

2. Связи между таблицами

Заказ ссылается на клиента, а не копирует его имя. Поменял имя в одном месте — оно верное везде. Это называется «реляционность».

3. Быстрый поиск

Найти заказ среди миллиона строк — миллисекунды, а не «прокрутить весь лист». За это отвечают индексы.

4. Надёжность изменений

Несколько изменений выполняются как одно неделимое целое: либо всё, либо ничего. Это транзакции — про них ниже.

Аналогия с Python. Таблица — это list[dict] (или DataFrame): список одинаково устроенных записей. Строка — один dict. Колонка — ключ словаря с зафиксированным типом значения. БД — это такой list[dict], который сам следит за типами, умеет мгновенно искать и не даёт двум процессам испортить данные одновременно.

Конкретно у вас — PostgreSQL 17, который крутится на Supabase (это хостинг, который берёт обычный PostgreSQL и добавляет к нему авторизацию, хранилище файлов и удобную панель). Схему таблиц вы описываете в коде через Drizzle (файл packages/db/src/schema.ts), а он превращает это в реальные таблицы.

2 Кирпичики: таблица, строка, колонка

Возьмём вашу таблицу users (клиенты) и посмотрим вживую.

Вот как реально выглядит таблица users — это «лист» с колонками сверху и строками-записями:

# id (PK) telegram_id display_name language created_at
1 7f3a…b21c 584213907 Игорь ru 2026-06-01 10:14
2 a91e…0f4d 219874550 Мария ru 2026-06-02 18:02
3 c52b…77a9 901233476 Алекс en 2026-06-03 09:41
  • Колонка — это поле с именем и типом. display_name — текст, created_at — момент времени.
  • Строка — один клиент целиком (всё, что в одной горизонтали).
  • Тип — обещание БД: в created_at всегда лежит дата-со-временем, никогда «вчера вечером».

Главные типы, которые встречаются в вашей схеме:

Про enum. Это «выпадающий список» на уровне БД. У заказа status может быть только одним из 13 заранее объявленных значений (draft, paid, completed…). Попытка записать status = 'оплачено' будет отклонена — опечатки в статусах невозможны by design.

3 Первичный ключ — паспорт строки

Как отличить одну строку от другой, даже если все поля совпадают.

У каждой строки есть первичный ключ (PRIMARY KEY, PK) — уникальный идентификатор. У вас это всегда колонка id типа uuid, например 7f3a8c10-…-b21c. Двух строк с одинаковым id в таблице быть не может — БД это гарантирует.

Зачем UUID, а не 1, 2, 3? Обычный счётчик (1, 2, 3…) требует, чтобы БД знала «какой был последний номер». В распределённой системе это узкое место. UUID — случайное 128-битное число, его можно сгенерировать где угодно (хоть в коде до записи), и совпадения практически невероятны. Минус — он длинный и нечитаемый человеком.

Поэтому у заказов есть две «личности»:

ПолеПримерДля кого
id (PK)946a3a0f-7883-…-5078для машины: связи, индексы, точность
short_idORD-2KB9Xдля человека: сказать оператору, вставить в чек

Оба уникальны, но short_id короткий и его не стыдно показать в Telegram.

4 Внешний ключ — сердце реляционных БД

Это самая важная идея. Если поймёшь её — поймёшь 80% всего.

Представь, что заказ должен «знать» своего клиента. Есть два пути:

Плохо: всё в одной куче

# заказ копирует данные клиента
{
  "short_id": "ORD-2KB9X",
  "client_name": "Игорь",
  "client_tg": "584213907",
  "amount": 209000
}

Игорь сделал 10 заказов → его имя записано 10 раз. Сменил имя — надо править в 10 местах. Забыл одно — рассинхрон.

Хорошо: ссылка по id

# заказ хранит id клиента, а не копию
{
  "short_id": "ORD-2KB9X",
  "user_id": "7f3a…b21c",  ← ссылка
  "amount_rub": 209000
}

Имя клиента живёт в одной строке таблицы users. Заказ хранит только её id. Сменил имя — поменялось везде сразу.

Колонка user_id в заказе — это внешний ключ (FOREIGN KEY, FK). Она содержит id строки из другой таблицы. «Внешний» = «указывает наружу, в чужую таблицу».

Аналогия с Python. Вместо того чтобы вкладывать целый объект клиента внутрь объекта заказа (order["client"] = {...}), ты хранишь только ссылку (order["user_id"] = "7f3a…"), а сам клиент лежит в общем словаре users["7f3a…"]. Это ровно нормализация: один факт — в одном месте.

БД охраняет эти ссылки

Внешний ключ — не просто текст. БД проверяет, что такой user_id реально существует в users. Нельзя создать заказ на несуществующего клиента. А ещё можно задать, что делать при удалении клиента:

ПравилоЧто значитГде у вас
ON DELETE CASCADEУдалил клиента — удалились и его диалоги/сообщенияconversations, messages
ON DELETE RESTRICTНельзя удалить клиента, пока есть его заказы (заказы — святое)orders.user_id, payments.order_id
ON DELETE SET NULLУдалили заказ — у вложения просто обнулилась ссылка, файл осталсяattachments

Видишь логику: деньги и заказы защищены жёстко (RESTRICT — их физически нельзя осиротить или удалить), а вспомогательные данные удаляются каскадом или просто отвязываются.

Как ссылку «разворачивают» обратно — JOIN

Когда нужно показать заказ вместе с именем клиента, БД делает JOIN: берёт user_id из заказа, находит строку в users с таким id и склеивает их. JOIN — это «иди по ссылке и подтяни данные».

-- "дай заказы вместе с именами клиентов"
SELECT orders.short_id, users.display_name, orders.amount_rub
FROM orders
JOIN users ON users.id = orders.user_id;   ← идём по FK

5 Типы связей: 1:1, 1:∞, ∞:∞

Сколько строк одной таблицы соответствует строкам другой.

Один-ко-многим (1 : ∞) — самая частая

У одного клиента — много заказов. У одного заказа — много платёжных попыток. Признак: внешний ключ стоит на стороне «многих».

users (1)  ──────►  orders (∞)        один клиент → много заказов
orders (1) ──────►  payments (∞)      один заказ → много попыток оплаты
orders (1) ──────►  order_events (∞)  один заказ → много событий в журнале

Один-к-одному (1 : 1) — редко

Одной строке соответствует ровно одна строка в другой таблице. У вас, по сути, нет жёстких 1:1 — но близко связь staff.auth_user_id → запись авторизации Supabase (один оператор = один аккаунт входа).

Многие-ко-многим (∞ : ∞) — через таблицу-посредник

Например, «много заказов могут использовать много карт за время жизни». Прямой такой связи в SQL не бывает — её всегда разбивают на две связи «один-ко-многим» через промежуточную таблицу. У вас это решено проще: orders.card_id ссылается на текущую карту, а карта переиспользуется между заказами (статусы active/idle/recycled).

Как читать диаграмму ниже. Линия между таблицами = связь. Метка 1 : ∞ показывает направление: со стороны «1» — таблица-родитель (на неё ссылаются), со стороны «∞» — таблица-ребёнок (она хранит внешний ключ).

6 Индексы — почему поиск мгновенный

Главный секрет скорости БД. И ответ на твой вопрос «выдержит ли нагрузку».

Допустим, в orders миллион строк, и тебе нужны все со статусом pending_payment. Без индекса БД честно просматривает все миллион строк — это «полное сканирование», медленно.

Аналогия — указатель в конце книги. Чтобы найти все упоминания слова «транзакция» в учебнике, ты не читаешь его целиком. Открываешь предметный указатель — там сразу «транзакция: с. 45, 88, 203». Индекс в БД — ровно такой указатель: отдельная отсортированная структура «значение → где лежат строки». БД заглядывает в неё и прыгает сразу к нужным строкам.

Индексы не бесплатны: каждый занимает место и чуть замедляет запись (при вставке надо обновить и указатель). Поэтому их ставят точечно — на те колонки, по которым часто ищут. Посмотри, что уже стоит у вас (из schema.ts):

ИндексНа таблицеУскоряет запрос
orders_status_idxorders«все заказы в статусе X» (очереди операторов)
orders_user_id_idxorders«все заказы клиента X»
payments_provider_provider_ref_idx (UNIQUE)payments«найти платёж по id у провайдера» + защита от дублей
messages_conversation_id_idx (… , created_at)messages«сообщения диалога по порядку времени»
order_events_order_id_created_at_idxorder_events«история заказа в хронологии»
cards_idle_idx (частичный)cards«найти свободную карту для переиспользования»

Все «горячие» запросы вашего приложения уже покрыты индексами. Именно поэтому количество строк (хоть миллионы) почти не влияет на скорость — БД не сканирует всё, а прыгает по указателю.

UNIQUE-индекс делает две работы сразу: ускоряет поиск и запрещает дубликаты. UNIQUE(provider, provider_ref) на платежах — это и быстрый поиск платежа, и гарантия, что один и тот же счёт L&P не запишется дважды (важно для идемпотентности — см. ниже).

7 Транзакции — «всё или ничего»

Что защищает деньги от рассинхрона при сбое посреди операции.

Когда оплата проходит, надо сделать несколько изменений сразу:

  1. пометить платёж как succeeded в таблице payments;
  2. перевести заказ в статус paid в таблице orders;
  3. записать строку «оплата прошла» в журнал order_events.

Что если сервер упадёт между шагами 2 и 3? Заказ оплачен, но в журнале нет следа — рассинхрон, расследовать невозможно. Чтобы такого не было, эти изменения оборачивают в транзакцию: БД применяет их как одно неделимое целое. Либо проходят все три, либо ни одного (откат к состоянию «до»). Третьего не дано.

Аналогия с Python. Транзакция — как with-блок: если внутри случилось исключение, __exit__ откатывает всё, что блок успел натворить, к началу. Никаких «полусделанных» состояний. 
with db.transaction():
    mark_payment_succeeded(...)   # шаг 1
    transition_order("paid")        # шаг 2
    append_order_event(...)       # шаг 3
# вышли без ошибки → COMMIT (всё сохранилось)
# упали посреди       → ROLLBACK (как будто ничего не было)

Это свойство называют атомарность (от «атом» — неделимый). Вместе с правилами типов, внешними ключами и UNIQUE-ограничениями оно даёт главное обещание БД: данные никогда не бывают в противоречивом состоянии. В вашем коде за переход заказа отвечает функция transitionOrder() — она и меняет orders.status, и пишет строку в order_events внутри одной транзакции.

9 Тур по 10 таблицам

Что хранит каждая и на кого ссылается.

ТаблицаХранитСсылается на (FK)Особенность
users клиентов из Telegram и веба — уникален по telegram_id или web_session_id

messages каждое сообщение в диалоге conversations, staff role: user / assistant / operator / system

RLS (Row Level Security) — это правила «кто какие строки имеет право видеть/менять», прямо в БД. Например, оператор видит только свои заказы, супервизор — все. Включён на всех таблицах с данными пользователей, выключен только на публичном каталоге services.

10 Жизнь одного заказа в данных

Как одна покупка «течёт» по таблицам — от первого сообщения до выданной карты.

1
Клиент пишет боту первый раз
Создаётся клиент, диалог и первое сообщение.
users +1conversations +1messages +1
2
AI собрал заказ
Появляется строка заказа, статус идёт draft → clarifying → ready_for_payment. Каждый переход = строка в журнале.
orders +1order_events +2…3messages +N
3
Клиент жмёт «оплатить» (confirm_order)
Создаётся счёт в L&P, записывается платёж, заказ переходит в pending_payment.
payments +1 (pending)orders → pending_paymentorder_events +1
4
Оплата прошла (webhook от L&P)
Платёж → succeeded, заказ → paid. Всё в одной транзакции.
payments → succeededorders → paidorder_events +1
5
Выпуск карты и выдача клиенту
Создаётся (или переиспользуется) карта, привязывается к заказу, статус идёт in_fulfillment → completed.
cards +1orders → completedorder_events +2

Обрати внимание: сам заказ — это одна строка, которая просто меняет status. А order_events накапливает историю всех её изменений — как лента «что произошло и когда». Поэтому в любой момент можно восстановить полную хронологию заказа, даже если текущий статус — completed.

11 Особые правила вашей схемы

Четыре инварианта, которые держат систему честной. Их нельзя нарушать.

💰 Деньги — в копейках (целым числом)

2090 ₽ хранятся как amount_rub = 209000 (копейки), тип integer. Никогда не дробным числом. Дробные числа (float) в компьютере неточны: 0.1 + 0.2 ≠ 0.3. На деньгах это недопустимо — копейки «утекают». Целое число копеек точно всегда.

📜 order_events — только добавление

Журнал событий заказа никогда не редактируется и не удаляется — только новые строки. Это даёт неподделываемый аудит: «кто, когда, с какого статуса на какой перевёл заказ». Форсится правилами RLS в БД.

🔁 Идемпотентность платежей

L&P может прислать webhook об оплате дважды (сеть ретраит). UNIQUE(provider, provider_ref) гарантирует: второй такой же платёж просто не запишется, заказ не «оплатится дважды». «Идемпотентность» = «повтори хоть 10 раз — результат тот же, что после одного раза».

🚦 Статус заказа — только через transitionOrder()

Менять orders.status напрямую запрещено. Только через функцию, которая проверяет, что переход разрешён (нельзя из draft прыгнуть в completed), и в той же транзакции пишет событие. Это и есть «машина состояний».

12 Выдержит ли БД 1000 оплат в день?

Короткий ответ: да, с огромным запасом. БД здесь вообще не узкое место.

1000 оплат в день — это в среднем меньше одной оплаты в минуту. Для PostgreSQL это смешная нагрузка. Посчитаем, сколько строк рождается:

messages~15 000–30 000~8 млн
cards~1 000 (минус переиспользование)<0,4 млн

Таблица в 8–10 млн строк с индексами — для Postgres «маленькая». Благодаря индексам (раздел 6) запросы не сканируют всё подряд, а прыгают по указателю — скорость почти не зависит от размера.

Тариф/размер Supabase + пулер соединений Не строки, а лимит одновременных подключений. Serverless-функции плодят коннекты — ходить надо через пулер Supabase (порт 6543), а не напрямую. Это стоит проверить.
Авто-пауза Supabase (free-тариф) БД засыпает без активности. Уже закрыто cron-ом keepalive, но для боевой нагрузки — переход на Pro.
Внешние API: L&P, Anthropic, PaySpace Вот настоящий потолок. 1000 выпусков карт/день упрутся в лимиты PaySpace раньше, чем в Postgres.
Пропускная способность операторов Если часть заказов обрабатывается вручную — людей надо больше, чем строк в БД.
Вывод. Про схему БД при 1000/день думать не надо — она спроектирована с запасом и проиндексирована. Думать надо про тариф Supabase (Pro + пулер соединений) и про лимиты внешних провайдеров.
