# Freekassa — контракт API и уведомлений

**Статус: контракт ПОДТВЕРЖДЁН живым платежом 2026-07-28** (заказ ORD-ZPP17,
850,62 ₽ по СБП, касса `74953`). Прод принимает рубли через Freekassa
(`PAYMENT_PRIMARY_PROVIDER=freekassa`). Проверены оба API-эндпоинта, вебхук,
переход заказа в `paid` и топап карты PaySpace — итог в §11. Настройки кабинета
(методы, комиссии, лимиты) — в §9.

> **Правило проекта: доки провайдеров врут.** С L&P тестовая панель кабинета
> слала фейковый формат событий; у PaySpace суммы приходят то строкой, то
> числом, а `exp_date` — в `MM/YY`. У Freekassa дока на поверку не соврала:
> живой платёж совпал с ней по формату уведомления, подписям и полям. Разделы,
> помеченные «по доке», проверены — расхождений не найдено.

Источник — <https://docs.freekassa.net/> (единственный живой домен: `docs.freekassa.com`,
`docs.fk.life` и `freekassa.com/docs` не отвечают вообще).

## 2. Способ подключения

Провайдер даёт два параллельных способа, и секретных слова поэтому два.
**Мы используем только API** (решение владельца 2026-07-26): счёт создаёт наш
сервер, как у L&P.

| | SCI-форма | API |
|---|---|---|
| Куда | `https://pay.fk.money/` (форма в браузере клиента) | `https://api.fk.life/v1/` |
| Подпись | MD5 по **секретному слову 1** | HMAC-SHA256 по **API-ключу** |
| Используем | нет | **да** |

**Секретное слово 2 нужно в любом случае** — им подписывается входящее
уведомление, а оно приходит независимо от способа создания заказа. Секретное
слово 1 кодом не читается вовсе (в env лежит про запас — переход на SCI не
потребует беготни по кабинету).

## 3. Создание заказа — `POST /orders/create`

### Подпись запроса (раздел 2.2 доки)

Значения параметров сортируются **по ключам** в алфавитном порядке,
склеиваются через `|`, строка хешируется `HMAC-SHA256` с **API-ключом**.
Само поле `signature` в подписываемую строку **не входит** — добавляется после.

PHP-эталон из доки:

```php
$data = ['shopId' => 777, 'nonce' => time()];
ksort($data);
$sign = hash_hmac('sha256', implode('|', $data), $api_key);
$data['signature'] = $sign;
```

Наш порядок ключей получается такой:

```
amount | currency | email | i | ip | nonce | paymentId | shopId
```

⚠️ **Числа в подписи и в теле обязаны совпадать посимвольно.** Мы подписываем
`String(value)`, а в тело уходит `JSON.stringify(value)` — в JS это один и тот же
алгоритм, поэтому отдельного форматирования суммы быть не должно (регресс на это
есть в тестах). Именно здесь ломаются интеграции, где сумму «красиво» приводят
к двум знакам только в одном из двух мест.

### Параметры

| Поле | Что шлём |
|---|---|
| `shopId` | `FREEKASSA_SHOP_ID` |
| `nonce` | `nextval('freekassa_nonce')` — см. §6 |
| `paymentId` | НАШ идентификатор попытки: `<shortId>-<6 hex>` |
| `i` | способ оплаты: `44` СБП, `36` карты РФ (дефолт `FREEKASSA_METHOD_ID`) |
| `email` | настоящий `users.email` (обязателен — гейт `422 email_required`; суррогат `<telegram_id>@telegram.org` убран антифрод-треком 2026-08-15, его появление алертится) |
| `ip` | настоящий IP плательщика из `users.last_seen_ip`; `127.0.0.1` провайдер блокирует (§5) |
| `tel` | НЕ шлём: за флагом `FREEKASSA_SEND_TEL` (дефолт выкл) — параметра нет в доке провайдера, ждём живого подтверждения (§10) |
| `amount` | сумма в **рублях** (у нас деньги — копейки, перевод один раз в клиенте) |
| `currency` | `RUB` |
| `signature` | HMAC по остальным полям |

Адреса возврата (успех/отказ) в запросе **не передаются** — они задаются в
кабинете магазина: успех `https://www.oplatishka.com/payment-success`,
отказ — главная.

### Ответ (по доке)

```json
{
  "type": "success",
  "orderId": 123,
  "orderHash": "bd4161db429848651499aabcb1d89330",
  "location": "https://pay.freekassa.ru/form/123/bd4161db429848651499aabcb1d89330"
}
```

`location` — ссылка на оплату, её отдаём клиенту. `orderId` пишем в
`payments.provider_ref` (ключ идемпотентности), наш `paymentId` — в
`payments.provider_invoice_number`.

Схема принимает `orderId` и числом, и строкой (урок PaySpace) и нормализует в
строку: `provider_ref` текстовый, разнотипица ломала бы `UNIQUE(provider, provider_ref)`.

### Ошибка

```json
{ "type": "error", "message": "..." }
```

Статусы по доке: `200` успех, `400` ошибка запроса, `401` ошибка авторизации.
⚠️ Отказ распознаём **по полю `type`, а не только по статусу**: провайдер
отдаёт `type: "error"` и с кодом 200.

## 3.1. Список заказов — `POST /orders` (добор потерянных уведомлений)

Параметры (по доке): `shopId`, `nonce`, `signature` — обязательные; опциональные
`orderId` (номер заказа Freekassa), `paymentId` (наш номер), `orderStatus`,
`dateFrom`, `dateTo`, `page`. Подпись — та же схема, что у `/orders/create`.

Ответ:

```json
{
  "type": "success",
  "pages": 12,
  "orders": [
    {
      "merchant_order_id": "Order #123",
      "fk_order_id": 652367,
      "amount": 100.12,
      "currency": "RUB",
      "email": "user@example.com",
      "account": "5555555555554444",
      "date": "2021-03-29 12:28:24",
      "status": 1
    }
  ]
}
```

Статусы: `0` новый, `1` оплачен, `6` возврат, `8` ошибка, `9` отмена.

⚠️ **`account` — номер карты плательщика, в примере доки это полный PAN.** Поле
намеренно НЕ объявлено в нашей Zod-схеме: `z.object` отбрасывает неизвестные
ключи, поэтому PAN физически не может попасть ни в логи, ни в
`payments.raw_payload`. Не добавлять без threat-model.

Как используем (`lib/jobs/poll-payment.ts`, каждые 5 минут):

- ищем по НАШЕМУ `paymentId` и дополнительно фильтруем ответ по
  `merchant_order_id` — если провайдер проигнорирует параметр и отдаст первую
  страницу всех заказов, обработать чужой платёж как свой хуже, чем не обработать
  никакой;
- `status = 1`, а у нас платёж `pending` → уведомление потерялось, обрабатываем
  как оплату с `recovered_via_polling = true`;
- `8`/`9`/`6` → терминальный путь. **Уведомление провайдер шлёт ТОЛЬКО об
  успешной оплате**, о неуспехе не сообщает вовсе — значит опрос это ещё и
  единственный способ узнать про отменённый счёт;
- `6` (возврат) по неоплаченному у нас счёту — денежная аномалия (деньги приняли
  и вернули, мы не видели): хороним как `cancelled` и алертим;
- неизвестный код → НЕ терминальный: хоронить заказ по догадке нельзя, деньги
  могли быть приняты.

Ответ содержит `fk_order_id`, поэтому добор заодно показывает, совпадает ли он с
тем, что мы сохранили при создании — это и закроет открытый вопрос про `intid`.

### Ретраев нет

`createOrder` **не повторяется** ни при таймауте, ни при 5xx. Причины:
операция мутирующая и без идемпотентного ключа (повтор создаёт второй заказ),
а `nonce` обязан расти — повтор с тем же телом провайдер отвергнет, повтор со
свежим nonce это уже другой заказ. Тот же вывод, что у PaySpace `createCard`.
Сбой отдаётся наверх → `503 provider_unavailable`, платёж в БД не создан, заказ
остался `ready_for_payment` — клиент жмёт «Оплатить» ещё раз.

## 4. Уведомление об оплате (webhook)

`POST https://www.oplatishka.com/api/payments/freekassa`, form-data.

| Поле | Что это |
|---|---|
| `MERCHANT_ID` | ID магазина |
| `AMOUNT` | сумма (строкой, с дробной частью) |
| `intid` | номер операции у провайдера |
| `MERCHANT_ORDER_ID` | наш `paymentId` |
| `P_EMAIL`, `P_PHONE` | плательщик |
| `CUR_ID` | валюта |
| `SIGN` | подпись |
| `payer_account` | **счёт/карта плательщика** |
| `commission` | комиссия в валюте платежа |
| `us_*` | пользовательские поля (мы их не шлём) |

Подпись: `MD5("MERCHANT_ID:AMOUNT:секретное слово 2:MERCHANT_ORDER_ID")`.

Ответ: **HTTP 200 всегда** (инвариант 6), принятым уведомление считается по
**телу `YES`**. Мы отвечаем `YES` только на окончательный исход (обработали,
идемпотентно пропустили, зафиксировали недоплату); «платёж ещё не найден»,
«невалидная подпись», «сбой обработчика» получают 200 с телом не-`YES`, чтобы
провайдер повторил — гонка «уведомление обогнало запись платежа» и «в env было
не то секретное слово» лечатся именно повтором.

### Следствия для архитектуры

1. **В подписи нет ни времени, ни nonce → уведомление воспроизводимо**, ровно
   как у L&P. Anti-replay держится на атомарном `claimPaymentSucceeded`
   (инвариант 2), а не на подписи.
2. `intid` → `payments.provider_ref`, он же ключ `UNIQUE(provider, provider_ref)`.
3. `AMOUNT` разбирается **точно в копейки** (`parseRubleAmountToKopecks`), без
   `parseFloat`: `parseFloat('2490.55') * 100 === 249054.99999999997`.
   Сумма с ненулевой дробью мельче копейки отвергается, а не округляется.
4. ⚠️ **`payer_account` — потенциально полный номер карты.** В логи и в
   `payments.raw_payload` уходит только маска `****1234`
   (`toStorableNotification`); поле добавлено в redact-лист pino.

### ✅ `intid` РАВЕН `orderId` из `/orders/create` (подтверждено 2026-07-28)

Живой платёж: `/orders/create` вернул `orderId = 320049073`, уведомление пришло с
`intid = 320049073`. Запасной поиск по `MERCHANT_ORDER_ID` не понадобился,
`intid_mismatch` в Sentry не сработал. Запасной путь оставлен намеренно — одно
наблюдение не гарантия контракта, а стоит он одного запроса к БД только при
промахе.

### ✅ `AMOUNT` — сумма НАШЕГО счёта, при любой стороне комиссии

**Комиссия на покупателе (2026-07-28).** Счёт был на 850,62 ₽, комиссия
покупателя 6% — в уведомлении пришло `AMOUNT = 850.62`. Надбавку провайдер берёт
с плательщика сверху и в `AMOUNT` её не кладёт.

**Комиссия на магазине (2026-07-30, контрольный платёж ORD-9NAGJ).** Это был
открытый риск: если бы провайдер клал в `AMOUNT` сумму за вычетом своих 6–7%,
терминальный детектор недоплаты (`gotKopecks < amountRub - 1`) ронял бы в
`failed` КАЖДЫЙ заказ. Проверено живыми деньгами — риска нет:

```
счёт          171912 копеек (1 719,12 ₽), Figma Full seat $16, курс 82,65
уведомление   amount="1719.12"  curId="44" (СБП)
результат     freekassa.handlers.paid_processed — сверка прошла, mismatch нет
```

То есть `AMOUNT` — всегда сумма выставленного счёта, независимо от того, кто
платит комиссию. Детектор недоплаты на комиссию не реагирует и реагировать не
должен.

Заодно снят тайминг всего денежного пути: заказ 13:02:30 → счёт 13:02:35 →
оплата 13:03:08 → карта готова 13:03:15, **45 секунд** от создания до
`completed`. Карта не выпускалась заново — сработал топап активной
($16 + 20% буфер = $19,20), поэтому надбавка за выпуск в заказе нулевая.

⚠️ Что этим платежом НЕ проверено: сколько реально зачислено на баланс магазина.
`AMOUNT` — это сумма счёта, а удержание комиссии видно только в кабинете
провайдера. Ожидаемо ≈1 616 ₽ (6% СБП с 1 719,12 ₽), но фактом не подтверждено.

### IP отправителя

По доке: `168.119.157.136`, `168.119.60.227`, `178.154.197.79`, `51.250.54.238`.

Жёсткий allowlist по умолчанию **выключен**: провайдер может сменить адреса
молча, и тогда приём денег остановился бы без единого симптома, кроме тишины.
Поведение:

- `FREEKASSA_ALLOWED_IPS` не задан → несовпадение только алёртится, уведомление
  обрабатывается (единственный жёсткий гейт — подпись);
- задан → несовпадение отвергается.

Перед включением жёсткого режима **сверить по логам, какой IP мы реально
видим**: за реверс-прокси «правый `X-Forwarded-For`» — это адрес прокси, а не
провайдера.

## 5. IP плательщика

`127.0.0.1` провайдер блокирует. С антифрод-трека 2026-08-15 шлём **настоящий
адрес клиента** — `users.last_seen_ip`: он пишется с троттлингом из живых
запросов самого клиента (кабинет, propose, confirm, чат — `rememberClientIp`),
поэтому внутренний self-call `payments/create` не мешает. До трека уходил
публичный IP узла — провайдер видел один адрес у всех плательщиков, портрет
дроп-схемы и главную причину антифрод-холдов.

`FREEKASSA_FALLBACK_IP` (`187.124.172.104`) остался страховкой на случай
клиента вовсе без `last_seen_ip`; его использование — аномалия с алёртом
`freekassa_ip_fallback` (Sentry). Живой заказ 2026-08-15 подтвердил: IP клиента
записывается за секунды до заказа, счёт уходит без fallback'а.

## 6. `nonce` — монотонная последовательность

Требование доки: «уникальный ID запроса, **должен всегда быть больше
предыдущего**».

Источник — последовательность Postgres `freekassa_nonce` (миграция `0026`),
значение берётся `nextval`. Она монотонна при любой параллельности и переживает
перезапуск контейнера; пропуски при откате транзакции допустимы (требование —
«больше предыдущего», а не «без дырок»).

**Timestamp не годится:** два конкурентных `confirm_order` в одну миллисекунду
дают одинаковое значение, и второй запрос будет отвергнут. Кейс реальный —
веб-вкладка и handoff заказа в боте после привязки Telegram.

Старт последовательности — `2000000000` (≈ 2033-05), с запасом выше unix-времени
в секундах: если по этому магазину когда-либо слались запросы с `nonce = time()`
(вариант из доки), счётчик с единицы оказался бы **меньше** уже использованного
и провайдер отвергал бы всё подряд.

⚠️ **Запаса над секундами оказалось мало** (инцидент 2026-08-15,
`docs/incidents.md`): nonce-водяной знак у провайдера общий для ВСЕХ клиентов
API-ключа, и внешний вызов с `nonce = Date.now()` (unix-МИЛЛИСЕКУНДЫ, ~1.79e12)
разом сделал все наши значения «маленькими» — каждый запрос падал
`400 nonce already exist`, включая создание новых счетов. Развязка:
последовательность переведена `setval`'ом на **`2400000000000`** (мс-шкала
плюс ~20 лет запаса; провайдер мс-масштаб принимает — подтверждено живой
пробой, наш `Number.isSafeInteger`-гейт держит до 9e15). Если симптом
вернулся — измерить новый водяной знак восходящей лестницей проб (неуспешные
запросы знак НЕ поднимают) и повторить `setval` выше него.

**Об отказе теперь узнаём сразу, а не через два часа.** Наблюдатель `onApiError`
клиента (`lib/freekassa/client.ts`) отдаёт КАЖДЫЙ сбой обращения в
`lib/freekassa/nonce-alert.ts`; тот распознаёт отказ по nonce и шлёт владельцу
прямой DM (`notifyOps`, дедуп час) плюс Sentry-алёрт
`freekassa_nonce_rejected`. Автоподъёма счётчика в алёрте НЕТ намеренно —
лечение остаётся ручным (`docs/BACKLOG.md`).

## 7. Срок жизни счёта

Провайдер срок жизни заказа **не отдаёт** — в ответе `/orders/create` его нет.
`FREEKASSA_INVOICE_TTL_HOURS` (дефолт 1 ч) — это НАШ срок ожидания оплаты, по
нему выравнивается `orders.expires_at`.

**Решение владельца 2026-07-28 — час остаётся навсегда, независимо от того,
какой срок у провайдера.** Причина не техническая, а продуктовая: клиент, который
не заплатил сразу, через день оформит новый заказ (это меньше минуты), а
длинный TTL копил бы висящие счета и протухшие фиксации курса.

⚠️ Остаточный риск: если форма провайдера живёт дольше часа, клиент может
оплатить уже захороненный счёт. Обрабатывается — алёрт `paid_after_terminal` +
DM владельцу о ручном возврате.

## 8. Что мониторится

| Сигнал | Где | Что значит |
|---|---|---|
| `recovered_via_polling = true` в `payments` + Sentry warning | `poll-payment` | уведомления теряются — стоит проверить доступность вебхука |
| `intid_mismatch` (Sentry) | `lib/freekassa/handlers.ts` | `intid` не равен сохранённому `orderId` — записать факт сюда и упростить поиск |
| `zero_conversion` (Sentry + DM) | `lib/jobs/payment-conversion.ts` | счета выставляются, оплат нет: вероятно, шлюз отвечает 200, но платежи не проходят. Порог — 5 счетов за окно 70 мин со сдвигом 10 мин |
| `gateway_fallback` (Sentry + DM) | `lib/payments/gateway.ts` | основной шлюз не ответил, счёт выставил резервный (только при `PAYMENT_AUTO_FALLBACK=1`) |
| `amount_mismatch`, `paid_after_terminal`, `refund_on_pending`, `refund_on_succeeded` | `lib/freekassa/handlers.ts` | денежные аномалии, требуют ручного разбора |
| `freekassa_email_fallback`, `freekassa_ip_fallback` (Sentry) | `lib/payments/gateway.ts` | счёт ушёл с суррогатным email / IP сервера — обход гейта контактов или рассинхрон кода |
| холд: `last_provider_status = 7` в `payments` | `poll-payment` | банк держит перевод — заказ уходит в `payment_review`, клиенту автосообщение; дольше 7 дней → DM-сторож `payment-review-watch` |

## 9. Кабинет магазина — снято 2026-07-28 (касса `74953`)

Касса активирована, `FREEKASSA_SHOP_ID = 74953`. Ниже — факты из UI кабинета
(не из доки), они закрывают часть прежних открытых вопросов.

### Методы оплаты: через API доступны ТОЛЬКО два

В разделе «Валюты к приёму» бейдж **API** стоит лишь у `Card RUB` (ID 36) и
`СБП (НСПК)` (ID 44). Остальные (ЮMoney, VISA RUB, MasterCard RUB, МИР,
USD/EUR-методы, FKWallet) через API-интеграцию недоступны — их наличие в списке
на нас не влияет, мы жёстко шлём `i = FREEKASSA_METHOD_ID` (44). Решение
владельца 2026-07-28: оставить включёнными только 36 и 44.

### Комиссия и лимиты

| Метод | Лимит операции | Комиссия магазина | Комиссия покупателя |
|---|---|---|---|
| СБП (44) | 10 – 150 000 ₽ | 0% | **6%** |
| Card RUB (36) | 50 – 150 000 ₽ | 0% | **7%** |

Ползунок в кабинете распределяет комиссию между магазином и покупателем.
**Решение заказчика 2026-07-28 — платит МАГАЗИН**: ползунок выкручен на нас
(6% / 7%), у покупателя 0%. Клиент платит ровно сумму нашего счёта, обещание
«итоговую сумму увидишь до оплаты» выполняется.

Цена этого решения — маржа: `COMMISSION_PERCENT` остался 30%, поэтому комиссия
съедает около четверти наценки (цена = база × 1.30, после удержания × 1.222).
Чтобы сохранить 30% чистыми, наценку пришлось бы поднять до ~39% — сознательно
не сделано.

⚠️ **Если комиссию когда-нибудь вернут на покупателя**, сумма на странице
провайдера станет выше нашего счёта. Код к этому готов: `FREEKASSA_BUYER_FEE_PERCENT`
(на проде **0**) включает предупреждения на всех экранах с ценой — витрины,
карточка заказа, кабинет, сообщение бота. Значение обязано совпадать с ползунком:
API комиссий провайдер не отдаёт, автосверки нет.

**Минимальная сумма** провайдера (10 / 50 ₽) НИЖЕ нашего порога 500 ₽ —
`FREEKASSA_MIN_AMOUNT_RUB=500` можно не трогать, пол витрины поднимать не надо.

**Максимальная — 150 000 ₽**, и это ограничение у нас держится в два эшелона:

1. витринный кап `$1200` (`HIGH_VALUE_MAX_AMOUNT_USD` и его три дубля) — клиент
   упирается в него ДО оформления заказа;
2. рублёвый гейт `FREEKASSA_MAX_AMOUNT_RUB` (дефолт 140 000) в `payments/create`
   → `422 above_max_amount`.

Второй эшелон нужен потому, что курс плавает: долларовый кап сам по себе не
гарантирует попадание в лимит (при курсе выше ~90 ₽ заказ на $1200 из него
выходит). Запас в 10 000 ₽ — на комиссию покупателя: неизвестно, считает
провайдер лимит до её начисления или после.

### Настройки, заданные в кабинете

- URL оповещения: `https://www.oplatishka.com/api/payments/freekassa`, метод POST
- URL успешной оплаты: `https://www.oplatishka.com/payment-success` (GET)
- URL возврата при неудаче: `https://www.oplatishka.com/` (GET)
- «Тестовый режим» и «Подтверждение платежа» — выключены. Тестовый режим даёт
  прогнать полный путь без денег; включать его безопасно, пока Freekassa не
  основной шлюз (при `PAYMENT_PRIMARY_PROVIDER=loveandpay` счета выставляет L&P).

## 10. Что ещё не выяснено

- **Нужен ли allowlist наших IP на их стороне** для запросов к API — в доке не
  упомянут, в кабинете такого поля не нашли.
- Актуальность списка IP уведомлений — сверить с провайдером.
- Считается ли лимит 150 000 ₽ до или после комиссии покупателя (от этого
  зависит, можно ли поднять `FREEKASSA_MAX_AMOUNT_RUB` со 140 000 до 150 000).
- **Поддерживает ли `/orders/create` параметр `tel`** (телефон плательщика) — в
  доке его нет. Код готов и выключен флагом `FREEKASSA_SEND_TEL`; включать только
  после подтверждения поддержкой и живого счёта с `tel` (тикет 12 у владельца).
