# Настройка доступа Love&Pay API: домен и статический IP Vercel

## Назначение

Этот документ — инструкция и техническое задание для агента, у которого есть доступ к
авторизованному браузеру владельца. Задача: подготовить production-интеграцию
«Оплатишки» к обязательной проверке доступа Love&Pay API по подтверждённому домену и
исходящему IP.

Официальные источники:

- индекс документации Love&Pay: <https://docs.loveandpay.io/llms.txt>;
- верификация домена и IP: <https://docs.loveandpay.io/guides/api-access-verification.md>;
- аутентификация API v2: <https://docs.loveandpay.io/api-reference/v2/authentication.md>;
- Static IPs в Vercel: <https://vercel.com/kb/guide/can-i-get-a-fixed-ip-address>;
- проект Vercel: <https://vercel.com/penkinjr-gmailcoms-projects/oplati-podpisku-web>;
- кабинет Love&Pay: <https://loveandpay.io/dashboard>.

## Контекст интеграции

Love&Pay теперь принимает API-запросы только при одновременном выполнении двух
условий:

1. в кабинете подтверждён хотя бы один домен через DNS TXT;
2. запрос пришёл с IP или из CIDR-подсети, добавленной в allowlist.

При нарушении требований API возвращает `403`:

- `DOMAIN_NOT_VERIFIED` — нет подтверждённого домена;
- `SOURCE_IP_NOT_ALLOWED` — исходящий IP отсутствует в allowlist.

Это дополнительный инфраструктурный гейт. Текущую HMAC-SHA256 аутентификацию API v2
менять не требуется.

Под проверку попадают исходящие запросы приложения к Love&Pay: создание инвойса и
получение его статуса. Входящий webhook Love&Pay на
`/api/payments/loveandpay` этим allowlist не ограничивается.

## Полномочия и стоп-условия

Перед началом агент обязан полностью прочитать `CLAUDE.md` в корне репозитория.

Разрешены без дополнительного подтверждения:

- чтение настроек Vercel, Love&Pay и Cloudflare;
- проверка DNS;
- фиксация текущего состояния без секретов;
- переходы по страницам настроек без сохранения изменений.

Требуют явного подтверждения владельца непосредственно перед действием, если оно не
было дано в сообщении, запускающем выполнение этого ТЗ:

- покупка или активация платной опции Static IPs;
- согласие с новой ценой или изменением биллинга Vercel;
- создание production-инвойса для smoke-теста;
- любые другие действия, создающие платный ресурс или финансовое обязательство.

После подтверждения настройки домена, DNS TXT и IP allowlist считаются ожидаемыми
действиями в рамках задачи и не требуют отдельного согласования на каждый клик.

Немедленно остановиться и запросить решение владельца, если:

- Vercel предлагает только Secure Compute/Enterprise вместо Static IPs для Pro;
- доступный регион Static IPs не включает `fra1`;
- включение Static IPs требует сменить регион production Functions;
- Love&Pay просит заменить или перевыпустить API/secret/webhook keys;
- домен или IP уже принадлежат другому партнёру/аккаунту;
- интерфейс или условия заметно расходятся с официальной документацией;
- для продолжения нужен доступ к аккаунту, которого нет в текущей браузерной сессии.

  он будет виден в DNS, но в рабочих артефактах его дублировать не нужно.

## Техническое задание

### Цель

Добиться состояния, при котором production Functions проекта
`oplati-podpisku-web` обращаются к Love&Pay API v2 со стабильного IP, этот IP разрешён
в кабинете Love&Pay, а production-домен подтверждён через DNS TXT.

### Результат

Должны одновременно выполняться условия:

- Static IPs активны для production Functions в `fra1`;
- все назначенные Vercel egress IP добавлены в Love&Pay;
- `www.oplatishka.com` или согласованный fallback-домен имеет статус
  «Подтверждён» в Love&Pay;
- production-запрос к Love&Pay не получает `DOMAIN_NOT_VERIFIED` или
  `SOURCE_IP_NOT_ALLOWED`;
- существующие HMAC-ключи, webhook и регион приложения не изменены.

## Порядок выполнения

### 1. Зафиксировать исходное состояние

1. Открыть проект Vercel по ссылке выше.
2. Проверить, что выбран именно team `penkinjr-gmailcoms-projects` и проект
   `oplati-podpisku-web`.
3. Проверить активный тариф Pro.
4. Открыть `Settings -> Connectivity`.
5. Зафиксировать без секретов:
   - включены ли Static IPs;
   - какие environments и регионы охвачены;
   - назначены ли egress IP;
   - показывается ли цена или дополнительное платное подтверждение.
6. Открыть Love&Pay `Настройки -> Доступ к API` и зафиксировать:
   - есть ли добавленные домены и их статусы;
   - есть ли разрешённые IP/CIDR;
   - какой IP указан как источник последнего API-запроса, если интерфейс это показывает.

Не копировать в отчёт ключи и секреты, даже если они видны на соседних страницах.

### 2. Включить Static IPs в Vercel

Этот шаг выполнять только после проверки стоп-условий и получения подтверждения на
платное изменение, если Vercel его запрашивает.

1. В `Settings -> Connectivity -> Static IPs` выбрать управление активными регионами.
2. Включить Static IPs для production Functions в `fra1`.
3. Не включать Builds и Preview без технической необходимости.
4. Если Vercel назначит несколько IP, сохранить полный набор: Love&Pay должен разрешить
   каждый возможный production egress IP.
5. Дождаться статуса `Ready`/`Active`.
6. Проверить, требует ли Vercel redeploy. Не делать redeploy «на всякий случай»; если UI
   прямо требует его, выполнить обычный production redeploy существующего успешного
   deployment без изменения env и кода.

Рекомендуемые метки для IP в Love&Pay:

- `Vercel prod fra1 #1`;
- `Vercel prod fra1 #2` — если назначен второй адрес.

### 3. Подтвердить домен в Love&Pay

Основной вариант — `www.oplatishka.com`, потому что это production `APP_URL` и реальный
сайт мерчанта.

1. В Love&Pay открыть `Настройки -> Доступ к API`.
2. Добавить домен `www.oplatishka.com` без протокола, пути и trailing slash.
3. Получить verification token.
4. В Cloudflare открыть DNS-зону `oplatishka.com`.
5. Создать запись:

   | Поле | Значение |
   | --- | --- |
   | Type | `TXT` |
   | Name | `_loveandpay.www` |
   | Content | `lnp-verify=<токен из Love&Pay>` |
   | TTL | `Auto` |

   Cloudflare автоматически допишет зону, поэтому итоговое имя должно быть
   `_loveandpay.www.oplatishka.com`.

6. Не добавлять TXT прямо на `www.oplatishka.com`: там уже находится CNAME, а DNS не
   разрешает одновременно держать CNAME и другие типы записей на одном имени.
7. Дождаться публичного DNS-ответа:

   ```bash
   dig +short TXT _loveandpay.www.oplatishka.com
   ```

8. Вернуться в Love&Pay и нажать «Проверить».
9. Убедиться, что статус домена стал «Подтверждён».

Если Love&Pay не принимает поддоменный вариант, не пытаться размещать TXT рядом с CNAME
`www`. Fallback:

1. удалить неподтверждённую запись домена из Love&Pay, если интерфейс этого требует;
2. добавить `oplatishka.com`;
3. создать TXT `_loveandpay` в зоне `oplatishka.com`;
4. проверить итоговое имя `_loveandpay.oplatishka.com`;
5. подтвердить apex-домен в Love&Pay.

### 4. Добавить egress IP в Love&Pay

1. В разделе `Настройки -> Доступ к API` добавить каждый IP, назначенный Vercel для
   production `fra1`.
2. Использовать одиночные IPv4/IPv6 или выданный Vercel CIDR строго в том виде, в каком
   их показывает Vercel.
3. Не добавлять:
   - IP Cloudflare;
   - A/AAAA-адрес сайта;
   - IP ноутбука;
   - IP посетителя;
   - произвольно широкий CIDR.
4. Сверить добавленные адреса с подсказкой Love&Pay «последний запрос пришёл с ...», если
   она доступна. При расхождении остановиться и выяснить, откуда реально выходит
   production Function.

### 5. Проверить работу

Предпочтительный smoke-тест — один запрос из существующего production payment flow.
Запрос с локального компьютера не проверяет Vercel allowlist.

1. Убедиться, что домен имеет статус «Подтверждён», а IP сохранены.
2. Если владелец разрешил создание тестового инвойса:
   - создать один тестовый заказ минимально допустимого размера штатным production flow;
   - дойти до успешного получения payment link;
   - не оплачивать инвойс;
   - отменить/закрыть тестовый инвойс в Love&Pay, если UI это позволяет;
   - не запускать выпуск карты и другие downstream-действия.
3. Проверить Vercel runtime logs для соответствующего запроса.
4. Проверить, что отсутствуют:
   - `DOMAIN_NOT_VERIFIED`;
   - `SOURCE_IP_NOT_ALLOWED`;
   - неожиданный `403` Love&Pay.
5. Убедиться, что создание обычных инвойсов и входящий webhook не перенастраивались.

Если тестовый инвойс не разрешён, не создавать его самовольно. Зафиксировать, что
инфраструктурная настройка завершена, а функциональная проверка отложена до первого
разрешённого production-запроса.

## Обработка ошибок

### `DOMAIN_NOT_VERIFIED`

- проверить статус домена в Love&Pay;
- проверить точное итоговое имя TXT;
- проверить значение целиком, без кавычек и пробелов;
- проверить публичный DNS, а не только интерфейс Cloudflare;
- дождаться распространения DNS и повторить проверку.

### `SOURCE_IP_NOT_ALLOWED`

- сравнить IP из ошибки/кабинета Love&Pay со всеми IP Vercel Static IPs;
- убедиться, что Static IPs подключены к production `fra1`;
- убедиться, что запрос действительно выполнялся из production, а не Preview или локально;
- не расширять CIDR наугад;
- если Vercel показывает новый набор адресов, добавить весь документированный набор.

### После настройки снова появляется `403`

- проверить, не отключены ли Static IPs или активный регион в Vercel;
- проверить, не изменился ли набор egress IP;
- проверить, что TXT остался доступен публично;
- проверить события биллинга/лимитов Vercel;
- не перевыпускать Love&Pay keys до подтверждения, что ошибка относится к ключам.

## Критерии приёмки

- [ ] Подтверждено, что команда Vercel остаётся на активном Pro.
- [ ] Static IPs активны для production Functions проекта `oplati-podpisku-web`.
- [ ] Активный регион Static IPs — `fra1`.
- [ ] Builds и Preview не подключены без необходимости.
- [ ] Все выданные egress IP добавлены в Love&Pay.
- [ ] В Love&Pay есть хотя бы один домен со статусом «Подтверждён».
- [ ] Публичный DNS возвращает корректный `lnp-verify=...` TXT.
- [ ] Production-запрос не получает новые access-related `403`.
- [ ] API/secret/webhook keys не менялись.
- [ ] Регион приложения не менялся.
- [ ] В git, отчёт и чат не попали секреты.
- [ ] Если был создан тестовый инвойс, он не оплачен и корректно закрыт либо отмечен как
  ожидающий автоматического истечения.

## Формат итогового отчёта агента

Отчёт должен содержать только безопасные данные:

```markdown
## Результат

- Vercel plan: Pro / другое
- Static IPs: active / inactive
- Environment: production
- Region: fra1 / другое
- Egress IP count: N
- Love&Pay domain: www.oplatishka.com / fallback
- Domain status: verified / pending / failed
- IP allowlist status: configured / incomplete
- Production smoke-test: passed / failed / not authorized
- Love&Pay error code: none / <code>
- Billing change approved by owner: yes / no / not required

## Изменения

- Vercel: <что включено>
- Cloudflare DNS: <имя и тип записи без verification token>
- Love&Pay: <домен и количество IP без ключей>

## Доказательства

- время проверки;
- безопасные скриншоты статусов без ключей и секретов;
- результат публичного DNS-запроса с замаскированным значением токена;
- request ID или временная метка smoke-теста, если доступны.

## Оставшиеся риски или действия

- <список либо "нет">
```

Фактические API keys, secret keys, webhook secrets, cookies и полные значения токенов в
отчёт не включать.
