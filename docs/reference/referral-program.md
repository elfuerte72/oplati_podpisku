# Реферальная (партнёрская) программа

Одноуровневая программа за флагом `REFERRAL_ENABLED` (на проде soft-start): как ловится
реферер, как считаются комиссии, как двигается статус партнёра и что готово в выплатах.

Выделено из `CLAUDE.md` 2026-08-14. ⚠️ Исторические спека и план
([`../history/spec-2026-06-referral-program.md`](../history/spec-2026-06-referral-program.md),
[`../history/plan-2026-06-referral-program.md`](../history/plan-2026-06-referral-program.md))
описывают **трёхуровневую** схему до упрощения 2026-07-02 и расходятся с кодом — как ТЗ не
использовать.

**UI-термин — «статус»; в коде и БД идентификатор остался `circle`/`current_circle`.**

## Одноуровневая с 2026-07-02

Уровни 2–3 и командный множитель удалены, `REFERRAL_MAX_LEVEL=1`. Партнёр получает процент
только с оплат СВОИХ прямых рефералов.

## Захват реферера

Только Telegram deep-link — веб-захват `?ref=` и middleware удалены. `users.referred_by`
immutable. Ловится в двух точках:

1. **Бот `/start ref_<code>`** — реферер проставляется при СОЗДАНИИ строки в
   `getOrCreateUserByTelegramId`, без анти-абьюз-гейта.
2. **Mini App `initData.start_param`** (`captureReferralFromStartParam` → `setReferrerOnce`), плюс
   поздний захват на повторном `/start ref_` для уже существующих строк — оба с гейтом
   `hasPurchasedOrders`: устоявшегося покупателя не переприсваиваем.

### Обратная связь на `/start ref_` (2026-09-05)

До этого любой заход по ссылке-приглашению получал одно и то же приветствие — и друг,
и сам партнёр, открывший свою ссылку «проверить». Разбор жалоб «реферальные ссылки не
работают» по проду показал исправный захват (12 из 12 новых закреплены за 45 дней,
ни одного `code_unknown`) и три захода партнёра по собственной ссылке: код молча выходил
на `referrerId === userId`, без лога и без ответа человеку. Теперь `attachReferral` в
`start-menu.ts` различает исходы `captureReferralForUser` (`ReferralCaptureOutcome`):

| Исход | Другу | Партнёру |
|---|---|---|
| Новая строка (реферер поставлен INSERT'ом) или поздний захват `set` | `REFERRAL_WELCOME_TEXT` | DM `REFERRAL_PARTNER_JOINED_TEXT` — без имени и id друга |
| `self_link` (своя ссылка) | `REFERRAL_SELF_LINK_TEXT` | — |
| `already_set`, `has_purchases`, `cycle`, `failed` | только приветствие | — |

Всё уходит ПОСЛЕ приветствия и best-effort: сбой поиска партнёра или его 403 не долетают
до webhook'а. О закреплении партнёр узнаёт НЕ БОЛЕЕ одного раза: `referred_by` immutable,
повтор даёт `already_set`. Ровно одного раза нет — если persist создал строку `users`, но упал
на разговоре, закрепление состоялось молча и следующий `/start` его уже не объявит (принятая
деградация). Сказанное клиенту пишется в `messages` после доставки (`meta.source =
'referral_feedback'`) — лента панели его видит. Ставка цифрой не называется. Для новой строки
поздний захват больше не зовётся: он гарантированно давал `already_set` ценой двух запросов.

### Код переживает привязку Telegram

Сайт `/partner` выдаёт код веб-строке ещё ДО привязки Telegram (`ensureReferralCode` в
`buildReferralSnapshot`), и партнёр мог уже раздать ссылку с ним. Merge в
`consumeLinkToken` удаляет веб-строку — до 2026-09-05 вместе с кодом, и каждый друг по
той ссылке получал `code_unknown`, то есть обычное приветствие без закрепления. Теперь код
веб-строки переносится на telegram-строку, если у той своего нет (после DELETE: колонка
UNIQUE). Если коды есть у обеих, выживает код telegram-строки — второй хранить негде
(`db.referral.merge_code_dropped`, алиасы кодов — в `BACKLOG.md`).

`setReferrerOnce` отклоняет установки, создающие **цикл** в дереве (`wouldCreateCycle` — обход
`referred_by` вверх, кап 16, fail-closed; M-1 аудита 2026-07-18, тот же чек давно есть в
merge-пути `consumeLinkToken`). Без него пара A↔B вечно фармила бы комиссию с покупок друг друга.

⚠️ **Инвариант (фикс 2026-07-02): `referred_by_set_at` в raw-`INSERT` = SQL `now()`, НЕ JS
`new Date()`.** Date-объект в bind-параметре ронял слой кэша запросов (`The string argument must ... Received an instance of Date`), из-за чего захват молча падал ТОЛЬКО когда реферер задан
(обычный `/start` без ref писался нормально) — реферальные начисления не работали с запуска
программы.

### Формат ссылки-приглашения

Bot deep-link `telegram.me/<bot>?start=ref_<code>` — друг видит бота, есть контекст. Прямой Mini
App-link `telegram.me/<bot>/<app>?startapp=ref_<code>` возможен за флагом
`REFERRAL_MINIAPP_DEEPLINK`, на проде выключен (решение владельца в пользу bot-контекста). Флаг
заведён 2026-07-10, чтобы `TELEGRAM_MINIAPP_SHORTNAME` можно было задать ради кнопки «Личный
кабинет» на сайте, не меняя формат реф-ссылки — `referralMiniAppShortName()` в
`lib/telegram/deep-links.ts`.

## Начисление комиссий

`accrueReferralForPayment` вызывается в `processInvoicePaid` сразу после `claimPaymentSucceeded`.

- Ledger `referral_accruals` **append-only**, идемпотентность `UNIQUE(payment_id, beneficiary, level)`.
- Инвариант: **сумма начислений заказа ≤ его комиссия**.
- Исторические строки уровней 2–3 валидны, новых не появляется.

### Ставка — один источник

**Платится ЗАФИКСИРОВАННАЯ ставка `referral_partners.locked_rate_l1_bps`, и это единственный
источник** (решение владельца 2026-08-11: «процент не падает»). `REFERRAL_RATE_TABLE`
(4%/4%/6%/7%) осталась таблицей ПОРОГОВ, по которой `planMonthlyProgression` двигает храповик
ставки, а не источником расчёта.

До 2026-08-11 начисление считалось по текущему `circle`, а кабинет показывал
`locked_rate_l1_bps` — два источника, расходящиеся при любом рассинхроне. Теперь расчёт и
витрина зовут общую `effectiveReferralRates`, и у неё есть **потолок**: раньше его давала
таблица по построению, теперь источник — колонка БД, а кривое значение платило бы из маржи заказа.

### Самореферал и мультиаккаунт

**Самореферал** (свою же ссылку открыли в боте, web-строка стала реферером telegram-строки)
гасится при merge компенсирующей строкой `status='reversed'` с `created_at` исходной — иначе
месячные агрегаты кабинета уходят в минус. На проде таких строк не было ни одной (проверено
2026-08-11).

⚠️ **Мультиаккаунт** (ссылку открыли аккаунтом A, web-строку привязали к B) отсюда неотличим от
честной пары. Это Этап E3, см. `BACKLOG.md`.

## Месячная прогрессия

Cron `referral-rollup` → `planMonthlyProgression`: храповик статусов, бонусы достижения / спринт /
серия, спринт-буст, уведомления. Идемпотентность на партнёра-за-месяц через `PK(user_id, month)`
в `referral_monthly_stats`. Легаси-колонки `active_l2`/`team_multiplier` пишутся нулями, миграций
не было.

## Кабинет партнёра

Веб `/partner` + Mini App (`components/partner/PartnerCabinet.tsx`), единый бэкенд
`POST /api/cabinet/referral`: один прокручиваемый дашборд (ссылка / сеть / доход / статус /
история) + кнопка возврата на сайт. Копирование ссылки — общим `copyToClipboard`
(`lib/clipboard.ts`, Clipboard API → `execCommand` → честный отказ с подсказкой выделить
ссылку, у которой стоит `select-all`): до 2026-09-05 партнёрский экран на отказ буфера
показывал «Скопировано», и в Telegram WebView, где clipboard часто заблокирован, друзьям
уходило содержимое буфера. «Поделиться в Telegram» в Mini App идёт через
`openTelegramLink`, на сайте — обычной ссылкой; оба действия пишут `referral_link_share`
с `surface: 'partner_cabinet'`. «Как это работает» ведёт на маркетинговый лендинг
`public/partner-presentation.html` (одноуровневый, `noindex`).

## Выплаты (Этап E) — каркас есть, движения денег НЕТ

Готово (E1): способы `card_rub`/`crypto_usdt`, комиссия вывода `computePayoutFee` (3.5% карта /
1% крипта, удержание из брутто), маскирование PAN и отсев Луна
(`packages/types/src/referral-payout.ts`; **CVV не собираем** — для выплаты не нужен, PCI-запрет),
схемы реквизитов input→stored (полный PAN не хранится и не логируется), машина статусов заявки,
`transitionReferralPayout`, `PayoutExecutor` + `MockPayoutExecutor` + чистая оркестрация
`settlePayout` (`apps/web/lib/referral/payout-executor.ts`).

**Реальный исполнитель ещё mock.** Ждёт решения `D-REF-6` — кто именно выплачивает (payout-API
L&P? сеть USDT?). `settlePayout` нигде не вызывается (семафор), формы реквизитов в UI нет
(поэтому `destination`/`method` в `referral_payouts` всегда NULL), антифрод (E3) не начат.

Чтобы заявка не замораживала баланс МОЛЧА, она уходит владельцу в Telegram через `after()` (без
реквизитов — в них PAN), а оба экрана партнёра, и до отправки и после, говорят одно: выплата
ручная, реквизиты уточним в Telegram (решение владельца 2026-08-11).
