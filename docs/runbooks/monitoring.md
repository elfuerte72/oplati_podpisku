Единая точка наблюдаемости — **Grafana Cloud** (стек `violetpasta1272`): логи всех

## Защита периметра VPS (аудит 2026-07-28)

**Снаружи открыты только 22/80/443** — проверено честным TCP-соединением с
постороннего сервера (не с рабочей машины: домашний провайдер отвечает SYN-ACK
на любой порт и показывает «открыто» даже там, где никто не слушает — например
на 5432). Панель Dokploy (3000), swarm-порты (2377/7946) и БД снаружи
недоступны.

Рубежей теперь два, и это важно: раньше всё держалось на одном тумблере в панели
хостера.

| Уровень | Что закрывает | Где |
|---|---|---|
| Firewall Hostinger `oplatishka-fra-prod` | всё, кроме 22/80/443 | панель хостера |
| `iptables INPUT` (policy DROP) | хостовые службы (sshd) | `/etc/iptables/rules.v4` |
| `iptables DOCKER-USER` | порты контейнеров — опубликованные порты Docker идут МИМО INPUT и ufw | там же |

⚠️ Правила сохранены через `netfilter-persistent`, но применение после
перезагрузки не проверялось (прод не перезагружали). Docker пересоздаёт свои
цепочки сам — при первой перезагрузке убедиться, что `DOCKER-USER` не опустела.

### Что защищает вход

- SSH: **только ключи** (`PasswordAuthentication no`), root без пароля,
  `MaxAuthTries 3`, X11 выключен. Брутфорс паролей невозможен в принципе.
- Ключей два: рабочий ключ владельца (комментарий `selectel`) и ключ агента
  Гилфойла — последний ограничен `command=`, то есть умеет ровно один скрипт
  статуса, без shell и проброса портов. ⚠️ Агент из мониторинга выведен (трек
  ops-group, 2026-09-04); снятие его ключа — шаг выката за владельцем, после него
  ключ остаётся один.
- `fail2ban` на sshd активен (0 банов — банить пока нечего).
- Rate-limit новых SSH-соединений: 30/мин с одного адреса, всплеск 15
  (`hashlimit` в INPUT). Рабочая автоматизация делает ~17 входов в час, своих не
  задевает.
- **Алёрт на вход с незнакомого IP** — `/opt/oplatishka-ssh-watch.sh`, каждые 5
  минут, список известных адресов в `/etc/oplatishka/ssh-known-ips`. Это главное:
  при входе только по ключу единственный реальный вектор — компрометация самого
  ключа, а её fail2ban не видит (для sshd это штатный успешный вход).

### Наблюдение за атаками

За первые 20 часов работы сервера — **ноль** неудачных попыток входа: 1778

## Ops-группа «Оплатишка - Support» — куда приходит всё

Одна приватная супергруппа с темами. Бот входа `@oplatishkaasupport_bot` — админ
группы и **единственный отправитель** машинных сообщений (решение владельца
2026-09-03: отдельный alert-бот и бот Гилфойла из контура выведены). Звук
включён только у «Аварии» — это настройка клиента Telegram у каждого участника
(группа в mute, тема «Авария» — исключение), кодом не задаётся. Оператор, когда
появится, просто добавляется в группу и видит «Поддержку» и «Платежи», ничего
не запуская; удалили из группы — доступа к новым обращениям нет.

| Тема | Поток в коде | Env с thread id | Что туда идёт |
|---|---|---|---|
| 🔴 Авария | `critical` | `OPS_GROUP_THREAD_CRITICAL` | сайт недоступен, контейнер пропал, cron умер, диск (Grafana critical); деплой не прошёл (GitHub); оплаченный заказ не доставлен, карта выпущена без записи в БД, топап с неизвестным исходом или при недоступном провайдере, оплата принята без перехода заказа, оплата по захороненному счёту, застрявший заказ (автоповтор не помог), прокси L&P не отвечает, «за час 0 оплат», клиент не смог оплатить из-за фонда или очереди, критический баланс карточного счёта |
| 💳 Платежи | `payments` | `OPS_GROUP_THREAD_PAYMENTS` | недоплата, возврат по оплаченному, холд банка и его исход, платёж завис у провайдера, «на проверке дольше 7 дней», гейт телефона, клиент с историей возвратов, nonce Freekassa, переключение на резервный шлюз, суточное предупреждение по балансу, «проверка фонда отключилась: нет таблиц», карточный счёт не прочитан, реферальный ledger и прогрессия |
| 🎧 Поддержка | `support` | `OPS_GROUP_THREAD_SUPPORT` | новое обращение (бот, Mini App, эскалация помощника), «без ответа больше 2 ч», оценки 1–3 из воронки |
| ⚠️ Ошибки | `errors` | `OPS_GROUP_THREAD_ERRORS` | релей Sentry (high priority); Grafana warning: всплеск ошибок в логах, память, CPU steal |
| 🚀 Деплой | `deploy` | `OPS_GROUP_THREAD_DEPLOY` | бэкапы Dokploy; провал деплоя дублируется сюда только по просьбе владельца — по умолчанию он в «Аварии» |
| 📊 Отчёты | — | — | создана на будущее, в этом треке ничего не пишется (дневная сводка — в `BACKLOG.md`) |

**Разделы владельца в группу не попадают.** Заявка партнёра на выплату и всё, что
закрыто оператору правами панели (`partners`, `staff`), уходит **личкой админам** тем
же ботом входа — правило одно, «в группу попадает только то, что видит оператор»,
и выводится из таблицы прав (`canAccess('operator', …)`), а не из второго списка.

**Как это устроено в коде** (`apps/web/lib/alerts/`): `streams.ts` — единственная
точка доставки `notifyStream(поток, текст)`; `notifyOps` — тонкая обёртка с
ОБЯЗАТЕЛЬНЫМ потоком (вызов без потока не компилируется); `notifyStaff` при заданной
группе постит в тему по капабилити (`support` → «Поддержка», остальное → «Платежи»;
явный `stream` поднимает событие в «Аварию»), дедуп-окна те же и занимаются по факту
поста; `format.ts` — единый шаблон сообщения (заголовок, тело, «Что делать» со ссылкой
на экран панели с `PANEL_HOST`). Sentry-релей `/api/alerts/sentry` шлёт в «Ошибки» и
Sentry не зовёт никогда (анти-петля).

**Режим без группы.** `OPS_GROUP_CHAT_ID` не задан → прежняя схема: `notifyOps` и
релей — в личку `ALERT_TELEGRAM_CHAT_ID` через `ALERT_BOT_TOKEN` (без него — через
клиентского бота), `notifyStaff` — личкой каждому сотруднику с правом на раздел,
при пустом штате — владельцу. Так живёт dev; на проде это страховка отката правкой
env. Незаданный thread id при заданной группе — корень группы, не молчание.

**Протухшая тема.** Тему удалили или пересоздали, а env остался старым → Bot API
отвечает «message thread not found»; алёрт уходит в **корень группы**, в логе `warn`
`alerts.stream.thread_not_found`, в Sentry — одно предупреждение на процесс. Лечится
правкой thread id в env и редеплоем. Ссылки на темы — `t.me/c/<id>/<thread>`, id
группы = `-100<id>`; метода «перечислить темы» в Bot API нет.

**Бот входа в группе молчит.** На входящие он отвечает только в личке; в группах и
супергруппах выходит до лимитера и БД (`telegram.staff_bot.ignored_chat_type`).

**Лимит Telegram** — 20 сообщений в минуту боту в одну группу. Дедупы приложения и
группировка в Grafana это перекрывают; 429 обрабатывает `withFloodRetry` бота входа.

**Токен бота входа лежит в ЧЕТЫРЁХ местах:** env прода (`TELEGRAM_LOGIN_BOT_TOKEN`),
Grafana Cloud (contact points), GitHub secrets (`DEPLOY_ALERT_BOT_TOKEN`), Dokploy
(уведомление «Бэкапы БД»). Утечка → `/revoke` у BotFather и замена во всех четырёх
разом, иначе часть каналов молчит при зелёном остальном.

### Алёрты Grafana: правило → тема

Два contact point на бота входа — «Авария» и «Ошибки» (chat id группы + thread id),
маршрутизация в notification policy по метке `severity` (`critical` / `warning`),
которая у правил уже стоит. Правила (папка «Оплатишка — алёрты»):

| Алёрт | Когда срабатывает | Severity → тема |
|---|---|---|
| **Сайт недоступен (внешний пинг)** | www.oplatishka.com не отвечает 200 из Frankfurt И London 2+ мин | critical → Авария |
| **Приложение: ошибки в логах** | >5 строк `level="error"` от `oplatishka-web` за 5 мин | warning → Ошибки |
| **Cron: poll-payment не отработал** | нет записей `module="cron.poll-payment"` за 30 мин (+10 мин выдержки) | critical → Авария |
| **Прод-контейнер пропал** | `oplatishka-web-wwrt50` не виден в метриках 10 мин | critical → Авария |
| **Узел: заканчивается диск** | свободно < 15% на `/rootfs` | critical → Авария |
| **Узел: CPU отбирает гипервизор** | `steal` > 20% за 10 мин | warning → Ошибки |
| **Узел: заканчивается память** | доступно < 10% | warning → Ошибки |

Про cron-алёрт (добавлен 2026-07-28): «тихая смерть» расписания по логам не видна
— нет запуска, нет и строки, поэтому правило ловит именно **отсутствие**
записей. `noDataState: Alerting` выбран сознательно: пустой ответ означает либо
мёртвый cron, либо сломанный сбор логов, и оба случая требуют вмешательства.
Цена молчания высокая — `poll-payment` дожимает потерянные вебхуки платёжных
шлюзов и заказы, застрявшие в `paid` (то есть деньги приняты, а карта не
выпущена).

Второе правило до 2026-07-25 называлось «Прокси сайта: ошибки 5xx» и следило за
`{node="timeweb-msk", container="oplatishka-proxy"}` — узлом, который после
перевода DNS на Hostinger не в пути трафика. То есть алёрт был мёртв: данных по
этому запросу не появилось бы никогда. Перенацелен на ошибки приложения; заодно
это второй канал ошибок в той же теме: Sentry с 2026-07-26 тоже шлёт их туда через
интеграцию «Telegram Alerts», но по другому поводу — Grafana реагирует на всплеск
(>5 за 5 минут), Sentry на первую же новую проблему.

## Слой 1 — Uptime (жив ли сайт снаружи)

**Grafana Synthetic Monitoring** (входит в Grafana Cloud): робот пингует
`https://www.oplatishka.com` каждые 60 с из **Frankfurt (14)** и **London (1)**,
проверяет статус 200 + валидный SSL. Метрика `probe_success{job="oplatishka-site"}`
(1 = жив, 0 = лёг). Check id `85330`. Управление —
Grafana → Synthetic Monitoring, или SM API
`synthetic-monitoring-api-eu-west-2.grafana.net`.

Ловит «сайт недоступен пользователю» по любой причине (лёг контейнер, лёг VPS,
сеть). Better Stack НЕ используется — у него нет Telegram-канала.

## Слой 2 — Ошибки (что сломалось)

**Sentry** — PII-скраббер, алёрты в Telegram через `/api/alerts/sentry`. Ловит
исключения со всех каналов: веб, бот, cron, платежи.

Доставка в Telegram включена 2026-07-26 через **Internal Integration «Telegram
Alerts»** (`telegram-alerts-d8df3a`), добавленную действием в правило `669372`
(проект `sentry-byzantium-battery`, орг `oplatishka`) **рядом с Email** — письма
никуда не делись, канала теперь два. ⚠️ Legacy Webhooks (Settings → Webhooks) для
этого **не годятся**: URL сохраняется, но действия в правиле не появляется, а
кнопка «Send Test Event» падает на стороне Sentry (их API `test-fire-actions`
отвечает `400`, до нас запрос не доходит вовсе).

**Что именно долетает в Telegram.** Условие правила — «Sentry пометил проблему как
high priority» (новую или существующую), а НЕ «любая новая ошибка»: события уровня
`warning`/`info` в Telegram не приходят (например, `L&P webhook без
X-Webhook-Signature`) — их видно только запросом в Sentry, в т.ч. из сводки
агента. Расширять до «любой новой проблемы» осознанно не стали: в проекте лежит
шумный CSP-issue (`Blocked 'script' from 'telegram.org'`, десятки срабатываний),
который забил бы канал.

Релей на проде: `SENTRY_ALERT_WEBHOOK_SECRET` + ops-группа (`OPS_GROUP_CHAT_ID`,
тема «Ошибки» — `OPS_GROUP_THREAD_ERRORS`), отправитель — бот входа. Без группы —
прежняя личка `ALERT_TELEGRAM_CHAT_ID` через `ALERT_BOT_TOKEN`. Нет секрета или
некуда слать — endpoint отвечает `200 {skipped:'not_configured'}` и молчит.

⚠️ **Грабля 2026-08-16: у internal integration и legacy webhook РАЗНЫЕ payload'ы.**
Наш парсер (`lib/alerts/sentry.ts`) знал только legacy-форму (всё на верхнем
уровне), а интеграция шлёт конверт `{action, data: {event, triggered_rule}}` —
событие на два уровня глубже, `environment` только в `tags` парами, имени проекта
нет вовсе (`event.project` — числовой id). Схема всё-optional + passthrough,
поэтому payload проходил валидацию, и владельцу приезжало **«Sentry issue /
Проект: — / Окружение: —»**: без названия ошибки, без места, без ссылки. Три
таких сообщения пришли во время инцидента с nonce и были неотличимы от шума.
Тесты не ловили — они были написаны по legacy-форме. Теперь поддержаны оба
формата, неизвестные поля не печатаются прочерком (отсутствие строки — тоже
информация), а невынимаемый заголовок логируется как `alerts.sentry.degraded`:
это единственный признак, что формат снова уехал.

**Sentry-uptime у нас нет и не нужен.** Монитор `1391039` (заведён при Vercel)
после переезда год стучался в мёртвый деплой `…vercel.app`, получал `410` каждые
60 с из трёх регионов и порождал issue «Downtime detected». Удалён 2026-08-16;
внешний uptime закрыт слоем 1 (Grafana Synthetic Monitoring). Если понадобится
дубль в Sentry — заводить на `https://www.oplatishka.com`, а не на домен
провайдера, откуда контур может уехать.

## Слой 3 — Логи (почему сломалось)

### Узлы → Grafana Loki

Агент **Alloy** (docker `grafana-alloy`, `--restart unless-stopped`, читает
`docker.sock`) шлёт логи в Loki. Конфиг: `/opt/alloy/config.alloy`, исходник с
комментариями — [`infra/alloy/config.alloy.example`](../../infra/alloy/config.alloy.example).

**Боевой узел — `hostinger-prod`** (`187.124.172.104`, Франкфурт): весь контур
Оплатишки, прод и dev. Метка узла сохранена прежней при переезде намеренно — на
неё завязаны правила алёртов и дашборды, менять её значит переписывать и их.

**`hostinger-legacy`** (`177.7.34.106`, Бостон) — прежний сервер: там остались
VPN-панель, личный бот владельца и Traefik, Оплатишки нет. Переименован
2026-07-28 при переезде: агент там продолжал слать логи чужого Traefik под меткой
`hostinger-prod`, и они смешивались бы с продовыми в одних и тех же запросах.

⚠️ **Грабля 2026-07-28:** при переезде агент остался на старом сервере — логи
прода не собирались вовсе, при этом дашборд показывал данные (старые, от
Traefik) и выглядел живым. Алёрт «ошибки в логах» при этом был мёртв: запрос
`{node="hostinger-prod", container=~"oplatishka-web..."}` не возвращал ничего, а
пустой результат срабатыванием не считается. **Перенос агентов наблюдаемости —
обязательный пункт чек-листа переезда** ([`server-migration.md`](server-migration.md)).

**Что собирается** (keep-фильтр по имени; на VPS живут и чужие проекты владельца):
`oplatishka-web-*` (prod и dev), `dokploy-traefik`.

**Что НЕ собирается намеренно.** Панель Dokploy и `oplatishka-db*` отсекаются отдельным
`drop`-правилом ПЕРЕД keep (keep и так пропускает только `oplatishka-web.*|dokploy-traefik`,
но цена ошибки в regex здесь не «лишние логи», а утечка); остальные чужие контейнеры
отсекает сам keep.

| Контейнер | Почему исключён |
|---|---|
| `dokploy.<n>.<id>` (панель) | печатает команду `rclone` **с ключами R2 открытым текстом** при каждом бэкапе — это доступ к дампам боевой БД |
| `oplatishka-db*` | Postgres пишет текст запроса при ошибке, то есть потенциальные PII клиентов |
| `remnawave*`, `vanyabot*`, `open-webui` | не наш контур |

⚠️ **Грабля 2026-07-25:** конфиг писался 23 июля, за день до переезда с Vercel, и
пропускал ровно один `lnp-proxy`. После переезда на этот VPS уехал весь прод, а в
Loki продолжали течь только логи squid-прокси — то есть логов приложения не было
вообще, при исправном канале (5163 строки за двое суток, 0 потерь). Проверять
надо не «жив ли агент», а **что именно он собирает**.

**Как смотреть:** дашборд (ссылка выше) или
[explore](https://violetpasta1272.grafana.net/explore) → источник
`grafanacloud-violetpasta1272-logs` (Loki) → режим **Code**:
```
{node="hostinger-prod"}                                            # весь узел
{node="hostinger-prod", container=~"oplatishka-web-wwrt50.*"}      # прод-приложение
{node="hostinger-prod", container=~"oplatishka-web-dev.*"}         # dev-стенд
{node="hostinger-prod", container=~"oplatishka-web-wwrt50.*"} | json | level="error"   # только ошибки
{node="hostinger-prod", container=~"oplatishka-web-wwrt50.*"} | json | module="cron.poll-payment"  # конкретный cron
{node="hostinger-prod", container="dokploy-traefik"}               # Traefik (TLS, роутинг, ACME)
```
Имя контейнера прод-приложения содержит суффикс Dokploy (`-wwrt50`) и номер
задачи swarm, который **меняется при каждом деплое**, — поэтому в запросах
всегда `container=~"...*"`, а не точное совпадение.

Приложение пишет структурированный JSON (pino): полезные поля — `level`,
`module`, `event`. Traefik по умолчанию access-log НЕ пишет, только ошибки, так
что запросов клиентов в Loki нет — если понадобится считать 5xx на входе, его
надо сначала включить.

**Тариф:** логи (Loki) и Synthetic Monitoring — в бесплатном плане Grafana Cloud
навсегда (50 ГБ логов/мес, лимит SM-проверок). Баннер «Trial» = платные
надстройки; после триала логи и uptime продолжат работать.

### Приложение → тот же Loki

С переездом на Dokploy приложение стало обычным контейнером на VPS, поэтому его
логи собирает тот же агент — отдельный конвертер, из-за которого их раньше
осознанно не тащили в Loki (решение 2026-07-23 в эпоху Vercel), больше не нужен.
Vercel-дашборд как источник логов неактуален: контур там холодный резерв.

#### Учёт AI-аналитика панели

Расходы аналитика (`/admin/ai`, DeepSeek) в `ai_usage_daily` не пишутся — единственный
источник учёта — строка лога `panel.ai.usage` с полями `staffHash`, `model`,
`inputTokens`, `outputTokens`, `toolCalls`, `durationMs`, `outcome`
(`ok` / `incomplete` / `max_iterations` / `api_error` / `error`). Loki-запрос:

```logql
{container_name=~"oplatishka-web.*"} | json | event = "panel.ai.usage"
```

Сумма токенов за день: `sum by (model) (sum_over_time({...} | json | event = "panel.ai.usage" | unwrap inputTokens [24h]))`
(и то же для `outputTokens`). Каждый запрос к базе — отдельная строка `panel.ai.sql`
(длительность, строки, усечение, ошибка); сам SQL — на уровне `debug`.

## Метрики узла (CPU, память, диск, контейнеры)

Собирает тот же Alloy: экспортеры `unix` (хост) и `cadvisor` (контейнеры) шлют в
Prometheus Grafana Cloud. Конфиг — [`infra/alloy/config.alloy.example`](../../infra/alloy/config.alloy.example);
запускать с монтированиями `/rootfs`, `/sys`, `/var/lib/docker` — без них
экспортеру нечего читать.

Появились 2026-07-28. До этого метрик не было вообще, и деградацию из-за CPU
`steal` (гипервизор отбирал до половины процессорного времени) нашли только по
жалобе на скорость, неделю спустя, — по логам такое не видно в принципе.

**Два ID, которые легко перепутать.** В Grafana Cloud у каждого сигнала свой
numeric пользователь, и они не совпадают ни между собой, ни со StackID:

| Сигнал | Пользователь | Endpoint |
|---|---|---|
| Loki (логи) | `1691092` | `logs-prod-012.grafana.net/loki/api/v1/push` |
| Prometheus (метрики) | **`3390834`** | `prometheus-prod-65-prod-eu-west-2.grafana.net/api/prom/push` |

Токен один на оба — политика `oplatishka-logs-write`, ей выданы `logs:write` и
`metrics:write`. Отдельный токен для метрик не нужен: права наследуются от
политики, поэтому расширение scope включает уже выпущенный токен.

⚠️ Ошибки различимы и подсказывают, где искать: `invalid scope requested` —
пользователь верный, не хватает права; `invalid authentication credentials` —
не тот пользователь. Мы прошли через обе.

⚠️ Диск в запросах — `mountpoint="/rootfs"`, а не `/`: агент видит корень хоста
через монтирование, и `/` внутри контейнера это его собственная файловая система.

**Проверить, что метрики идут:**

```bash
curl -s -H "Authorization: Bearer $GRAFANA_SA_TOKEN" \
  --get "https://violetpasta1272.grafana.net/api/datasources/proxy/uid/grafanacloud-prom/api/v1/query" \
  --data-urlencode 'query=up{node="hostinger-prod"}'
```

Ожидаемо две серии (`integrations/unix`, `integrations/cadvisor`) со значением 1.

**Почему нет алёрта на load average.** На 2 ядрах он законно уходит выше числа
ядер во время `docker build` при каждом деплое — правило давало бы ложные
срабатывания несколько раз в неделю. Деградацию узла ловит `steal`, который в
норме близок к нулю и растёт только по внешней причине.
