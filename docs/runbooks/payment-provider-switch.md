# Рунбук: переключение платёжного шлюза

Кто принимает рубли — Love&Pay или Freekassa — задаётся переменной окружения.
Смена значения + перезапуск контейнера, без правок кода и релиза.

**Состояние на 2026-08-27:** на проде основной шлюз — **Freekassa** (с 2026-07-28,
`PAYMENT_PRIMARY_PROVIDER=freekassa`, касса `74953`, контракт подтверждён живым
платежом — `reference/freekassa-api.md`); Love&Pay — резерв. Переключение на
`loveandpay` — это ОТКАТ, а не включение. Текущая картина обоих шлюзов —
[`../reference/payment-gateways.md`](../reference/payment-gateways.md); здесь —
только процедура переключения.

---

## 1. Что вставить в env прода

Приложение Dokploy `oplatishka-web` → вкладка **Environment**. Блок ниже можно
вставить целиком: значения безопасные, секретов в нём нет.

```dotenv
# ─── Платёжный шлюз ────────────────────────────────────────────────────────
# Кто принимает рубли ПРЯМО СЕЙЧАС. Допустимо: loveandpay | freekassa.
# Влияет ТОЛЬКО на создание нового счёта. Вебхуки ОБОИХ провайдеров работают
# всегда и флагом не гейтятся — иначе в момент переключения оплаты по уже
# выставленным счетам прежнего шлюза не были бы приняты.
# ⚠️ Опечатка (Freekassa, True, freekasa) роняет старт приложения — это
# намеренно: молча уйти на другой шлюз хуже, чем не подняться.
# Текущее значение на проде — freekassa; loveandpay = откат.
PAYMENT_PRIMARY_PROVIDER=freekassa

# Автофоллбэк: если основной шлюз не ответил (таймаут / сеть / 5xx), счёт
# выставит второй. Пусто или отсутствует = выключено. Включить: 1
# ⚠️ Включать ТОЛЬКО когда ОБА шлюза проверены живыми деньгами: иначе сбой
# основного уведёт весь поток на непроверенный контур.
# ⚠️ Требует ключей обоих провайдеров одновременно.
PAYMENT_AUTO_FALLBACK=

# ─── Freekassa ─────────────────────────────────────────────────────────────
# FREEKASSA_API_KEY и FREEKASSA_SECRET_WORD_2 уже заданы (2026-07-26) — НЕ ТРОГАТЬ.
# FREEKASSA_SECRET_WORD_1 тоже задан, но кодом не читается (нужен только
# SCI-форме, которую мы не используем). Лежит про запас.
#
# ID магазина (касса активирована 2026-07-28).
FREEKASSA_SHOP_ID=74953

# Всё ниже — необязательное: в коде есть рабочие значения по умолчанию.
# Задавать, только если хотите отойти от дефолта.
#
# Способ оплаты: 44 = СБП, 36 = карты РФ. Дефолт 44.
FREEKASSA_METHOD_ID=44
# Рублёвый потолок одного счёта (лимит операции провайдера ~150 000 ₽ минус запас);
# второй эшелон над витринным капом $1200. Дефолт 140000.
FREEKASSA_MAX_AMOUNT_RUB=140000
# Комиссия, которую провайдер накручивает ПОКУПАТЕЛЮ — зеркало ползунка
# «Магазин ↔ Покупатель» в кабинете (инвариант 10). Дефолт 6; 0 = тексты о
# надбавке не показываются.
FREEKASSA_BUYER_FEE_PERCENT=6
# Передавать ли телефон плательщика провайдеру. Дефолт выкл до живого
# подтверждения контракта (антифрод-трек, Р4).
FREEKASSA_SEND_TEL=
# Базовый URL API; менять только если провайдер сменит домен. Дефолт в коде.
FREEKASSA_BASE_URL=
# IP плательщика, когда реальный неизвестен (заказ из Mini App или бота).
# 127.0.0.1 провайдер блокирует, поэтому шлём публичный IP нашего VPS.
FREEKASSA_FALLBACK_IP=187.124.172.104
# НАШ срок ожидания оплаты в часах. Провайдер срок жизни счёта не отдаёт вовсе,
# так что это наше решение. Уточнить у них на смоуке и выставить по факту.
FREEKASSA_INVOICE_TTL_HOURS=1
# Минимальная сумма счёта в рублях. Дефолт 500 — тот же порог, что у L&P
# (решение владельца): переключение шлюза не меняет, какие заказы вообще можно
# оформить, и совпадает с полом каталога. Своего минимума провайдер не
# публиковал. 0 = аварийно отключить проверку.
# ⚠️ Поднимать выше 500 нельзя без синхронного подъёма пола каталога.
FREEKASSA_MIN_AMOUNT_RUB=500
# Список IP, с которых принимаем уведомления, через запятую.
# ПУСТО (рекомендуется) = несовпадение только алёртим, уведомление принимаем:
#   провайдер может сменить адреса молча, и жёсткий список положил бы приём
#   денег без единого симптома, кроме тишины. Подпись MD5 остаётся жёстким гейтом.
# ЗАДАН = несовпадение отвергаем. Включать только убедившись по логам, какой IP
#   мы реально видим — за реверс-прокси это адрес прокси, а не провайдера.
FREEKASSA_ALLOWED_IPS=
```

### Комиссия

`COMMISSION_PERCENT=30` **менять не нужно** — это наша наценка, она одинакова
для обоих шлюзов (решение владельца 2026-07-26). Клиент платит одну и ту же
цену независимо от того, кто принимает деньги; разницу в комиссии провайдеров
съедает маржа. Это принято осознанно.

## 2. Нужно ли задавать это на dev?

**Нет. И `PAYMENT_PRIMARY_PROVIDER=freekassa` там задавать НЕЛЬЗЯ.**

Причины:

1. На dev-стенде **намеренно нет платёжных ключей** (ни L&P, ни PaySpace, ни
   Freekassa) — иначе тестовый заказ выставил бы реальный счёт и выпустил карту
   за реальные деньги. Ни один шлюз там не заработает в принципе.
2. Значение `freekassa` включает гейт обязательных ключей. Ключей на dev нет →
   **приложение не запустится.**

Оставить dev как есть: переменных нет, работает дефолт `loveandpay`, платежи
там всё равно недоступны.

## 3. Порядок переключения (в любую сторону)

Строго по шагам. Пункты 1–2 менять местами нельзя. Так Freekassa и включали
2026-07-28; тот же порядок — при возврате на неё после отката.

1. **Убедиться, что ключи целевого шлюза заданы** (для Freekassa —
   `FREEKASSA_API_KEY`, `FREEKASSA_SHOP_ID`, `FREEKASSA_SECRET_WORD_2`) → сохранить.
2. **Только теперь** поменять `PAYMENT_PRIMARY_PROVIDER` → сохранить.
   > Наоборот приложение не поднимется: гейт требует, чтобы при `freekassa`
   > были заданы `FREEKASSA_API_KEY`, `FREEKASSA_SHOP_ID`,
   > `FREEKASSA_SECRET_WORD_2`. Это защита от «переключили флаг, забыли ключ».
3. **Нажать `Deploy`** в General. Полторы-две минуты, мгновенного рубильника
   нет. `Reload` быстрее и по нашим докам env тоже подхватывает, но живьём это
   не проверялось — после него обязательно проверить шаг 4.
   ⚠️ `Deploy` тянет свежий `main`: вместе с переключением уедет всё, что
   накопилось в ветке с прошлого деплоя.
4. **Проверить:** `https://www.oplatishka.com/api/health` → поле `startedAt`
   должно стать свежим.
5. **Смоук копеечной суммой:** заказ → ссылка → реальная оплата → уведомление →
   заказ `paid` → карта → реквизиты в Telegram. Проверить в БД, что у платежа
   `provider` равен целевому шлюзу и сумма в копейках сошлась точно (для
   Freekassa сделано 2026-07-28, ORD-ZPP17).

## 4. Откат

Вернуть `PAYMENT_PRIMARY_PROVIDER=loveandpay` → `Deploy`.

Клиенты, которым счёт уже выставлен через Freekassa, **не пострадают**: её
вебхук продолжает принимать деньги независимо от флага, а cron `poll-payment`
дожимает потерянные уведомления по каждому платежу отдельно.

Единственный неприятный случай — клиент в момент переключения жмёт «Оплатить»
по заказу, у которого уже есть живой счёт прежнего шлюза. Он получит ссылку
прежнего шлюза (и она рабочая) — это нормальное поведение, а не сбой.

## 5. Что смотреть после переключения

| Сигнал | Где | Что значит |
|---|---|---|
| `zero_conversion` | Sentry + DM | счета выставляются, оплат нет — шлюз, вероятно, не проводит платежи. **Главный сигнал для отката** |
| `recovered_via_polling=true` в `payments` | БД + Sentry | уведомления теряются, добор их подхватывает |
| `intid_mismatch` | Sentry | `intid` в уведомлении не равен сохранённому `orderId` — записать факт в `reference/freekassa-api.md` |
| `gateway_fallback` | Sentry + DM | основной не ответил, счёт выставил резервный (только при включённом автофоллбэке) |
| `amount_mismatch`, `paid_after_terminal`, `refund_on_pending` | Sentry + DM | денежные аномалии, разбирать вручную |

Контракт провайдера и открытые вопросы —
[`../reference/freekassa-api.md`](../reference/freekassa-api.md).
Все переменные окружения — [`../reference/env-vars.md`](../reference/env-vars.md).
