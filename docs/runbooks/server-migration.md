# Рунбук: переезд контура на другой VPS (Dokploy → Dokploy)

Отработано 2026-07-27 на переезде Boston → Frankfurt. Заняло около трёх часов,
из них окно с остановленным приёмом — примерно десять минут.

Здесь только то, что нельзя вывести из документации Dokploy: она про миграцию
почти ничего не говорит, а половина шагов ниже — следствие живых граблей.

---

## Что переносится чем

| Слой | Чем переносится | Комментарий |
|---|---|---|
| Проекты, приложения, домены, git-доступ, destinations R2 | дамп БД `dokploy-postgres` | приезжает целиком, вместе с ID сервисов и паролями БД |
| **Значения env** | **вручную через API** | см. грабли §1 — дамп приносит шифротекст, который новый инстанс не откроет |
| Данные приложения (Postgres) | `pg_dump -Fc` → `pg_restore` | ролям — предшествовать, см. §2 |
| Ручные конфиги Traefik | руками из [`infra/traefik/`](../../infra/traefik/) | не переносит ничего, см. [`deploy.md`](deploy.md) |
| Системный crontab | руками из [`infra/crontab.example`](../../infra/crontab.example) | адрес переписать, см. §4 |
| Сертификат www/apex + lego | `tar` каталога `/opt/lego-oplatishka` + `certs/` | вместе с ACME-аккаунтом, иначе обновление перестанет работать |
| **Агенты наблюдаемости** | руками: Alloy (`/opt/alloy`) + скрипт сводки `oplatishka-status.sh` | см. §8 — забыть легко, заметить трудно |
| **Домен админ-панели** | A-запись `admin.*` + файл `oplatishka-admin.yml` в `dynamic/` | у панели НЕТ своего приложения — она часть `oplatishka-web`, поэтому дамп панели Dokploy её маршрут не несёт |
| **Привязка домена у @BotFather** | вручную, `/setdomain` боту персонала | при смене домена панели кнопка входа молча исчезает: `oauth.telegram.org` отвечает `Bot domain invalid`, а логи и консоль чисты |

Перенос БД панели даёт приятный побочный эффект: **прежний `DOKPLOY_API_KEY`
продолжает работать** на новом инстансе, и все ID сервисов (`oplatishka-web-wwrt50`
и прочие) остаются теми же — значит строки подключения в env и шаблоны Traefik
не требуют правок.

---

## Порядок

**Подготовка (прод продолжает работать, спешить некуда).**

1. VPS: чистая Ubuntu, Docker не ставить — Dokploy поставит сам нужную версию.
2. `DOKPLOY_VERSION=<та же, что на старом> bash install.sh`. Версии обязаны
   совпадать: restore чужой схемы БД панели не ляжет.
3. ⚠️ **Сразу зарегистрировать админа** — установщик публикует порт 3000 на
   `0.0.0.0`, а в Dokploy админом становится первый зарегистрировавшийся. Пока
   аккаунта нет, машину может занять любой, кто просканирует порт.
4. Firewall хостера (не `ufw`: Docker пишет правила в `iptables` мимо него и
   публикует порты в обход) — оставить снаружи 22/80/443.
5. Перенести БД панели, env (§1), TLS и lego, конфиги Traefik, cron (выключенным).
6. Поднять сервисы, залить данные, прогнать смоук по `--resolve` на localhost —
   до переключения DNS домен ещё смотрит на старый сервер.
7. **Проверить доступность нового IP из РФ без VPN** — блокирующий шаг: если
   подсеть дросселится ТСПУ, переключать DNS нельзя.

**Окно.** Порядок именно такой, иначе данные разъедутся между двумя базами:

1. cron на старом — выключить (`mv /etc/cron.d/oplatishka /root/`);
2. приём на старом — остановить (`docker service scale <web>=0`);
3. финальный `pg_dump` → `pg_restore` на новом;
4. DNS на новый IP (короткий TTL заранее — у нас было 60 с);
5. вернуть отложенные роутеры (§5), дождаться сертификатов;
6. cron на новом — включить;
7. смоук; вебхуки проверить, а не предполагать.

Домены не меняются, поэтому адреса вебхуков L&P и Freekassa править не нужно —
только **IP в allowlist Love&Pay** (в их кабинете, минуты). Проверка без побочных
эффектов: запрос к их API с нового VPS должен отдать `401 MISSING_HEADERS`, а не
`403 SOURCE_IP_NOT_ALLOWED`.

## Грабли

### 1. Env зашифрованы ключом инстанса

В БД панели значения лежат как `enc:v1:…`, а ключ живёт вне базы (в свежих
версиях — docker secret `dokploy_auth_secret`). После restore новый Dokploy
расшифровать их не может и передаёт в контейнер **ноль переменных**: приложение
стартует без `DATABASE_URL` и платёжных ключей. У SRH это видно сразу (падает
в цикле, ища `srh-config/tokens.json`, потому что не получил `SRH_MODE=env`), у
Next.js — только по факту.

Обход: снять значения со **старого** сервера из спеки работающих сервисов, где
они в открытом виде, и записать через API нового — он зашифрует своим ключом.

```bash
ssh root@OLD 'docker service inspect <svc> --format "{{json .Spec.TaskTemplate.ContainerSpec.Env}}"' \
  | ssh root@NEW 'cat > /root/env.json'
# затем POST /api/application.update {applicationId, env: "K=V\nK=V"}
```

Проверка после деплоя — число переменных в контейнере:
`docker service inspect <svc> --format '{{len .Spec.TaskTemplate.ContainerSpec.Env}}'`.

### 2. Роли Supabase создавать ДО восстановления

`anon` / `authenticated` / `service_role` (см.
`packages/db/scripts/init-roles.ts`) обязаны существовать до `pg_restore`, иначе
политика `services_public_read_active` молча не создастся — `pg_restore` сочтёт
это одной проигнорированной ошибкой, а каталог перестанет читаться анонимно.
Роли кластерные, дампом БД не переносятся.

Заодно: дропая схему перед накатом, дропать и `drizzle` — иначе конфликтует
таблица истории миграций и restore заканчивается «errors ignored: 5».

### 3. Бэкап-крон Dokploy оживает на новом сервере

Вместе с настройками приезжает расписание бэкапов в R2. Новый сервер начинает
писать в тот же бакет по тому же ключу — и при `keep 14` дамп ещё пустой базы
вытесняет рабочие копии. **Отключить сразу после restore**
(`update backup set enabled = false` + перезапуск `dokploy`, иначе уже
зарегистрированный крон останется), включить обратно после переключения.

### 4. Cron нового сервера не должен ходить по внешнему домену

Скопированный дословно crontab обращается к домену, который ещё указывает на
старый сервер, — то есть новый сервер дёргает джобы чужого контура (двойной
фулфилмент). Ходить в свой Traefik:

```
curl --resolve www.oplatishka.com:443:127.0.0.1 https://www.oplatishka.com/api/cron/...
```

SNI и Host остаются правильными, сертификат валиден, зависимость от DNS исчезает.

### 5. ACME сожжёт лимит, пока DNS смотрит на старый сервер

Traefik пытается выпустить сертификат каждую минуту и получает 404 со старого
сервера. У Let's Encrypt **5 неудачных валидаций в час на домен**; упёршись в
лимит, в момент переключения останешься без сертификата на час — а Telegram без
валидного TLS вебхук не принимает.

Роутеры доменов, чей DNS ещё не переключён, **отложить** (унести файл из
`dynamic/`) и вернуть после смены A-записи. Если ждать не хочется — форсировать
`docker restart` Traefik: он повторяет попытку сразу, не выдерживая паузу.

### 6. Роутеры не появляются от вставки строк в БД

Домены и basic-auth, добавленные прямым `INSERT` в БД панели, не порождают файлов
в `dynamic/`: Dokploy генерирует их в своих обработчиках. Роутер при этом может
сослаться на несуществующий middleware, и Traefik молча не поднимет его.

Лечится вызовом API поверх уже вставленных строк — `domain.update` и
`security.delete` + `security.create` (пароль в таблице `security` лежит открытым,
хеширует его Dokploy при генерации конфига).

### 7. CI деплоит по адресу панели

`.github/workflows/deploy.yml` берёт адрес из переменной `DOKPLOY_PANEL_URL`
(fallback — прежний хост). После переезда её надо задать, иначе триггер уходит на
старую панель, где приложения уже нет:

```bash
gh variable set DOKPLOY_PANEL_URL --body "https://dokploypanel.oplatishka.com"
```

Если панель закрыта basic-auth — открыть `/api/deploy` отдельным роутером
(`infra/traefik/dokploy-deploy-hook.yml.example`), иначе CI получит 401.
Проверка контракта — в [`deploy.md`](deploy.md).

### 8. Мониторинг молча остаётся на старом сервере

Agent Alloy и скрипт сводки `oplatishka-status.sh` (лежит в каталоге бывшего профиля Hermes; сам агент из мониторинга выведен треком ops-group) живут вне Dokploy, поэтому не переезжают ни с
чем. Коварство в том, что снаружи это незаметно: дашборд продолжает показывать
данные (старые, от контейнеров прежнего узла) и выглядит живым, а логов прода в
нём нет вовсе. Алёрт на ошибки при этом тоже мёртв — его запрос возвращает
пустоту, а пустой результат срабатыванием не считается.

Что перенести и проверить:

```bash
# логи
scp /opt/alloy/config.alloy NEW:/opt/alloy/config.alloy      # креды внутри, chmod 600
docker run -d --name grafana-alloy --restart unless-stopped \
  -v /opt/alloy/config.alloy:/etc/alloy/config.alloy:ro \
  -v /var/run/docker.sock:/var/run/docker.sock \
  grafana/alloy:latest run --storage.path=/tmp/alloy /etc/alloy/config.alloy

# скрипт сводки (ему нужен свой .env с read-токенами Loki и Sentry)
scp -r /root/.hermes/profiles/oplatishka NEW:/root/.hermes/profiles/
```

На старом сервере **переименовать узел** в конфиге (`node = "...-legacy"`),
иначе его логи смешаются с продовыми под одной меткой. Метку нового узла,
наоборот, сохранить прежней — на неё завязаны алёрты и дашборды.

⚠️ Переносить `.env` профиля Hermes целиком не надо: там сотни ключей от всего
подряд (биржа, GitHub, LLM-провайдеры), а скрипту нужны шесть — токены чтения
Loki и Sentry. Лишняя копия секретов на боевом сервере это чистый риск.

Проверка, что канал ожил: `bash oplatishka-status.sh` на новом сервере покажет
непустую строку «История логов в Grafana Loki».

### 9. Комментарии в env Dokploy понимает

Проверено на dev: строки, начинающиеся с `#`, отбрасываются, число переменных не
меняется. Поэтому env можно держать читаемым — секциями и с пояснениями. Но
комментарий писать **над** переменной: `KEY=value # текст` многие парсеры считают
частью значения, и в прод уедет токен с хвостом.

## После переезда

- Смоук: все домены, `/api/health`, каталог (читается из БД), Mini App, вебхук
  Telegram (`getWebhookInfo` — там же виден `ip_address`), cron в `syslog`.
- **Перезагрузить сервер и убедиться, что контур встаёт сам** — swarm-сервисы,
  Traefik (`restart: always`), cron, fail2ban. Дешевле проверить сразу, чем
  выяснять при первом внеплановом ребуте.
- Старую прод-БД не удалять сразу: остановить и держать неделю как резерв отката.
- Ротировать `DOKPLOY_API_KEY` — после переноса базы он открывает оба контура.
